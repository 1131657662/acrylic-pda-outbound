原归档恢复库、私有文件和Pixel_6数据保留。本轮没有启动模拟器、操作M71、切换公网后台或启动公网Worker。

## 实际场景

| 合成批次 | Worker扫描前 | 实际结果 |
| --- | --- | --- |
| 超时待审 | REVIEW_REQUIRED，创建时间超过30分钟 | 提醒表及订单时间线各新增1条；仍待审，没有自动出库或释放占用 |
| 未到期待审 | REVIEW_REQUIRED，创建时间不足30分钟 | 多轮扫描始终没有提前提醒，原占用保持 |
| 扫描前已批准 | 通过真实HTTP批准为SUCCEEDED | 即使创建时间已超时，也没有补发提醒；原成功回执和出库资料保持 |
| 扫描前已拒绝 | 通过真实HTTP拒绝为REJECTED | 没有补发提醒，原预留/事实保持，没有自动释放 |
| 已提醒后再批准 | 对第1种批次调用真实HTTP批准 | 正常出库后再次扫描，原提醒ID/时间/正文保持，不新增、不改写历史提醒 |

每轮用实际订单详情、原提交结果和操作时间线API核对。系统生成的提醒操作人为空，仍通过时间线API完整返回，正文关联正确批次；对应API继续按各账号自己的仓库访问。

## 回滚、重试与两个 Worker

1. 在专用库创建仅拦截`SUBMISSION_REVIEW_REMINDER`审计写入的临时触发器，模拟提醒事务中的审计存储失败。
2. 首个真实调度任务进入`RETRY`，attempt1、错误码`HANDLER_FAILED`，下次可执行时间比失败更新时间晚5秒。此时提醒表和时间线均为0条，任务未伪装成功，证明提醒与审计一起回滚。
3. 读取失败证据后撤除触发器。同一任务ID按默认退避自动重试，attempt2转为`SUCCEEDED`，仅产生1条提醒和1条时间线。
4. 启动第二个独立Worker，共用原任务表和分钟幂等键。两个进程的日志均有真实领取并完成的任务；后续自动扫描没有重复提醒。
5. 显式批准已经提醒的批次后，等待下一轮真实调度并再次比较业务摘要。审批是HTTP命令的结果，Worker没有再次出库、改审批结果或释放库存。

最终收尾时共9个调度任务成功，其中首个经历上述1次预期故障与自动重试；总提醒数始终为1。所有任务最终无活动租约，故障触发器已撤除。这里只验证两个运行中的Worker协作，不将其冒充Linux systemd退出143修正或主机断电验收。
