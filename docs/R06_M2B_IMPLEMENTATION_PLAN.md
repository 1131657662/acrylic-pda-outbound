## 5. 事务与锁顺序准备

M2b-1 仍是只读查询，不因此新增写锁，当前可派工。以下为后续写子批的待验证方案。完整锁图必须包括 `ServerState.lockWritable`、`user_management_guard`、用户行、`WarehouseBaseline.read(..., true)`、`PdaAuthLocks.device` 及会话锁；还须展开外键带来的隐式锁，不能只登记显式 `FOR UPDATE`。新 Web 决定建议明确 `READ_COMMITTED`，入口预检只用于早拒绝；真正授权必须在锁后重验，避免把锁前普通查询的 RR 快照继续当作当前权限。

已识别的静态风险：`UserAccess.lock` 先取人员管理 guard；`UserStore.update` 再更新 `app_user` 并重建 `user_warehouse`。V1 外键检查会对 `warehouse` 父行取得共享锁，因此旧提案“仓库锁 → 用户锁”可能与人员更新形成仓库/用户反序。`TemporaryAccess.lock` 已明确 guard 先于仓库/设备/会话；`PdaAuthLocks.device` 内部先锁仓库再锁设备。不能直接复用已持仓库/设备锁的 `SubmissionAccess` 后再补取 guard 或用户锁。

拟共享前缀调整为：恢复屏障共享锁 → `user_management_guard` → 本动作需要的用户行（按 ID 排序）→ 仓库行（按 ID 排序）→ 必需设备行（按 ID 排序），之后再按 scope、order/活动槽、submission、bale 的 ID 排序锁定；会话锁及所有外键隐式锁的位置必须一并纳入完整图。用户集合包括实际决定者及本次需重验的原操作者，设备集合按动作确定。该顺序只是供整合执行者核验的提案，须与现有人员更新、设备准入、PDA 上传/取消、正式/PC 领取和库存发布逐项对照；有相反路径时由单一共享模块负责人调整统一方案，不能在单个服务私自补锁。

**写阶段阻断仍未关闭：**本轮没有实测上述死锁，也没有修改或证明锁序已修复。M2b-2a 及之后写入口开工前，须完成包含 guard、外键和会话的锁图，并以真实 MySQL 多连接覆盖人员授权变更与决定/关联/最终化互相等待、撤权和回滚；证据经独立复审后才能关闭对应阻断。此项不阻止 M2b-1 只读候选开发。

用户锁后重新调用当前身份/角色/仓库鉴权，设备锁后重验设备版本、原资格及当前准入。有效权限来源是服务器当前记录，不接受客户端传入权限版本作为证明。资格历史与当前调用者的权限分别核验，不将当前确认者替换为原上传者。

业务锁集合先收集，锁后核验 canonical/current/round；如果关联导致集合改变，回滚重取，禁止持锁逆序补目标。涉及两来源/订单时统一排序；共享仓库锁可供当前正式发布与候选核对序列化，能否覆盖所有入口须用锁图和并发测试确认。

决定表和命令回执应在同事务插入；唯一键保护命令身份和当前决定版本。同键异正文拒绝；不同键竞争同一上下文以条件更新/唯一约束裁决。写审计失败全部回滚，不出现“决定生效但原回执缺失”。未来成功路径必须先准备可验签回执，再在一个事务完成逐包防重、可选扣账、结果、状态、审计与 outbox；不新增平行记账栈。
