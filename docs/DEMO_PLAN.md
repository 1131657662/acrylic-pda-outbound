```text

       ScannerAdapter 有界FIFO入口
                 ↓
       Room 持久输入 + 来源/周期/序号
                 ↓

                 ↓ 结束作业后
```

## 4. 广播与物理按键接入

### 4.1 扫码广播

| 参数 | 值 |
| --- | --- |
| Action | `com.android.decodewedge.decode_action` |
| 首选字符串 Key | `com.android.decode.intentwedge.barcode_string` |
| 备用 Key | `com.android.decode.intentwedge.barcode_data`，先诊断实际类型和编码，未验证前不启用推测转换 |

Activity 的可扫码生命周期内注册接收器，按目标 SDK 使用兼容的接收器导出设置；厂家为外部应用发送时不能误设为仅本应用可见。若有厂家签名权限/定向广播，实测后采用；普通广播仍按不可信输入处理。

回调只复制完整字符串、接收时间及不可变上下文，交给专用单消费者，不在回调访问网络或等待写库。进出页面、屏幕休眠、重启恢复不能重复注册造成双收。应用失去前台停止扫码并明显提示，恢复时核对未决队列；后台扫码不属于本 Demo 的可靠接收承诺。

验证首尾空白和结束符规则，记录原字符串与规范化值，禁止截断到11位或将字母 O 改为数字0。短时间扫相同条码必须留下重复尝试，不能时间防抖吞掉。

双通道验证包括：扫码时焦点在非编辑区域、手输框、汇总弹窗、错误提示时是否发生键盘注入；自动结束符是否会触发保存。若仅广播无法配置且应用无法可靠区分自动回车与人工回车，判接入失败，先解决固件/厂家接口，不能让厂家自动 Enter 误确认手输或错误。

### 4.2 按键映射与确认

| 键 | 目标动作 | 验证 |
| --- | --- | --- |
| 正面/左/右扫描键 | 触发厂家扫描；应用记录能观测到的事件 | 某些固件扫描键由系统消费；有广播不等于应用收到键码，按实际能力记录 |
| Enter | 确认屏幕当前capture/inputRevision | DOWN/UP成对、repeat不重复、无候选不储存额度 |
| K1 → 逻辑F1 | 校验完整手工输入 | 实测配置键码，手输未F1不得保存 |
| K2 → 逻辑F2 | 当前允许的辅助/放弃未确认项 | 已确认项目不清除；长按不连发跨候选动作 |

`dispatchKeyEvent`/兼容事件适配统一处理，避免 EditText 的 IME action 与 Activity 同时消费一次回车。映射配置持久保存但不能覆盖系统必需返回行为。错误确认使用专门上下文，整次按下释放只确认当前错误，不提供下一包的人工确认；恢复后的自动项使用各自持久策略保存。

测试长按、双击、左右扫描键、先回车后校验结果、A保存时B/C广播到达、无候选回车、软键盘打开、切页、应用重建。记录每个确认所绑定的capture，而非只统计Enter总次数。

## 5. Room、序号与持久化实现

### 5.1 最小但完整的本地业务模型

直接遵循 V2.3 §11：local_inventory_snapshot/bale、local_cloud_bale_state、local_order/line、local_input_capture、local_scan、local_barcode_guard、local_device_state、local_operation_event、local_candidate、local_submission，以及测试授权/恢复控制。诊断结果另存，不污染业务计数。

- 输入/扫码都有 origin_device_id；设备序号唯一约束为 `(origin_device_id,device_capture_seq)`，审计为 `(origin_device_id,local_seq)`；订单扫码号跨修订/续作/换机不重置。
- 完整输入持久化时固定 expectedDispatchCycle、sourceRecoveryEpoch、原订单/库存/授权上下文。
- 接收、确认意图、最终保存是清晰可观测的耐久事务。最终事务包含重复/产品/计划复核、scan、guard、汇总、审计及 COMMITTED 终态。
- BUSINESS_REJECTED 留下确认和原因、不产生有效scan；STORAGE_ERROR 停止保存，恢复后先查是否已提交。失败写盘时即使错误状态无法写入，也保留之前耐久的确认意图。
- 汇总读有限字段、最近记录有限行；全明细分页，不加载所有库存/历史为Kotlin对象。

### 5.2 WAL/FULL 与文件

在实际 Room/SQLite 连接上验证 `journal_mode=WAL`、`synchronous=FULL`、foreign_keys，记录每次连接/重开后的值，不能只在一个临时连接执行 PRAGMA 就宣称全部有效。使用 SQLite 支持的事务和检查点方式；压力测试中不以 OFF/NORMAL 降低耐久性换速度。

业务成功反馈发生在 Room 事务真正返回成功之后。输入/确认仅进入内存不算可靠；第一次写盘前突然断电无法凭空恢复，应在报告中量化界限。不把每250ms延迟批量刷盘后补写全部成功的方式当成逐包耐久达标。

导出须暂停业务写入并通过一致性读取/受控导出得到 JSON/NDJSON 及必要恢复包。需要完整DB证据时使用已验证的一致性备份方式，正确处理 WAL；禁止运行时只复制 `.db` 而遗漏 WAL。

### 6.3 指标与计算

每个capture记录外部基准编号、输入来源、originDeviceId、orderScanSeq、完整字符串、单调时钟各阶段时间、确认ID、终态、错误码、队列长度。外部基准独立存放，不由“已保存的行”反向生成期望序列。

| 指标 | 门槛/目标 |
| --- | --- |
| 必须吞吐 | 4包/秒持续10分钟，输入/有效确认/有效保存各2,400；无静默丢弃、错误重排、持续积压 |
| 全合法序列一致 | 外部基准→广播→持久输入→确认→有效scan逐项一致，差额0、重复0、字符错误0 |
| 接收回调 | P99≤5ms目标；不含异步业务写库 |
| 自动完整输入接收→耐久保存；人工回车→耐久保存分别计算 | P95≤100ms、P99≤200ms目标；记录最大值及超标事件 |
| 每包数据库服务耗时 | 接收+预校验+确认+最终保存累计均值≤125ms目标，分别记录分位数；不以单条INSERT代替 |
| 队列 | 入口64/预警16为初值；目标负载无溢出，停止输入后1秒内排空已确认有效项 |
| 无错误反馈 | 成功音/已保存状态后数据可恢复；业务拒绝无成功音，错误未处理时不被后续成功遮盖 |

统计时间使用 elapsedRealtimeNanos 等同一启动内单调时钟，跨重启用 bootSessionId 分段；手机墙上时间只用于显示。保留原始逐事件数据及脚本计算结果，不能只交平均值截图。

判定沿用V2.3 §16.1：完整4包/秒、固定确认策略、零未解释丢失、严格顺序及PSS是必须门槛；100ms/200ms、回调5ms、数据库服务均值125ms属于初始技术目标。目标未达如实记录，不改数值、不标记为达标。用户已通过Q17收敛剩余范围，不因初始时延目标未达追加Demo调优或重复压测；剩余现场验收按本节开头三组执行。

## 7. SoundPool 音效时延

提前加载短 WAV/PCM，少量采样、有限流数，load完成后才开放声音测试；不在扫描回调解码或新建播放器。成功、错误、完成各用可分辨音，成功短音建议40～80ms，避免250ms节奏下长音叠压。

记录三个时刻：事务完成、调用play、实际声学起音。`SoundPool.play()`返回不代表扬声器已出声；返回0视为播放失败并记录。用外部录音配合可见同步标记/经校准的视频时间轴測实际起音；说明仪器采样率、帧率与测量误差，不靠人工“感觉很快”。

| 检查 | 验收 |
| --- | --- |
| 保存完成→play调用 | P95≤20ms的初始工程目标，报P99和最大值 |
| 保存完成→实际起音 | P95≤100ms、P99≤150ms的初始Demo目标，给测量误差；未测声学不能填写为已通过 |
| 连续成功音 | 连续4包/秒时无长音排队；每次有效保存有对应反馈事件 |
| 错误优先 | 重复、超量、保存错误时暂停后续业务反馈，错误明显，不能把前一成功音理解为失败包成功 |
| 音效关闭 | 应用静音仍更新明确视觉反馈；厂家识别音单独检查，不承诺应用开关控制厂商音量 |
| 预载/音频异常 | 音效失败不撤销已提交数据，不重写第二份scan；显式显示声音故障并记录 |

上述声学阈值是本计划新增的验证目标，达不到需给出原因和解决办法后复测；不能为了音效指标把成功音放到事务完成前。

## 8. 断电、重启与失败终态验证

### 8.1 注入点

| 点位 | 操作 | 正确恢复结果 |
| --- | --- | --- |
| D0 广播已到、首次接收未持久化 | 杀进程/实际断电 | 可能无记录；不能曾显示耐久已接收或已保存；报告边界，现场重扫核对 |
| D1 输入已提交、尚未登记确认 | 故障后重启 | AUTO 按原策略复核并最多保存一次；MANUAL 仍待人工确认；原序号不变 |
| D2 确认意图已提交、最终事务前 | 故障后重启 | 查同capture是否已保存，再按原上下文完成一次；资格失效明确拒绝或对账 |
| D3 最终事务写入中 | 中止进程/断电 | 明细、guard、汇总、审计、终态全有或全无，没有半包 |
| D4 事务完成、成功提示前 | 立即断电 | 记录存在且唯一；重启不因上次未响音而再写一份 |
| D5 成功音/已保存显示后 | 立即断电 | 已成功反馈的记录耐久存在，顺序、数量和重量正确 |
| D6 冻结正文写入/登记交界 | 中断 | 没有“已冻结但文件缺失”；孤儿文件可核验处理 |

可在测试构建中添加仅用于定位时机的闸门，不改变事务内部写入顺序或耐久配置。每个D1～D5先进行至少20次进程终止验证，再进行至少10次实际供电中断验证；D0/D6另覆盖边界。每次保留故障前后DB和原始观测证据，不把成功样本覆盖失败样本。

**实际断电方法须基于 M71 硬件能力确认。**拔USB但电池仍供电不是断电；`force-stop`、普通重启或长按电源正常关机也不能替代闪存突失电。使用厂家允许的可拆电池/工程电源方式，由现场人员操作；若无法实施真实断电，只能报告进程恢复通过、硬断电项未验证，不能将整项勾选通过。

### 8.2 必须出现明确结果的失败场景

- 仅剩一个产品名额，两个候选均预校验并已确认：一个保存，另一个 BUSINESS_REJECTED；用户确认错误后可继续，原确认不转移。
- 低空间、磁盘写失败、提交结果未知：STORAGE_ERROR 暂停；若错误状态写入本身失败，原持久CONFIRM_REQUESTED仍可用于恢复。
- 保存前授权到期、已知周期改变或服务器恢复代次改变：不自动换上下文补存，保留原来源证据。
- 长按Enter、连续回车、错误确认弹窗：一个物理动作最多影响一个对象。
- 原机与接收机序号均从1开始的交接夹具：来源唯一不冲突，订单高水位连续；原来源不可被接收机覆盖。实际两台交接在有第二台时复测。

故障恢复后检查事务关联、外键、唯一约束及 `received=saved+voided+invalid+businessRejected+discarded+pending`；数据库可读时做完整一致性校验。不得以删库/卸载恢复作为通过方法。

## 10. 峰值内存、闪存与长时稳定性

**必须门槛：应用进程PSS峰值≤250MB，包含Java、native、图形及音效等内存，不只看Java heap。**统一报告以 MiB（bytes/1024²）记录数值并同时注明项目沿用的“250MB”门槛；为避免单位放宽，验收按不超过250,000,000 bytes，即约238.4MiB执行。

| 场景 | 采集 |
| --- | --- |
| 冷启动/库存导入并激活 | 低频周期采样加导入/解压/切换前后事件采样，观察最高PSS |
| 四档扫码各10分钟 | ADB dumpsys meminfo 等采集PSS，保存每轮峰值与时间线；同步记录GC和帧卡顿 |
| 4包/秒复测及30分钟混合 | 查泄漏、列表增长、SoundPool资源和入口积压 |
| 90天历史夹具 | 冷查询、扫码、汇总、分页、故障恢复、受控导出，不能只测试空库 |
| 多次页面进出/重建 | 不重复注册接收器，不保留旧Activity/声音/数据库监听 |

常规PSS采样可先1秒一次，关键阶段加密；ADB采集会扰动性能，另跑相同负载对照并说明采样间隔可能遗漏短峰。需要借助 Android profiler/系统跟踪查瞬时分配，不能把稀疏采样最大值写成绝对内存上界。调试构建用于定位，最终用接近发布配置的构建重复验收。

2026-09-16测量修订：本机应用内memtrack读取受限，补充含Graphics的主机`dumpsys meminfo --local`采样。普通详情采样会回调应用进程，已观测到相关停顿，须保留受干扰轮并用相同速率对照；不通过删除慢记录修正指标。当前主机采样间隔2秒，应用内原1秒诊断继续保留，两者不能混称为绝对完整峰值。

数据库缓存、RecyclerView列表、入口队列、日志缓冲、声音流数设定上限；不在扫描过程中同时导入历史数据或清库。记录数据库、WAL、索引和导出文件大小、剩余磁盘；低于阈值提前阻止新任务并保留现有数据。

### 2026-09-16：B 模式数据库事务优化（0.1.7）

0.1.6 的自动路径有接收、预校验、意图、最终保存四次耐久提交；首轮总时延超标，证据保留。0.1.7 对 AUTO 的预校验与自动意图使用一个 Room 外层事务，包含原状态变更及确认审计，整体成功返回后才记 CONFIRM_DURABLE。原始接收仍先独立落盘；最终 scan/guard/数量/重量/审计/终态仍同一事务提交。原来自动路径的 WAITING_CONFIRM 中间态不单独对外宣称耐久。MANUAL 与旧候选仍保持四段和人工确认。

全链路计时从完整接收开始，不删除任何阶段。VALIDATED 的 dbServiceNs 包含自动确认同一事务，CONFIRM_DURABLE 标记 serviceIncludedIn=VALIDATED、耗时为 0，避免重复累加；实际总时延不依赖这些分段指标。D1 原接收后故障、D2 组合事务后故障、D3 最终保存中故障均保留验证。WAL/FULL、失败处理、原序号和幂等语义不变。性能门槛未改，须新 APK 真机复测。

### 2026-09-16：独立按键向导（0.1.8）
