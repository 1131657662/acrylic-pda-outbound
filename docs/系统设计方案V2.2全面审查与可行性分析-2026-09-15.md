# 系统设计方案 V2.2 全面审查与可行性分析

**审查日期：2026-09-15｜被审查版本：V2.2 方案评审稿｜审查对象：docs 全部 8 份现有文件及用户最新确认**

## 1. 审查结论

**总体技术可行，架构选型有条件通过；V2.2 仍需修订后才能冻结为各端共同遵循的开发与验收基线。**

保留 **Vue 3 + TypeScript + Vite + Element Plus、Java 21 + Spring Boot、宿主机 MySQL 8.0.45、Kotlin + Android View + Room**。没有发现需要改用 PostgreSQL、React、微服务或 WebView 扫码的理由。主要风险集中在跨设备数据来源、异常提交恢复、出库周期与灾后对账，换框架不能解决这些问题。

V2.2 已经覆盖完整功能目标，并修正了旧版大量关键问题。但是，“功能被列出”“规则方向正确”“数据与接口可以直接实现”“真机已经达到指标”是不同的完成程度。本次发现 **7 项 P1 设计问题、7 项 P2 细化或文档问题**，详见第 4～6 节；另列出性能与部署验证条件，不把尚无软件的压测缺失误称为运行故障。

| 评估事项 | 判断 | 对下一步的影响 |
| --- | --- | --- |
| 完整业务范围 | 基本覆盖 | 多产品、临时单、修改作废、审计、扣账、导出均保留；PDA 打印按用户要求取消 |

## 5. P1：需优先修订的设计问题

### F01：换机时必须保留每条记录的原设备与序号空间

**依据：**[换机规则 §6.5](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:461)、[扫码顺序交接 §7.4](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:563)、[Room 表 §11.1](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:955)、[本机设备身份说明](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:967)、[完整上传示例](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1197)。

**问题：**云端 `scan_record` 已用 `(origin_device_id, device_capture_seq)` 唯一，但本地 `local_scan` 对 `device_capture_seq`、`local_seq` 分别单列唯一，且允许从“本机固定设备身份”推导原设备。上传明细没有逐条 `originDeviceId`，顶层也只有本次授权信息。

**触发例子：**A 机记录设备接收序号 21、审计序号 101；B 机以前也产生过这些序号。把 A 的恢复包导入 B，会遇到本地唯一键冲突；如果改写为 B 的设备身份，又会破坏审计与离线授权的原始归属。B 机最终上传也不能仅凭当前登录设备解释 A 的历史记录。

**建议修订：**

1. 每条采集、扫码及转存审计显式保留原设备注册身份；设备序号按原设备命名空间唯一。当前接收/上传设备另记，不覆盖来源。
2. 若恢复记录进入同一 Room 表，把设备级唯一键改为“原设备 + 对应序号”；也可用独立恢复只读表，但必须定义统一查询和最终提交方式。
3. `order_scan_seq` 继续全订单唯一，跨设备、修订不重置。交接恢复包明确原授权、原版本、完整高水位和批准保留的 capture 清单。
4. 新设备只能提交经服务端认可的旧来源记录；普通请求不能借新增 originDeviceId 冒充任意设备。
5. `frozenEventSeq` 和审计确认不能只用一个本机标量涵盖所有来源，改为每来源检查点，或引用已完整确认的交接包加本机检查点。

**关闭证据：**使用两台均有历史数据、设备级序号重叠的设备，完成换机、续扫、提交、审计补传和 Excel 导出。来源不变、订单序号不变、无唯一键冲突、无伪造来源放行。

### F02：冻结每次扫码所见的出库周期，防止旧数据进入新周期

**依据：**[出库周期定义](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:235)、[云端周期字段](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:851)、[本地状态与 guard](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:950)、[扫码上传明细](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1197)。

**问题：**`dispatch_cycle` 已出现在包、出库事实、状态流和本地 guard 中，但没有进入持久输入/扫码字段和冻结上传明细。快照主要固定型号与重量，也不能替代“本次允许的是哪个出库周期”。

**触发例子：**B 机在周期 1 离线误扫了一包，未上传；A 单将该包确认出库，后来完成真实退货并开放周期 2。B 的旧数据此时到达，如果只读取包当前周期 2，就可能把周期 1 的旧操作当作新一次合法出库。最后仍需有显式的过期周期校验，不能只靠时间或当前 claim。

**建议修订：**

1. 输入及扫码记录固定 `expectedDispatchCycle`，随提交正文参与摘要；服务器比较期望周期与当前允许周期。
2. 旧周期不自动升级，进入明确冲突/恢复流程。没有周期信息的兼容请求不能在发生周期切换后自动入账。
3. 新周期的本地重新开放，只能依据更高版本的已审核恢复事件，且不得清除未提交、待审、未知结果的旧周期占用。
4. 周期递增、实物确认、原出库状态、占用及账务反向凭据应在受控事务内协调；一份恢复凭据不可多次递增周期。

**关闭证据：**“旧机离线 → 其他订单出库 → 退货 → 旧机迟到上传”必须拒绝自动入账；同步新周期后发生的新扫描可以正常出库。

### F03：让“请求尚未到达也能取消批次”具有可落库的模型

**依据：**[原子 abort 要求](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:787)、[非空字段原则](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:822)、[submission 表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:873)。

**问题：**原文正确要求：查询不到不等于没有在途请求，abort 要建立永久标记。但 `submission` 的版本、正文摘要、文件路径、期望汇总等没有标为可空，也没有独立取消标记表或最小提交头状态。如果原上传尚未到达，服务端未必拥有这些信息，不能照当前字段规则创建取消记录。

**建议修订：**选择一种统一实现并写入数据字典：用可先创建的提交控制记录承载身份、目标和终态，再关联正文；或者让 submission 按状态允许正文尚未存在，并用约束保证成功时所有必需字段齐全。不得伪造空正文/零摘要来填必填字段。

abort、首次接收、分块 finalize、审批最终入账必须竞争同一个稳定控制记录；首次并发插入由唯一键裁决。取消请求仍须验证调用人、设备和目标归属。该标记在受支持的迟到/重试与账据保留窗口内不可随上传临时文件一起清掉。

**关闭证据：**故意让 abort 先到、原上传后到；反过来让提交先成功；再并发首次建行。结果只能是“取消有效且永不入账”或“返回既有成功回执”，没有可复活的中间状态。

### F04：退审与取消传输之后，还需要独立的业务续作过程

**依据：**[临时单拒绝/关联](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:475)、[提交终态](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:778)、[待审占用](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1315)、[接口目录](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1023)。

**问题：**原文已经指出拒绝不等于卸货，但没有统一定义 `REJECTED/ABORTED → 允许续扫 → 新批次` 的授权和占用迁移。云端只限制一个成功批次，未明确同单多个未终结批次的选择规则。本地一旦重新提交，新 submission 的占用与旧待审批次的占用如何关联也未定。

**触发例子：**临时单 S1 含 80 包，待审占用指向 S1；主管退回补扫后提交 S2。如果原占用仍只属于 S1，S2 可能与自己冲突；如果 abort 自动释放全部占用，已装车货物又可能被其他订单使用。S1 的迟到批准还可能与 S2 竞争最终入账。

**建议补充统一状态转换矩阵，至少规定：**

| 动作 | 提交正文 | 作业资格与库存处理 |
| --- | --- | --- |
| 仅取消未成功传输批次 | 原正文保留、终态固定 | 不等于取消订单、卸货或释放已知实物占用 |
| 退回修改/补扫 | 原批次不可改，记录被替代关系 | 主管明确恢复作业资格；旧批准失效；旧包占用在续作期间保持可追溯 |
| 新批次替代旧批次 | 新 ID、新摘要 | 单事务选择唯一有效候选；保留包转移归属，减少的包需卸回/纠错凭据 |
| 临时单关联空白正式单 | 原始输入和正文不改 | 固定唯一目标、处理原临时记录状态，迁移占用并同步 PDA 对应关系 |
| 冲突处置后重新提交 | 原冲突证据保留 | 明确哪些包归谁，不能只删除冲突行便自动放货 |

入口可复用现有 change-request/decision API，不强制增加新路径；但必须给出明确命令、前置状态、版本、权限、失败响应与恢复方式。严重异常“提交给主管查看”与“允许最终入账”也要分别定义，避免本地冻结拦截使后台永远看不到待处理资料。

**关闭证据：**退审补扫、退审减包、取消后重提、临时关联、旧审批迟到，均只有一个当前有效提交目标；无过早释放、永久锁死或重复出库。

### F05：更正后应区分原始事实、调整凭据与当前有效结果

**依据：**[已上传更正规则](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:453)、[汇总/导出](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:519)、[结果与账务表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:876)、[更正表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:893)。

**问题：**已定义更正凭据和出库反向状态，但未明确审批通过后，`order_line_result`、订单状态、默认汇总、实际 PDF 和 Excel 如何表现更正。`scan_record` 只保存原确认记录，不能仅靠查询这些行得出当前有效净出库。关闭自动扣账时也不能反向写入一笔从未发生过的自动扣减。

**触发例子：**原单 100 包，后来确认 1 包错误出库并完成实物恢复。原扫码事实仍为 100 条，当前有效结果可能应为 99 包；两者都合理，但必须有清晰口径。否则不同页面可能分别显示 99 和 100，旧回执与新报表又无法解释。

**建议修订：**

1. 区分非实物信息更正、错误出库撤销、真实退货；确定各自对有效结果、库存、周期和原订单的影响。
2. 原成功回执保持不可变；更正产生独立版本和凭据。页面同时可追溯原确认结果及当前有效结果，明确日期统计按出库日还是调整日。
3. 需要冲销账务时引用实际存在的原扣账流水，幂等反向一次；原单未扣账时只处理适用的出库事实与对账状态。
4. 标准“原始扫码明细”仍按原 `order_scan_seq`；调整单独成表。若提供“当前有效明细”，以独立名称说明筛选规则，不重排或伪装原顺序。
5. PDF/Excel 的数据版本固定到出库和更正版本，旧文件仍可解释，新版标记替代关系。仅保存生成时间或筛选 JSON 不足以重建任意历史状态。

**关闭证据：**更正前后、重复审批、扣账开/关、跨日统计、导出排队期间发生更正，所有数字都能由原事实与调整凭据复算。

### F06：数据库恢复之后，客户端回执和同步游标也必须对账

**依据：**[回执确认](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:978)、[备份与 RPO](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1418)、[隔离恢复](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1432)。

**问题：**V2.2 正确禁止回滚其他生产库，但没有说明本项目恢复到较早截点后，如何处理 PDA 已持有、服务器却丢失的成功回执、取消标记、授权和已推进游标。日常幂等建立在服务端这些记录仍存在的前提上。

**触发例子：**09:00 出库成功并回执，云端故障后只恢复到 08:55。PDA 认为已同步，服务器没有该单出库事实；其他设备可能重新获得相同库存，PDA 也可能继续使用比恢复后服务端更大的状态版本/游标。单纯重试、全量下载或把服务重新启动都不能安全解决。

**建议补充灾后恢复模式：**

1. 在恢复工具控制下生成新的服务器恢复代次，避免该代次本身又来自被回滚的旧备份。
2. 恢复期间暂停新授权和有风险的出库入账，保留上传证据入口。将受影响时间窗口、设备和订单纳入对账。
3. 同步响应携带恢复代次；PDA 发现变化后重新建立云端基线，保留本机 guard、未决数据、成功回执及冻结正文，不直接清空重下。
4. 对比各设备的提交 ID、正文摘要、回执、取消记录、授权和审计检查点。丢失服务端记录的旧成功结果进入恢复核对，不能当普通新订单盲目重放。
5. 有离线设备未完成核对时，按能确认的范围保持隔离；无法恢复的部分明确实物盘点，不能宣称获得完整原始扫码顺序。

**关闭证据：**故意恢复到一次成功提交和一次 abort 之前，随后旧设备、新设备分别联网。没有迟到请求复活、库存重复开放或游标永久卡住，恢复操作也不改变旧项目数据。

### F07：已确认但最终未保存的候选，需要明确的失败终态

**依据：**[确认与保存状态规则](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:665)、[本地队列状态](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:984)。

**问题：**第 8.4 节允许确认后展示下一条、后台顺序保存，并要求保存时重新校验；同时写了“失败后 F2 放弃或修正”以及“已确认且尚未完成不可编辑或 F2 清除”。队列枚举中也没有明确解释最终事务业务拒绝与临时写库失败如何离开已确认状态。

**触发例子：**一个产品只剩 1 个名额，A/B 在 A 最终提交前都完成预校验并各有确认意图。A 保存成功后 B 的事务复核必须失败。如果 B 仍停在 `CONFIRM_REQUESTED`，既不能保存又不能放弃，切单和冻结都会被未决队列阻塞。这是预校验与最终校验不同时发生时需要定义的分支。

**建议修订：**

- 明确“已确认待执行”“业务拒绝终态”“存储错误待恢复”“已保存”的区别，可扩展枚举，也可用状态加结果字段表达。
- 业务拒绝：保留确认事件和拒绝原因，不产生出库行，不把确认转交下一包；允许操作员确认处理结果后继续。
- 存储错误：不报成功，暂停业务保存；恢复后先按 scan/capture ID 检查是否已经提交，再对同一持久意图重试，不重复保存。
- 仅临时校验失败且尚未确认的候选可按原规则修正/放弃；已确认项目的处置需要专门命令，不能靠清空输入框隐式完成。
- 为待执行确认保留数量名额可减少此类冲突，但不能取代最终事务校验和失败出口。

**关闭证据：**预校验均通过但最终名额不足、保存前权限过期、低空间写失败等场景，都有可恢复状态；没有错误成功音、错用确认、丢事件或永久无法结单。

## 6. P2：详细设计和文档需补齐的内容

### F08：把全量状态与增量事件拼接成一个确定协议

**依据：**[同步清单 §9.2](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:759)、[outbox 发布规则](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:928)。

串行发布和分页高水位已设计正确。还需说明首次安装、游标过期时：当前可用状态从哪里生成、与哪个流高水位绑定、下载期间发生的出库如何补入、较旧实体版本如何忽略。不能读一份不断变化的全量列表，再任意取“此刻最新 cursor”作为已应用位置。

建议固定一份可校验的状态基线和起点，明确后续增量补齐规则；事件携带实体业务版本，流序号只负责传输排序。先应用一页及相关版本，再同事务推进游标。恢复代次另按 F06 处理。补充“全量下载过程中连续出库/恢复、旧事件后发布、页面重传”的验证。

### F09：补全数据字典，尤其是不可变映射与来源字段

**依据：**[映射规则](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:305)、[云端映射与订单表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:847)、[Room 表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:953)。

原文承诺映射版本保存型号、品名，但 `delivery_mapping` 只列 product_id 等字段；若 product 的型号/品名可改，仅指向同一产品 ID 不足以恢复旧映射。订单/临时单还需明确绑定哪个映射/规则版本，不能只在文字中说“固定”。

详细字典应补齐：

- 不可变产品描述或映射快照、版本引用、来源导入和生效信息。
- 原始扫码授权/版本与当前接手授权的区别，参见 F01。
- `local_order.updated_at`、`export_artifact.created_at` 等已被索引引用但字段栏未列出的列。
- 云端时间质量所需的原始偏差、单调时间、启动会话如何查询；若只留在冻结文件中，明确读取路径和保留期。
- 临时原因、作业区域备注、本机操作者/提交者/代传者、审批、每类状态枚举、默认值和精确类型。
- `inventory_import` 文件/解析版本/仓库去重如何用实际唯一约束实现，以及重新解析/重新发布的允许条件。
- guard、审计和扫码表之间的保留/引用规则，确保清理 30 天前的显示明细时不破坏长期防重证据。

这些是把“核心字段表”转为可执行迁移所需的工作；并不表示 MySQL 无法实现当前模型。

### F10：补齐关键接口、分块和处理状态的可恢复契约

**依据：**[API 目录及通用约定](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:990)、[提交与重试](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:772)。

普通提交示例已有较好基础，但完整开发不能只靠路径目录。优先完成以下契约：

| 契约 | 需要明确的内容 |
| --- | --- |
| 同步与授权续期 | stockStateCursor 的请求/响应位置；过期、撤销、恢复代次；续期是否保持原快照与 epoch |
| 换机与恢复包 | schema 版本、逐来源身份、序号范围、包体摘要、下载权限、原记录认可清单 |
| abort/续作/重新提交 | F03/F04 的最小字段、目标绑定、前置状态、占用处理和错误码 |
| 临时单关联 | 关联前后的唯一目标、原临时记录终态、PDA 映射更新与迟到请求返回 |
| 分块上传 | 切分对象是固定字节正文还是结构化记录；总块数/总字节/摘要、part 大小、缺块查询、过期后重建 |
| PROCESSING 恢复 | 谁负责推进、处理者崩溃后如何重新领取、状态查询如何反映积压；不能永久返回“处理中” |

| 审计补传 | 相同事件 ID/设备序号但异内容必须冲突；连续检查点不能越过缺口；异设备代传不改来源 |

| 正文规范化 | 安全整数/序号表示、空值、字符串、数组顺序、未知字段、各 schema 兼容规则及跨语言向量 |

分块边界处再明确文件与数据库的崩溃一致性：先持久保存文件、验证摘要，再登记可靠引用；过期清理不能删除待审、成功回执或恢复流程仍引用的内容。大订单不能在 PDA 或 API 中重新拼成无界对象集合。

### F11：安全措施还需落到身份生命周期与部署清单

**依据：**[身份表](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:831)、[本地身份](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:700)、[安全设计](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1400)。

当前已经有权限、Keystore、CSRF、模板隔离和日志脱敏，不应重复列为完全缺失。需要细化：

### F12：为容量与文件恢复窗口给出可验证预算

**依据：**[资源预算](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:195)、[保留和恢复目标](D:/acrylic-pda-outbound/docs/系统设计方案与开发计划.md:1418)。

当前 65G 可用和小于 1MB 的输入文件，只能证明当前起步规模较小。长期占用还包括快照版本、逐包多条审计、索引、提交文件、导出临时文件、binlog 和多份备份。第 8 节给出预算方法。

RPO≤15 分钟也必须覆盖不可重建的提交/恢复文件，不能数据库 binlog 每 15 分钟归档、正文文件仍仅每日备份。需选择同步文件归档或可证明的重建来源；绑定数据库截点、文件清单、摘要及归档完成位置。单独生成的 PDF/Excel 可按已冻结版本重建，但未审正文和恢复证据不能凭模板重建。

## 7. M71 性能与现场 UI/UX 可行性

### 7.1 设备适配判断

**M71 的 Android 9、2GB RAM、16GB Flash 不构成本方案的明显硬件不匹配；但无法仅由这些参数判断完整 4 包/秒一定达标。**

原生 View、索引查库、串行事务、有限列表、SoundPool 预载和后台按单上传，是适合该设备的选择。12,639 条库存不需要全量复制到 Kotlin 对象图。Hilt 采用编译期生成，选用它本身不构成需要更换设备的理由，具体依赖仍需锁定 Android 9 兼容版本。

DEVICE_SPEC 给出了 E3250/E3200 两种可能扫码头，没有给出确定的固件、闪存实测、设备密度和连续按键结果。V1.3 中“4核/8核、15小时续航”等也不能替代当前采购批次的实测。应保存每个被验证配置的设备诊断记录，不能用一台设备结果覆盖所有硬件/固件组合。

### 7.2 高速扫码的真正瓶颈

| 环节 | 当前设计 | 审查建议 |
| --- | --- | --- |
| 光学识别 | 厂商扫码头输出完整广播 | 以已知真实条码序列检验漏发/乱序/字符完整；软件无法修补未送达的内容 |
| 输入隔离 | 优先仅广播，必要时隔离键盘注入 | “输入框+广播”是现有设置事实；实施前验证可否关闭键盘注入和结束符 |
| 事件接入 | 回调轻量、有界 FIFO、不防抖丢事件 | 保留原始内容及接收顺序；明确页面退出和模式切换时的在途事件处理 |
| 回车确认 | 每包一次，绑定屏幕候选 | 不得预存未来确认额度；候选尚未可确认时的回车应有明确未接受反馈 |
| 输入/确认/保存耐久 | 三段必要持久操作，事务带审计 | 测完整服务耗时及长尾；不能只测单次 INSERT 或关闭 FULL 换速度 |
| UI 与声音 | 合并界面刷新，成功音在事务后 | 当前候选切换与可确认状态不能因 UI 节流滞后；普通统计刷新可以合并 |
| 上传/导出 | 扫码本地完成，网络按单进行 | 不把网络响应放进逐包保存路径；确定旧单后台上传与当前扫码是否允许并行 |

4 包/秒对应平均 250ms 一包。按当前设计至少包含输入持久化、确认意图持久化、最终业务保存三个阶段，数量级上是每秒约 12 次关键事务，另有必要审计写入和 WAL 检查点。实际是否每事务触发几次存储同步由实现和 SQLite 配置决定，不能简单以事务次数等同物理 fsync 次数。

原文建议每包数据库累计均值≤125ms，是合理的预留余量目标，但不是证明。需要同时检查 P95/P99、最长停顿、队列深度、闪存剩余空间、同步/上传干扰与长期数据积累。64 条队列可吸收短时抖动；如果保存速度长期低于输入速度，任何有限队列最终都会满。

### 7.3 验收口径应继续保留的硬条件

1. 在 M71 分别以 1、2、3、4 包/秒执行规定负载；4 包/秒 10 分钟为 2,400 个合法完整输入和 2,400 次逐包确认。
2. 对照外部已知序列，逐项核对条码和序号；“总数相同”不足以排除丢一条又重一条。
3. 光学输入、真实 Enter 键、应用注入分开记录结果；应用注入通过不能宣布现场整机通过。
4. 保留回车至耐久保存 P95≤100ms、P99≤200ms、进程 PSS≤250MB 等目标；达不到先定位瓶颈，不提前声称已满足。
5. 真机覆盖已接收未确认、确认已落盘、保存已提交、成功音之后的杀进程与掉电边界；首次持久化前没有可靠记录的输入不能凭空恢复。
6. 测试序列包含混产品、同秒、时钟回拨、撤销再扫、换机和分块乱序重传，最终 Excel 行顺序与本地有效扫描序列一致。
7. 用独立测试库或足够多的合成/真实可用条码，不关闭查重来满足吞吐。2,400 条是软件压力工作负载，不代表真实一车应装 2,400 包。

### 7.4 小屏与实体按键的补充建议

| 场景 | 可落地的建议 | 验收点 |
| --- | --- | --- |
| 队列积压 | 固定显示“当前候选、待确认数、已确认待保存数、最后成功条码” | 操作员不会把下一条显示误认为上一条已保存 |
| 候选切换 | 当前可确认 capture 与屏幕渲染同一状态提交；不对候选身份做普通节流 | 每次 Enter 绑定人实际看到的候选 |
| 手工补码 | 有明确手工模式、字母键盘、F1 和可达的屏幕保存；扫描输入仍独立处理 | 扫码注入不拼入手工草稿，不自动借用 F1/Enter |
| 错码/超量 | 固定反馈区显示失败包；错误优先，确认处理后继续 | 后续成功音不掩盖尚未处理错误 |
| 回车过早 | 明确提示当前无可确认候选或确认未接受，保留原输入 | 不能操作员以为按过回车就已保存，也不能把回车挪给后来的条码 |
| F2 | 扫码页含义固定，放弃队列候选须可追溯；存储失败用专门恢复动作 | 不跨候选清空，不删除后续队列 |
| 换人/切单 | 待处理输入先处理或留在原上下文；确认显示车牌与操作者 | A 人收到的未决输入不会静默变成 B 人操作 |
| 弹窗/切后台/锁屏 | 暂停新作业入口，已持久确认按明确策略完成或待恢复；回前台显示恢复状态 | 不在登录框、系统界面或错误焦点下悄悄确认下一包 |
| 戴手套/强光/噪声 | 主操作用实体键，至少 48dp 触控目标，大包数、完整当前条码、高对比文字 | 使用现场手套和实际环境验证，不以按钮尺寸代替触控能力 |
| 班次持续使用 | 适当保持作业页亮屏，测功耗、发热、充电及断电恢复 | 不把旧文档标称续航作为满足一班的证据 |

无需在 480×800 扫码页加入完整多产品表格。固定核心操作区、最近 1～2 条记录、另设汇总页，比缩小字号挤满所有信息更适合现场。

本轮没有查询外部依赖仓库，不能据此认定某个具体新版本仍在维护。实施应冻结 Java、Spring Boot、Flyway/MySQL 支持模块、Connector/J、Android Gradle/Room/Hilt、Vite、Playwright 及浏览器版本，并做许可证和兼容性核对；不能照旧项目版本字符串盲目复制。

盘点为 **4 vCPU、约 16GB 内存、约 10Gi 可用、根分区约 65G 可用**。API/Worker 初始约 2.5GiB 进程总上限与小连接池具有可行性，但不包含 MySQL 新增缓存、内核缓存及全部文件 I/O。新系统运行限额只限制本项目进程，不能保证旧系统高峰不会反过来影响本项目。

部署前应形成以下证据：

| 检查 | 具体判断依据 |
| --- | --- |
| MySQL 连接与权限 | 确认宿主机 3306 可新建本项目库/账号；不使用报表 3307；应用、迁移、备份权限分别核对 |
| 数据库耐久 | 核实 innodb_flush_log_at_trx_commit、binlog、sync_binlog 和存储行为；不为新项目擅改共享全局设置 |
| 基线负载 | 覆盖代表性业务高峰和 02:15、约 02:35、03:30 的已有备份/同步时段 |

### 8.3 数据增长预算

建议使用以下关系估算，实际系数由代表性数据测量：

```text
长期容量 ≈ 出库包数 × 每包扫描/审计/索引占用
         + 库存快照版本数 × 每版快照占用
         + 冻结正文/恢复包/导出/日志
         + binlog、备份副本与临时工作空间
```

例如，**仅作为敏感性分析**，假设每包扫描、必要审计和索引合计占 3～8KiB，按 365 天/年、保留 3 年：

| 每日出库包数 | 上述数据三年累计 | 尚未包括 |
| ---: | ---: | --- |
| 1,000 | 约 3.1～8.4GiB | 快照、原文件、导出、日志、binlog 和备份 |
| 5,000 | 约 15.7～41.8GiB | 同上 |
| 10,000 | 约 31.3～83.5GiB | 同上 |

3～8KiB 不是现有系统实测值，不能用于采购承诺。这里说明的是：每天作业量会显著影响三年容量，即便 sku.txt 一直不到 1MB。若每天保存一版 12,639 行的完整库存，三年还会产生约 **13,839,705 条快照关联行**。应保留可追溯性，同时定义在线热数据、不可变归档和被在途订单引用版本的不同保留规则。

不建议在尚无性能证据时引入复杂分库分表；先按真实日量和实测行大小建立容量表、空间告警和恢复演练，再决定归档与扩容时间。

## 9. 数据库与接口落地前的共同检查

### 9.1 必须落到真实引擎的规则

| 规则 | 云端 | PDA | 必须避免 |
| --- | --- | --- | --- |
| 一个活动作业设备 | MySQL 订单活动标记唯一 + 原子领取 | 本机固定授权上下文 | 用长数据库事务维持离线锁 |
| 一个有效出库结果 | 提交终态唯一 + 包活动占用唯一 | guard + 有效扫码约束 | 仅查询后插入、没有数据库兜底 |
| 每包逐次确认 | 复核稳定 capture/扫描身份 | 确认意图绑定 capture 与版本 | 把一次回车累计为下一包额度 |
| 原始来源与序号 | 来源设备复合唯一 | 按 F01 修正复合唯一 | 换机后改写原设备或重编号 |
| 撤销后重扫 | 原出库事实不硬删 | 仅 ACTIVE 条码唯一，旧 VOID 留存 | 永久唯一(order,barcode) 阻断合法重扫 |
| 出库周期 | 期望周期比较 + 周期唯一 | 保存所见周期及 guard | 以服务端当前周期替换旧输入周期 |
| 精确重量 | BIGINT 克，事务内求和 | Long/SQLite INTEGER | Float/Double 累加重量 |
| 摘要与幂等 | 目标绑定、重新计算、异内容拒绝 | 冻结后复用同一正文 | 仅因批次存在就返回成功 |
| 查询与导出顺序 | 明确 ORDER BY order_scan_seq | 保留跨重启高水位 | 依赖时间、UUID、上传或插入次序 |
| 同步顺序 | 已提交发布流 + 业务版本 | 应用状态和推进 cursor 原子完成 | 把自增 ID 最大值当无缺口的确认位置 |

MySQL 生成列 1/NULL 实现活动唯一、DATETIME(3) 配 UTC、BINARY(16) UUID、不使用 PostgreSQL 专用语法，这些 V2.2 的决定可以保留。迁移验收应覆盖精确 MySQL 版本和实际 SQLite 行为；不能用 H2 或内存 Map 测试替代数据库约束测试。

REPEATABLE READ 下的唯一冲突、锁等待与重试查询也应测试：失败后从完整回滚的新事务或适当当前读取得已提交结果，避免用旧一致性快照认定对方没有成功。按统一顺序锁提交/订单/包，死锁重试整个业务事务，不能留下部分库存操作。

## 11. 完整开发计划的可行性与调整建议

### 11.1 对 12～16 周估算的判断

原文明确假设后端、Android、Web 各 1 人，加 0.5～1 名测试/实施；在成员熟悉相应技术、业务及时决策、M71 及时到位的情况下，可以作为初始安排。

但恢复、临时单审批、召回换机、库存对账和后台更正主要同时依赖后端，不能因为有 3 名开发就把这些工作全部并行摊开。Android 也必须同时处理硬件、Room、队列、迁移、后台上传和真机验收，是另一条关键路径。普通管理页面不是主要工期风险。

建议 G1 后按接口、状态分支和故障用例重新估算，单列修复、联调、真机、生产共存与恢复演练工作量。没有团队实际经验和这些证据之前，不给新的精确交付日期，也不将测试视为开发完成后附送的工作。

### 11.2 保留全部功能的推进顺序

| 原里程碑 | 建议补强 | 必须具备的退出证据 |
| --- | --- | --- |
| G1，第 1～2 周 | 完成 P1 状态/身份/周期/恢复契约，提前做完整 4 包/秒验证 | 关键业务有默认或确认规则；真实输入、实体确认和必要持久事务通过技术验证 |
| G2，第 2～4 周 | 主数据/权限/订单骨架与 MySQL 约束一起完成 | 文件解析结果精确；发布失败不改有效库存；抢单和唯一约束成立 |
| G3，第 4～7 周 | Room 直接按换机来源及失败终态设计 | 离线保存、续作、重启、手输、队列失败出口及跨设备恢复可演练 |
| G4，第 6～10 周 | 将正常提交、退审、取消、关联、纠错作为同一业务链联调 | 没有永久处理中、退回后无法继续、过早释放或重复入账 |
| G5，第 8～12 周 | 报表同步实现原始/更正口径；落实身份与运维细节 | PDF/Excel 可核对；审计完整；备份包含文件与幂等凭据 |
| G6，第 12～16 周 | 进行完整性能回归、历史积累、同机共存及灾后回执对账 | 原 T01～T41 与新增场景无未解决的账务/可靠性缺陷；完成现场签收 |

上述窗口继承 V2.2，用于说明依赖，不代表本次承诺一定在 16 周内完成。这些是同一完全体的开发顺序，所有保留功能均在统一交付前完成，没有把修改作废、审计或异常恢复后置到另一期。

### 11.3 上线前还需确定的切换办法

旧系统到新系统不能只写“安装 APK 后开始用”。建议建立一次明确切换截点：

1. 盘点并收回旧设备未归档 out.txt，标识其原文件与行顺序，不伪造精确车次。
2. 对切换时仍在装车的任务决定继续旧系统完成，或经核对迁移到新订单；同一实物作业只能有一个权威采集来源。
3. 发布经核对的初始库存与出库防重基线；确认哪些旧出库已体现在上游完整文件中。
4. 新系统首批作业核对本机、云端、Excel 和实物。允许核验用的影子数据时，必须与正式库存账隔离。
5. 若需回退，先保存新系统所有已确认及未决作业证据并停新授权，再按明确台账交接，不能直接恢复旧数据库后继续发货。
