## 顺序与范围规则

1. 近期按R01 → R02 → R03 → R04推进，随后完成R05～R10。可提前准备后一步独立的资料或依赖，但不能把当前任务遗漏、静默跳过或标为完成。
2. R02建立可持续使用的测试环境，后续功能完成后继续联调；真机或异地网络发现影响扫码、保存、恢复的阻断问题，当步修复，不等到R10。
3. 每一步同时完成对应交互、必要契约、迁移、权限、错误恢复和相关验证。R03/R04建立统一使用体验，之后新功能直接遵守[设计总规范](design-system.md)、[Web规范](web-page-template.md)、[PDA规范](pda-page-template.md)和[状态语义](status-semantics.md)，不积累到最后重新改造。
4. 所需身份、同步、任务等基础能力可以随依赖任务先补齐并记录，R05核对剩余缺口；不为遵守编号人为延后必要依赖。相关性能与回归随开发执行，R10负责综合验收。
5. 用户确认的是现有完整交付范围和执行路线；不据此新增复杂主题、无依据批量操作或独立平台。PC异常处置按明确场景收尾，不无限扩展为所有后续更正/灾后功能。
6. 现场操作需要用户、设备或网络条件时，准确记录待验项，先完成可独立推进的工作；不能模拟用户操作或把等待条件写成已验证。需要调整路线时说明原因并留下记录。
7. 本路线登记本身不执行服务器变更、提交、推送或上线；后续实际执行按当时已有授权和明确目标办理，不重复索要已获得的授权。尚缺目标或必要授权时，先完成可审阅的配置、迁移及回退准备，再说明具体缺口。

## 收到“继续”时怎么衔接

1. 先阅读根目录[AGENTS.md](../AGENTS.md)、[Git管理说明](GIT_WORKFLOW.md)、本文及[最新开发进度](DEVELOPMENT_PROGRESS.md)，再读取当前步骤关联设计、交付记录和实际代码。
2. 如果本会话已有未完成工作，先续接该工作；用户仅要求查看、审查或答疑时按其当前范围处理，不自动开启业务开发。
3. 如果用户要求继续项目开发，且没有指定另一项任务，则先完成正在进行步骤的未完成事项；该步已有相应收尾证据后，从本路线选择下一项尚未完成且依赖就绪的任务。不要重新询问已确认路线，也不要重复做已完成的短码配对或PC正常流程。
4. 开始前检查分支、远端和工作区，辨认其他会话正在处理的范围。必要时只读核对任务状态，避免并行覆盖同一业务；不擅自给其他会话发指令、不自动创建新任务或改变其范围。
5. 向用户简短说明当前接续步骤、依据和本次范围后推进已授权工作；不只给出计划就结束。新的业务选择确实影响实施且无法从既有决策确定时再提出明确问题。
6. 收尾或中断前更新本文“当前接续位置”和开发进度，记录已完成子项、真实验证、失败/未测范围、下一具体动作及版本兼容边界；保留历史证据，不用新结论覆盖旧记录。提交、推送、部署分别报告实际状态。
