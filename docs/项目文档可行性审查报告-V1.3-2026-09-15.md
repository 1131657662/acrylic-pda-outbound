**一、项目理解与可行性判断**

系统拟将原有依赖 `sku.txt`、`out.txt` 和人工 Excel 整理的装车作业，改为“后台维护库存和订单—PDA 联网下载—仓库离线扫码并回车确认—联网按单上传—后台汇总导出”。一个订单代表一车，包含多个发货代码，各产品有独立计划包数。新草稿要求取消旧文档固定的 116 包上限，建议保留“实际不超过产品计划及订单计划合计”的控制。PDA 负责离线作业，服务端负责最终业务结果。

V1.3 排除了自动扣减库存、订单修改及作废、多 PDA 并发订单锁定、完整审计等能力；README 将其及本地打印纳入完整目标；新草稿进一步明确不要按一期、二期拆分功能设计。建议统一为一份覆盖全部目标的设计文档，V1.3 保留作历史资料并标注被替代的条款。完整设计仍可按模块安排开发先后，但不能把要求的能力默认为不交付。

**R00｜P1：将完整功能与取消 116 包的新要求落实为统一基线**

依据：[README 完整系统功能范围](D:/acrylic-pda-outbound/docs/README.md:189)、[V1.3 一期排除项](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:57)、[草稿取消 116 包](D:/acrylic-pda-outbound/docs/Untitled.md:17)、[草稿要求完整设计](D:/acrylic-pda-outbound/docs/Untitled.md:41)。

README 与 V1.3 的差异如下。新增草稿已经给出了完整功能设计的方向，因此后续修订应补齐这些能力，不能沿用 V1.3 的排除项。它们不仅是界面开关，还会改变数据一致性及故障处理。

| 能力 | README | V1.3 一期 | 完整目标还需要明确的设计 |

| 上传后扣库存 | 支持，可配置开启 | 排除 | 哪套数据是库存权威；扣减与提交是否原子、重试是否重复扣减；后续全量导入如何避免恢复已扣库存；切换开关的历史口径。 |

固定 116 包限制则在 README 与 V1.3 中都存在，新草稿要求取消。应同步修订建单校验、产品计划范围、订单累计校验、数据约束、错误提示、报表示例和验收工作负载。取消固定业务上限不等于取消计划校验，也不等于系统能够处理无限大的订单；应依据现场最大正常作业规模确定容量目标和技术保护边界，避免把 116 换成另一个未经调查的业务上限。

README 还把“办公室不能实时查看装车情况”列为痛点，但新方案仍需回到有网区域上传。后台只能及时显示已上传的数据；若业务要求装车过程中实时看进度，需要改变联网或传输前提，不能仅增加后台页面。[依据：README 老系统痛点](D:/acrylic-pda-outbound/docs/README.md:43)

建议产出完整功能覆盖表及旧新规则变更表，逐项对应状态、数据、接口和验收。本文后续引用 V1.3 是为了说明现有方案的缺口；其中的“不扣库存”“禁止作废”等旧约束不作为新完整目标的推荐范围。

**R01｜P1：上传幂等需要覆盖整个业务提交周期**

依据：[§7.6 上传幂等设计](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:492)、[§8.1 上传批次](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:599)、[§18.4 上传重试](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:1116)。

原文要求“每次上传生成唯一 batch_id”，同时规定已完成订单收到不同 batch_id 要返回冲突。这会产生确定的协议歧义：服务端提交成功但响应丢失，PDA 重试若生成新批次，便会收到冲突，无法按现有规则将本地订单确认为已上传。

此外，“同一 batch_id 直接返回成功”没有区分该批次是否真正完成、内容是否相同。批次表又允许 FAILED 状态，因此只凭批次号存在不能判定业务成功。

建议文档明确：

1. 一个订单的一次最终提交生成并持久化一个批次号及不可变明细快照；断网、重启、自动和手动重试全部复用。
2. 批次绑定订单、设备、提交身份及内容摘要。同批次同内容返回原有成功回执；不同内容或不同绑定对象返回明确冲突。
3. 只有已经成功提交的批次才能返回成功。处理中、失败及结果未知的处理方式分别定义。
4. 服务端以一个原子业务事务完成明细写入、汇总更新、订单完成和成功批次记录；启用扣库存时，同次库存变化及必要业务凭据也须保证原子一致。并发请求不能各自通过检查后都完成订单或重复扣减。
5. 提供可查询的提交结果或等价对账机制；本地核对批次、包数和重量后才转为已上传并允许清理。

服务端事务内的并发保护，与一期排除的“离线多 PDA 抢单锁定”是不同问题；前者仍是上传正确性的必要条件。

**R02｜P1：跨订单与跨设备的重复出库边界没有成立**

依据：[§1.2 排除项](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:57)、[§8.1 明细唯一规则](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:582)、[§10 统一校验规则](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:727)。

V1.3 的唯一规则是“订单号 + 条码”，跨订单校验仅建议覆盖“本机未上传订单”。按其不扣库存的一期方案，订单 A 上传后条码仍在库存快照中；随后订单 B 再扫该码，不在当前订单内重复，也不占用其他未上传订单。即使只用一台 PDA，现有规则仍可能允许重复记录。若启用 README 的扣库存功能，旧离线快照仍须处理，不能仅依赖云端扣减防重。

两台设备离线共享同一批可扫库存时，即使各自领取不同订单，也不能知道对方刚扫了哪个包。仅增加订单归属或云端上传查重，不能保证现场不发生重复装车；云端只能在联网后发现冲突。

README 已明确“一包一唯一条码”，可作为基本业务事实；还需明确是否复用、是否存在退货后再次出库及相应生命周期。[依据：README 业务对象](D:/acrylic-pda-outbound/docs/README.md:5) 建议据此确定以下边界：

1. 若一包只允许出库一次，需要独立的已出库或已占用事实及相应的服务端约束；这不要求自动扣减上游库存数量。
2. 本地查重范围应包含适用期间的已上传记录。清理展示明细时，应保留仍有业务作用的查重凭据；不能让清理操作重新开放已出库条码。
3. 完整目标要求多 PDA 作业，需要在联网时确定订单归属，并定义离线期间的归属有效性和换机交接；服务器锁过期不能证明旧设备已停止扫码。
4. 多台离线共享库存时，还需选择事先互斥的条码/库存分配，或明确接受上传后冲突并补充现场处理流程。仅按订单分配不够；限制同一库存范围内单台活动设备只能作为临时现场控制，不能代替完整目标。

**R03｜P1：库存快照必须具有明确的发布与使用边界**

依据：[§6.1 库存导入](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:191)、[§7.1 同步与版本](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:299)、[§9.2 库存接口](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:640)。

README 已说明上游交付完整全量 `sku.txt`，且旧系统以覆盖文件方式导入；这一输入事实无需重复等待确认。[依据：README 库存维护](D:/acrylic-pda-outbound/docs/README.md:24) 但新系统仍未说明全量文件如何替换或合并云端有效库存、删除如何传播、版本何时发布、失败行如何影响可用库存、分页下载如何锁定同一版本。单纯记录同步时间或导入批次，不能解决这些问题。

例如 PDA 用 V1 扫到重量 303kg，后台随后导入 V2 将该包改为 302.5kg，上传时到底使用哪份重量没有规则。又如全量库存解析失败却直接发布成功行，可能把原本存在的条码从有效库存中删除。

建议定义“解析暂存—结果检查—发布固定版本—PDA 下载暂存—完整性验证—原子启用”的生命周期。解析可收集错误并继续，不等于可以自动发布不完整库存。

应补齐全量/增量策略、版本标识、条数或校验摘要、分页游标、删除标记、历史版本保留以及中断后保留上一完整版本的规则。订单开始作业时绑定库存版本，保存和上传都按这份版本解释；版本有更正或失效时，明确定义冲突处理。

订单刷新也应保护本地未上传明细、进度和批次。下载确认应在订单完整落地后发送，并可重复确认、恢复已领取未完成订单；只列出 `status=NEW` 不足以描述重装或下载确认丢失后的恢复路径。

离线设备无法知道服务端是否刚发布新版本。“库存过旧”必须依据预先约定的有效期或作业政策判断，并区分“从未同步”“版本不完整”“超过允许离线时长”。

**R04｜P1：本地可独立校验，服务端仍须负责最终复核**

依据：[§3 权限](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:113)、[§9.5 上传请求](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:668)、[§10 第 1 条](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:729)。

文档写“所有业务校验在 PDA 本地执行”，未明确服务端独立复核。上传体同时包含车号、柜号、操作员、设备号、分产品明细和重量。如果这些值直接成为最终账据，客户端数据损坏、旧版本逻辑或越权调用都会绕开现场校验。

建议补充权威来源：订单基本信息与计划以服务端订单为准；条码、产品与重量以已确认的库存快照为准；上传身份由认证会话确定，历史扫码操作员按可验证的作业身份保存；设备标识不能仅凭任意字符串认定已获授权。

服务端还需校验 URL 与请求体订单一致、操作者及领取设备对该订单有权限、订单版本仍允许提交且未作废、明细属于订单、条码格式与库存版本合法、请求内重复、适用范围内历史重复、各产品及订单计划上限、订单状态和批次绑定。库存快照曾包含某包，不代表该包当前仍可重复出库。包数、重量应由验证后的明细重新计算。

“订单详情、明细、导出允许范围”需明确到业务对象。列表、详情、同步和导出应使用一致的数据权限；仅在前端隐藏按钮不足以构成权限控制。

**R05｜P1：必须定义从输入到落库的完整事件规则**

依据：[§7.3 操作与校验](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:368)、[§17.3.2 回车示例](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:953)、[§18.2 双通道示例](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:1074)。

示例使用一个 `isValidated` 标记决定是否保存，但文档没有要求它绑定条码、订单及库存版本，也未规定输入修改后的失效规则。按示例缺失的约束实现，可能出现：A 校验通过后输入被改成 B；A 的异步校验结果在 B 到达后才返回；保存 A 尚未结束时输入框被 B 覆盖；长按回车引发多次保存。

“输入框 + 广播”还有两个独立事件源。`isFromBroadcast` 只包围本次程序设置文本，不能阻止稍后到达的硬件键盘注入继续改变输入框内容；仅避免重复校验不足以消除双通道风险。

建议在文档中定义等待输入、校验中、待确认、保存中、保存成功/失败等状态及合法事件。任何条码、订单或版本变化都使先前校验失效；旧异步结果不得应用到新输入。保存针对已经验证的不可变记录，并在本地事务中复核重复和数量上限。

当前条码未确认时再来新条码，必须明确选择排队或拒绝并提示，禁止静默覆盖；队列也需要容量和逐条确认规则。回车连按、删除与保存并发、切单、退出和应用进入后台均应有定义。

建议优先验证设备是否支持仅广播接收，手动输入由应用输入框独立承担。若必须双通道，先验证真实事件时序和去重方案。只有数据库事务提交成功后才播放“保存成功”音；识别或校验通过音不能代表该包已经记账。

**R06｜P1：订单完成与纠错路径需要业务闭环**

依据：[§5 本地状态](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:175)、[§7.3 删除与锁止](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:429)、[§7.4 98/116 示例](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:438)、[§16 短装问题](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:850)。

“待扫码→待上传”没有明确触发动作；汇总示例在 98/116 时显示上传入口，而短装是否允许仍列为待确认。由于成功上传会完成并锁定整单，不能把第一次上传同时解释为“阶段性保存”与“最终结单”。

README 已明确单次出库最少 1 包，因此正常出库结单应阻止零包；不足订单计划、某产品完全未扫及扫满时的结单条件仍需明确。建议使用明确的最终提交动作：若允许短装，需定义批准权限、差额展示与差异记录。完整目标已包含异常备注，但还需说明备注与异常放行权限的关系。

上传前删除错误条码，必须同步回退包数、重量、占用及满额锁止状态。批次冻结后、上传进行中或提交结果未知时，不允许修改同一批次内容。只有服务端明确未接受且处理规则允许，才能退回编辑；超时不等于未接受。

按 V1.3，订单作废和修改均被排除，因此错误车号、误建订单、车辆更换、任务取消没有正常关闭路径。完整目标需要补齐受限状态下的修改与作废流程，明确新旧版本及本地未上传记录的处理；不能仅以“重新建单”留下原单继续可扫，也不能承诺后台作废能立即停止完全离线设备。

**R07｜P1：主数据格式及产品识别规则应先于开发定稿**

依据：[§6.1 解析建议](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:201)、[§6.2 发货代码映射](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:244)、[§8.1 重量字段](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:524)、[§16 待确认项](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:842)。

通过 11 位条码可以定位条码及其后重量，但当条码前型号与品名之间没有稳定分隔符时，不能仅靠条码正则可靠区分两者。现有例子不足以证明所有历史文件可解析。

应向上游确认文件编码、分隔符或固定宽度、列顺序、表头、空行、字段内空格、重复行、重复条码及异常字符的规则；整理正常与异常样本及人工确认的解析结果。不要依赖未声明的猜测规则静默导入。

条码需要明确长度、字符集、大小写及空白处理。“去空格”应区分修剪首尾和删除内部空白，避免把本应无效的两个值归一化为同一条码。是否允许条码复用要与 R02 一并决定。

若同一发货代码对应多个型号或品名，单靠前三位不能完成唯一匹配。建议默认遇到此类冲突时阻止相关产品映射发布或建单，先由上游治理；若业务必须支持多映射，需要改动匹配规则及订单模型，不能只增加一个选择框。

重量应明确单位、有效范围、允许小数位、舍入时机和展示规则。服务端定点小数、PDA 精确小数或约定最小单位整数应保持同一口径；SQLite 不能仅靠声明 DECIMAL 类型就假定与服务端相同的固定精度语义。JSON 传输格式也应明确。文档中 `decimal(10,2)` 与“精度待确认”应收敛为一个已决定规则。

**R08｜P1：WAL 是日志机制，不能独立证明突然断电不丢记录**

依据：[§11 可靠性](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:742)、[§13.3 断电验收](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:801)、[§17.3.3 WAL 示例](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:973)。

SQLite 官方明确说明：WAL 配合 `synchronous=NORMAL` 时，已经提交的事务仍可能在掉电或系统崩溃后回滚；应用进程崩溃与设备突然失电不是同一耐久性等级。因此，仅声明“必须开启 WAL”不足以支撑现有承诺。本次没有检查真实设备的数据库参数，不能断言设备正在采用何种同步级别。

建议把“已保存”的边界明确为满足规定耐久性要求的事务提交完成，并验证实际 Room/SQLite 配置、磁盘同步策略与设备表现。若目标是突然断电后仍保留每条已确认记录，应评估适当同步配置，并同时测量性能成本。

验收分别覆盖页面退出、应用进程被杀、系统重启和突然掉电；以操作员已经收到保存成功反馈的记录集合为核对依据。备份或导出本地数据库时也需采用能保持 WAL 一致性的方式，不能假设复制单个数据库文件就得到完整数据。

官方依据：[SQLite PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。

**R09｜P2：时间校准需区分设备系统时间与应用业务时间**

依据：[§18.5 时间同步](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:1129)。

原文要求通过服务器时间接口“校准本地时间，保证 scan_time 可靠”。若这里指修改 Android 系统时钟，普通第三方应用不能直接凭一个时间接口完成：Android 将直接设置系统时间的权限列为非第三方应用使用权限。若厂家提供特权能力，应另行取得设备及部署条件的证明。

建议默认采用应用业务时间校正，记录服务器时间与设备时间的偏差、最近校正时刻和时间质量；同时保留原始设备时间、服务端接收时间以及稳定的本地记录顺序。长时间离线、人工改时、跨时区和设备重启后的处理要明确。不能把联网后推算的时间直接表述为精确可信的历史发生时间。

作业开始、结束应定义为明确业务动作，例如首条成功保存与确认结单，或明确的开始/结束操作，并约定删除首末条记录后的口径。接口采用带时区或明确时区约定的时间格式。

官方依据：[Android Manifest.permission.SET_TIME](https://developer.android.com/reference/android/Manifest.permission#SET_TIME)，其中明确标注 “Not for use by third-party applications”。

依据：[§8 数据模型](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:509)、[§9 接口建议](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:630)。

**R11｜P2：取消固定上限后需重新定义容量与真机验收负载**

依据：[§13.2 性能验收](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:793)、[§17.1 设备参数](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:866)、[§17.4 真机清单](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:1015)、[§18.4 重试示例](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:1116)。

每秒 2 条持续 5 分钟为 600 条，每秒 3 条为 900 条。旧 116 包规则下只能跨单完成这些负载，新草稿取消该固定上限后则应根据真实单订单规模确定单单或跨单压测。需要区分扫码保存链路、跨订单连续作业及实际装车效率，明确切单时间是否计入。扫码还需要人工按回车，系统响应速度不能直接当成整个人工作业吞吐。

旧文档的单订单上传 1,000 条与旧 116 包限制不一致；取消上限后，1,000 条可以作为候选测试样本，但不能直接断言它就是典型或最大负载。应补充单订单计划上限的实际分布、最大期望明细数、上传包体及处理时限；如需分块传输，应仍确保订单最终提交的完整性和幂等。列表测试也要说明是当前订单还是跨订单历史。

“校验到保存小于 300ms”包含用户等待回车的时间，不能作为纯系统指标。建议分别定义收到完整条码至校验结果、回车至耐久保存成功的耗时，注明统计分位、最大允许值及测量方法；WiFi 上传需给出网络与服务端环境。

库存数据总量和文件体积应先确认，内存峰值需说明统计口径与工作负载。必须在完整同步、连续扫码及历史积累后分别验证，不能由 16GB 标称容量推断导入过程、临时文件和本地存储一定充足。

实际 M71 的 CPU、扫描头、固件、屏幕密度、可用空间及广播数据类型需要逐台型或批次确认。“4核/8核”“E3250/E3200”仍是多个可能配置；厂家标称续航不能替代班次实测。数字键盘如何输入示例中的字母 C，也应纳入手工补录验收。

320×533dp 还要扣除系统栏、应用栏及软键盘。顶部五行、输入及校验、状态提示、最近 5～8 条和底部操作同时展示，存在空间压力；须用真实可用高度核对可滚动区域与固定操作区。48dp 按钮只是尺寸要求，普通手套是否能触发电容屏需实测。

WorkManager 的退避配置本身不等于自动恢复上传方案，还需定义网络条件、唯一任务、防止手动与自动重复排队、可重试与永久失败分类、认证失败处理及用户可见状态。设备支持 4G，若产品明确只允许 WiFi，应专门表达该限制；无计费网络与 WiFi 并非严格同义。后台任务受系统调度影响，不宜承诺恢复 WiFi 后立刻执行。

官方依据：[Android WorkManager 工作约束、重试与调度说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)。

**R12｜P2：导出业务与后端技术选型应一起收敛**

依据：[§6.2 建单即生成 PDF](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:250)、[§6.5 实际出库明细导出](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:285)、[§14 部署建议](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:811)。

建单时尚无实际扫码数据，应区分计划装车单与上传后的实际装车明细，并约定短装时计划/实际差额、数据截点、模板版本及导出权限。需给出真实模板及中文字体、纸张、分页、签字栏、重量精度和 Excel 条码文本格式等验收样例。PDF 生成失败不能让“订单是否创建成功”变得不确定，应有可重试的文件生成状态。

部署部分尚未选择后端语言及框架，却列举了主要属于 Java 生态的 PDF/Excel 库。这不构成技术不可行，但不能视为完整选型。建议结合团队经验确定后端、数据库和导出方案，并对具体版本的维护状态、许可证及中文字体分发条件做核对。当前资料不足以判断这些依赖的最终成本。

**R13｜P2：需要明确离线身份、设备交接和最低恢复能力**

依据：[§3 离线用户缓存](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:121)、[§7.7 本地清理](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:499)、[§13.3 可靠性验收](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:801)、[§14 部署建议](D:/acrylic-pda-outbound/docs/腈纶包仓储离线PDA扫码出库系统.md:811)。

需定义允许离线作业时长、换人登录、账号在离线期间被禁用及回网令牌过期的行为。重新认证不得删除待上传记录，也不能把历史扫码人默默改成当前上传人；管理员代传或设备交接若允许，需要记录实际提交身份。

未上传数据若只有 PDA 内的一份副本，设备丢失或存储损坏无法靠 SQLite 保证恢复。应明确承诺仅覆盖何种故障，确定可接受的数据损失窗口、班次交接同步要求和故障设备的人工恢复流程。此处不是要求一期实现完整灾备系统，而是使现场知道什么情况下仍有可恢复副本。

部署及维护文档至少应覆盖云端备份与恢复验证、本地清理条件、APK 签名与升级分发、数据库版本升级保留待上传数据、剩余空间不足时的阻止写入和明确提示，以及人工冲突处置入口。

完整目标已要求操作审计，应覆盖订单创建、修改、作废及归属，库存导入发布及扣减，提交批次，异常处理，以及扫码记录删除的操作者、时间和前后值。离线事件如何补传、重复补传如何去重、查询权限及保留期限需要形成完整契约，不能只以后台接口日志替代。
