# PDA APP 界面与作业体验优化分析

日期：2026-09-29。范围：USB 真机页面结构观察、主树 Android 源码核对，以及[断网补救与独立运行报告](PDA_OFFLINE_CONTINUITY_ANALYSIS_2026-09-29.md)涉及的新界面设计。本文是分析与布局建议，未实现业务功能、替换 APK 或开放生产能力。版本信息统一见[看板事实块](ORCHESTRATION_STATUS.md)。

> 2026-10-11计划纳入：本文阶段A–D、P0/P1/P2、目标设备首屏约束与第7节场景已映射到[十步路线](DEVELOPMENT_ROADMAP.md)、[剩余计划O/U子项](REMAINING_DEVELOPMENT_PLAN.md)及[总目标](AUTONOMOUS_DEVELOPMENT_GOAL_2026-10-07.md)，详见[纳入记录](history/PDA_OFFLINE_UI_PLAN_2026-10-11.md)。下文观察/预览/交接写权是分析时点记录，后续状态读看板；不计交互验收或自动唤醒旧任务。故障处理按[R07撤回重发政策](BUSINESS_POLICY_R07.md)，PC中转仍属原设备事实链。

## 1. 结论与建议顺序

**值得进行一次围绕现场作业的界面整理。最突出的问题是重要信息出现太晚、不同性质的状态混在一起、普通操作与维护操作争抢位置。单纯换颜色和圆角解决不了这些问题。**

建议保留现有青绿色识别色和已建立的安全约束，调整为“作业／数据／我的”三个主入口；进入扫码后使用专注作业页。第一阶段先整理现有首页、扫码页、结单页，再把应急导出和独立导入接入同一套信息结构，不要继续在首页末尾叠加按钮。无需为了本次优化重写整个 Android 技术框架。

三条必须讲清的主线：

- **做什么：**继续当前车辆扫码、核对结单、处理待办。
- **数据在哪里：**待保存、本机已保存、服务器已接收、最终确认；这些不能用一个“完成”替代。
- **异常怎么走：**查询原提交、重试原批次、导出本机事实；导出成功不代表出库完成。

优先级含义：P0 为新增断网功能前必须澄清的交互语义；P1 为高频作业效率与误触问题；P2 为视觉一致性及辅助体验，不代表已发现对应等级的安全漏洞。

## 2. 本次实际看到了什么

### 2.1 真机观察与边界

通过 USB 连接 Mobydata M71，系统为 Android 9，屏幕 480×800 px、密度 240，约等于 320×533 dp；后者还未扣除系统栏。字体缩放为 1.0。观察了已安装测试渠道应用的本机任务、历史完成、设备设置及应用更新页。

进一步读取到的设备约束是：MT8768 平台、4 个在线 CPU 核、约 1.9 GB 总内存、约 1 GB 可用内存（读取时点）、约 1 GB swap；屏幕刷新模式约 58.21 Hz。应用进程读取时约占 66 MB PSS，包含 92 个 View；这是现场读取快照，不是压力上限或长期平均值。状态栏占约 36 px，因此首页真正的应用内容高度约 764 px，即约 320×509 dp；底部系统栏、横屏或设备厂商设置仍需现场复核。布局预览按 320 dp 宽度设计，但不能替代在这台设备上的 APK 回归。

设备安装的是测试渠道包，不能把不同渠道的版本号大小直接视为“最新正式版”。本地存在更新日期不同的 debug、release、staging APK；本地 staging 元信息与设备观察一致，但没有提取已安装 APK 做逐字节比对。**本报告分别标注“USB 实见”和“源码核对”，不声称验证了最新生产部署。**

历史页中可见一项已完成测试订单，其进入动作要求原操作员；本次遵守该限制，没有进入该订单。扫码、结单、临时草稿与明细页的结论来自源码，并非本次真机操作这些业务页面的结果。

App 截图输出为空文件；同一设备的桌面截图正常，且首页源码设置了 `FLAG_SECURE`，结果与截屏保护相符。未解除该保护。页面位置来自 UIAutomator 控件树，不能代替真实位图对字重、颜色观感、遮挡和动态反馈的判断。附带布局预览是提案和示例数据，不是设备截图。

未扫描、领单、冻结、上传、取消、注销、改配置、检查下载或安装更新；结束后返回系统桌面。启动 App 可能触发其已有后台同步，因此不承诺 App 在本次观察期间没有自行联网或写入本机状态。

### 2.2 设备性能与连续扫码的限制

源码中的 `ScannerReceiver` 收到广播后将原始字符串交给 `WorkEngine`；作业引擎使用容量为 64 的队列和单线程执行器，`WorkReception`、校验、Room 事务保存及发布状态按顺序处理。队列满时会停止接收并提示“入口已满”，因此界面不能鼓励操作员无限快扫或把“已收到广播”当成“已保存”。每次保存都会更新扫码事实、产品汇总、整单汇总和事件序号；这一致性优先于盲目提高并发。

这带来四项具体 UI 约束：

1. 扫码页只能有一个持续作业主区域，主计数显示“本机有效已保存”，而不是模糊的“扫描数”；短暂的待处理／待落盘值只有非零或阻断时才突出。
2. 保存反馈必须可见且稳定，声音只能作为辅助。队列积压时显示“正在处理第 N 条，暂缓继续扫码”，并保留最近成功记录；错误时明确“本条是否保存”。
3. 不在每次扫码后刷新整页或创建大量控件。保留有限的最近记录窗口，产品明细进入分页详情；避免动画、阴影、图片和网络请求参与扫码闭环。
4. 扫码枪扳机和现有 F1／F2／Enter 语义不能因视觉改版改变。确认按钮仍按候选状态出现；在确认期间不把返回、撤销、停止放在连续扫码主命中区旁边。

本次读取到 `dumpsys gfxinfo` 的现有统计为 269 帧、18 个卡顿帧（6.69%），但统计起点和操作集合不可控，不能据此判定 App 已有性能故障。没有执行连续扫码、队列 64 边界、前后台切换、低存储、声音未就绪或设备温度下的压测；应在目标设备用真实扫码枪记录 P50／P95 单条保存延迟、最大无错误连续速率、队列峰值、丢弃／重复数和 30 分钟稳定性。

### 2.3 最有代表性的实测：首页先展示维护事项，后展示任务

| USB 观察项 | 屏幕纵向位置（px） | 对操作员的影响 |
|---|---:|---|
| 检查应用更新 | 132–204 | 低频维护占据首页核心位置 |
| 通用“操作已完成；资料和本机记录已保留” | 204–273 | 不清楚完成的是刷新、保存还是出库 |
| 本机任务／历史完成／待领取与刷新 | 273–345 | 导航之后仍未看到订单 |
| 领取异常与拒绝记录 | 345–417 | 无论是否有待办，均占整行 |
| 身份、仓库、设备信息 | 417–489 | 日常无需反复阅读的信息持续占位 |
| 第一项订单或空态标题 | 从 525 开始 | 约在整屏高度的 66% 处才出现工作内容 |

历史订单操作按钮从约 735 px 处开始，需要继续滚动。这里证明的是首屏优先级问题，不把正常滚动认定为控件裁切缺陷。

设置页初始可见范围被返回、重新读取信息、环境、身份和同步说明占据，“检查后台连接”接近首屏下缘；更新页出现“本机更新记录暂不可用，请重新检查更新”，但没有足够直接的下一步解释。环境未配置与登记／会话信息并存，界面应区分“构建环境配置”和“本次后台可达性”，不能仅凭这些文字断定服务器异常。

### 2.4 对多页面布局提案的设备适配复核

这组提案按 320dp 等比例预览后，9 个页面均没有横向溢出；扫码工作台的候选确认按钮、已保存数量和扫码记录入口在约 509dp 可见高度内可以同时出现，方向正确。这个结果只说明静态提案的宽度和主扫码动作基本合适。

目前不能判定“整组页面已经符合 M71 首屏要求”，原因如下：

- 提案页面的自然高度约为 540–600 CSS px，而设备应用区约为 509dp。首页、本机任务、待领取和设置页的底部导航会落到可见区之外；扫码记录的导出按钮已前移到首屏，较早记录仍可继续滚动查看。
- 初版数据保全页的“生成应急包并校验”接近或超过首屏底部，`导入 sku.txt` 明显在首屏以下；本轮已把主导出按钮和资料预检的主启用按钮前移到约 509dp 可见区内，次级导入入口仍需滚动。断网时最重要的导出动作不应依赖操作员猜测页面可以滚动。
- 提案中的“扫码队列空闲”和“待确认输入”已修正为“扫码队列空闲 · 1 条待确认输入”。实际实现必须把队列积压、待确认候选和本机已保存三个状态分别呈现，不能复用一个“待处理”数字。
- 顶部页面选择器是本次预览的浏览器辅助控件，不是 PDA 业务界面；不能把它的可达性当成 App 的导航验收。PDA 内部仍须用真实返回、主导航和页面滚动完成同样路径。

因此阶段 A 的新增验收条件应是：以 M71 的应用可见区为裁剪框，扫码页在不滚动时保留车号／来源、已保存计数、候选确认、最近保存反馈和异常入口；数据保全页在不滚动时至少保留当前订单、只读说明和“生成应急包并校验”；其他次要说明可以滚动查看。当前提案已经满足扫码页和数据保全主动作的静态位置条件，但首页、本机任务、待领取和设置页的底部导航仍落在约 509dp 之外，必须在 Android 实机上决定是进一步压缩首页，还是采用明确的页面滚动／顶部返回，不可直接照搬实现。

## 4. 建议的信息结构

| 主入口 | 首要内容 | 次级入口 |
|---|---|---|
| **作业** | 当前车辆／本机未结束作业，按真实状态继续或处理 | 待领取、历史、领取异常；有权限且资料有效时创建临时作业；未来独立采集 |
| **数据** | 待同步事项与数据保全；每项关联到原订单 | 已有临时资料、未来签名资料包／sku 文件管理、导出历史和复制核验 |
| **我的** | 操作员、仓库、设备简要信息与声音设置 | 连接诊断、应用更新、详细环境；受控退出及高级维护 |

首页不必增加大面积统计面板。推荐“当前任务优先”的首页；多车切换频繁的岗位可选紧凑任务列表，仍须保留同一来源、状态与操作语义。扫码时隐藏全局底部导航，避免手持或连续扫描时误切页；提供明确返回，返回本身不冻结、不结束作业。

正式单、临时单、独立采集是**来源**，不应做成可以改变已有作业性质的“在线／离线”开关。网络断开时，同一正式单仍是原正式单；不能换模式消除原批次、身份、时限或重复占用限制。

### 4.1 首页首屏构成

1. “作业”标题＋精简仓库／操作员；详细设备标识放“我的”。
2. 只有需要行动时才显示一条摘要，例如“1 单待确认，可查询原提交”；网络不可达另有简短状态，不用红色整屏警告制造误解。
3. 当前任务：车号、正式／临时／独立来源、有效已扫／计划、当前业务状态、一个主要动作。
4. 其余任务或待领取入口；底部三个主导航。更新提示放“我的”，强制更新等既有阻断仍按实际政策保留。

### 4.2 扫码首屏构成

顶部：返回、车号、来源；其后明确“未确认出库／不可放行”等必要状态。中间突出本机有效包数、计划和剩余，重量为次级信息。再显示最近一条的产品、包号和保存结果，较早记录进入明细。底部集中候选确认或手输操作，以及“核对结单”入口。

普通连续扫描应让操作员迅速回答四件事：扫的是哪辆车、本次有没有保存、还差多少、异常接下来怎么办。手输时键盘不得遮住待确认内容与确认键；保留必要的车号和保存结果，减少非必要列表。

### 4.3 结单页按状态引导

| 已知事实 | 主要说明 | 主动作 | 可用次动作 |
|---|---|---|---|
| 扫码未结束 | 有效包数、差异、待处理输入 | 符合条件时核对后结单冻结 | 返回扫码；未来只读导出 |
| 已冻结、尚未提交 | 原批次已保留，不能续扫 | 上传原批次 | 查看明细；未来导出 |
| 请求已发出但结果未知 | 服务器是否处理尚未确定 | 查询原提交结果 | 满足原机制时重试原批次；未来导出 |
| 收到明确拒绝／待核对 | 已知原因与下一步，仍保留原事实 | 进入对应核对或处置入口 | 导出、查看原回执 |
| 收到最终有效确认 | 展示确认结果与回执时间 | 查看回执／返回作业 | 查看明细、导出核对资料 |

“服务器收到文件”“导出文件成功”和“管理员已看过”均不得显示成最终确认出库。是否可放行仍按有效业务回执与既有政策判定。

### 4.4 结单前调整已扫码包

“核对并撤销末包”继续保留，用于刚刚发现的最后一包误扫或未装车。它不应承担任意旧包调整；扫码页只显示最近少量记录，明细页也不能直接物理删除历史行。

新增入口命名为“调整已扫码包”，放在订单明细和扫码页的次级操作区。操作员进入后看到固定提示“调整模式，不会新增扫码”，再用实体扫描键扫描需要取消的包；PDA 显示原扫码序号、条码、产品、重量和当前状态，确认“未装车／本车不装”并填写原因后才提交本地调整。条码损坏时，按扫码序号、条码或产品筛选列表作为备用路径。

- 调整模式只接受已有有效包的定位，不走普通扫码的重复条码错误流程，也不产生新扫码序号。
- 每次确认后立即显示“已撤销，未计入有效装车”，并刷新整单、产品数量和重量；原扫码行仍在明细和导出中，序号不重排。
- 入口只在订单仍为 `SCANNING`、队列和待确认输入归零时可用。已冻结、上传结果未知、召回或主管保留明细时显示阻断原因，不提供修改按钮。
- 如果包已经实际装车，需要卸下或隔离，界面引导到主管批准的实物处置流程，不允许用普通撤销掩盖实物变化。
- 结单页根据调整后的有效数显示各产品差额；存在短装时要求填写短装原因，并显示“提交后需主管审核”。

调整过程不使用“删除扫码记录”“修改总数量”等文案。这样能让操作员知道实际减少的是本车有效装车集合，同时保留后续恢复、导出和审计所需的原始事实。

## 5. 新增断网场景如何融入 UI

### 5.1 本机应急导出：最先建设的补救入口

入口建议同时出现在“数据 → 数据保全”和订单详情。普通导出是读取某一时刻本机事实，不强迫结单、停止或清除异常；未冻结、待确认、已成功等状态均应有明确处理。

流程：**选原订单 → 核对导出范围和时点 → 生成并校验应急包 → 保存到可用目标 → 复制到电脑并核验。**

- 核对页分开列“有效扫码、已撤销、未决输入”，显示是否包含原冻结批次及已有回执；未冻结就写“无冻结批次”，不补造。
- 默认保留供恢复使用的机器原件，同时提供可用于 Excel 导入的 CSV／TSV 及交接说明。前导零和长条码的导入方式明确提示；人工编辑后的表格不能替代恢复原件。
- UI 分别记录“应急包已生成”“目标文件已写入并校验”“已在电脑核验副本”。设备无法证实电脑副本时显示“待核验”；人工确认只能标为人工确认，不能伪装机器校验。
- 空间不足、取消选择、介质拔出、写入失败时保持原记录，并允许重新生成／重试保存；失败不显示完成。
- 文件导出成功仍提示“本机原件保留，订单确认状态未改变”。“停止并保全”继续使用独立、明确的状态操作。

PDA 网络模块损坏时，Wi-Fi 分享不能成为唯一按钮。目标路径和 USB／MTP／适用时 OTG 要在实际硬件验证后才承诺可用。本次 USB 调试可读页面，不等于这些业务文件交接通道已经验收。

**离线登录失效时，救援入口不能被联网登录完全挡住，也不能因此无身份开放全部数据。**需为只读救援设计受控本地身份校验与范围；是否允许跨操作员取出仍按待定业务政策处理。UI 可先保留清晰入口和原因说明，不绕过既有身份门。

### 5.2 sku.txt 独立导入：新的作业来源

推荐流程：**数据 → 导入资料 → 选择 sku.txt → 预检 → 固定资料快照 → 新建独立采集 → 扫码 → 导出／待对账。**

预检页需列出文件名、资料来源、可解析条目、重复／冲突／错误条目、首批产品样例及范围。对无法确定的编码、字段或有效期不要默默猜测；错误可定位，失败导入不覆盖已启用资料。启用前明确“只能核对本机资料，不能证明服务器实时库存和跨机唯一占用”。

新建页使用常驻标签填写车号、作业说明、产品及计划；产品以代码、型号、名称可检索。显示绑定资料快照，开始后不得通过换文件悄悄改变旧单依据。扫描页持续展示“独立采集／待对账”，结尾使用“结束采集并导出”等符合其真实能力的词，不能显示“确认出库”。

本机正式／临时／独立任务须共用必要的防重与未决核对；发现某包已在未确认原单内时，应引导核对原单，不能靠新建独立单绕开。多台完全离线 PDA 的冲突仍需事后处理，UI 不承诺全局无重复。独立身份、长期离线或跨重启资格的政策尚需明确，布局提案不代表这些权限已获授权。

### 5.3 服务器恢复后：保留来源与责任链

“待同步”逐单显示已知结果和可用动作；正式已冻结单查询／补传原批次。电脑中转应急原件要显示接收、核验、业务处理分别处在哪一步。未冻结快照和独立采集进入核对流程，不因文件接收成功自动变成正式提交。与正式单关联时展示双方差异、原来源及经办结果，继续遵循已定人工确认边界。

## 6. 统一视觉、文案与硬件体验

以下尺寸是为该设备提出的设计起点，尚未通过真机可用性或无障碍验收：

| 项目 | 建议 |
|---|---|
| 主色与层次 | 延续现有青绿色；中性浅背景、清晰内容区；主按钮实色、次按钮弱化；危险操作用文字与明确色义，避免所有按钮同样突出 |
| 字体 | 正文先以 16–18sp 验证，次级约 14sp，关键计数约 28–32sp；长车号／产品名换行，不能通过持续缩小字体适配 |
| 触控 | 保留现有约 52–56dp 的主要按钮尺寸；紧凑来自移走低频内容，而非缩小命中区；紧邻的撤销、结束、停止动作应隔开 |
| 间距 | 在现有 XML 样式体系集中定义常用间距、按钮、输入、状态条；减少页内硬编码和默认样式混用 |
| 成功反馈 | 真正本机持久化后再给成功文案／声音；保留最近一条结果，不能仅依赖一闪而过的 Toast；声效失败有可见反馈 |
| 错误表达 | “发生了什么＋记录是否保留＋下一步”；不把所有网络错误都称为断网，也不把未知结果称为失败 |
| 时间 | 统一使用项目的展示时间规则，重要时间明确时区；未经可信校验的设备时间另标，不能只修改显示就声称时间已可信 |
| 无障碍 | 状态同时有文字，图标有名称；放大字体后允许重排；保持合理焦点顺序，避免每个计数变化都重复打断操作员 |
| 硬件按键 | 保持 F1 手输校验、F2 丢弃／清空、Enter 确认的现有语义；其他厂家键位仅在已验证条件下使用，不随视觉改版重映射扫码扳机 |

“已保存到本机”“等待上传”“结果未确认”“已接收、待处理”“最终确认”应使用统一术语表。正常完成刷新不再留下泛化的“操作已完成”长期横幅。错误中的技术码仍保留于详情，便于现场与研发对照。

## 7. 分阶段交付与验收标准

| 阶段 | 内容 | 可验证标准 |
|---|---|---|
| A：整理现有页面 | 首页、任务卡、扫码主次层次、结单文案、结单前已扫码包调整、临时产品误移除 | 目标设备默认字号首屏能看到当前任务和主动作；身份／状态／权限不变；无操作误指向；原键盘及扫码确认逻辑回归 |
| B：统一数据保全体验 | 数据入口、只读导出、文件状态、连接诊断 | 已领未结／已冻结／未知结果均有可解释路径；失败文件不报成功；USB 电脑副本核验与本机文件生成分开 |
| C：独立采集及恢复 | 文件预检、资料快照、独立任务、待对账／电脑中转 | 错文件不污染旧任务；本机跨来源重复受控；不自动确认库存或放行；恢复时不重造原批次 |
| D：体验完善 | 列表、检索、视觉样式、提示音和辅助体验 | 长文本和大字体可读；错误有可执行下一步；关键任务现场走查通过 |

验收场景至少包括：

1. 320dp 宽及真实系统栏环境；字体 100%／130%／150%／200%，长车号、长名称、零记录、大数量；不得横向溢出或遮住关键动作。布局预览不代替 Android 实测。
2. 扫码枪连续输入、手输键盘、候选确认、F1／F2／Enter、重复输入、未决／待保存、保存失败、末包撤销、非末包调整、连续多包调整后的统计一致性；调整模式不会误新增扫码，扫码过程中不误跳导航。
3. 无网络、服务器不响应、会话到期、设备重启后时间资格失效、回执丢失；能够解释“可看／可扫／可结／可传／可导出”分别为何可用或阻断。
4. 文件选择取消、空间不足、只读目标、USB 拔出、进程中断；原事实不丢，不产生虚假的完成状态。
5. 原操作员不在、管理员受控救援、跨设备或多机离线冲突；权限拒绝仍可理解，不以 UI 绕开身份和生产门。
6. 手套、单手操作、仓库光线、提示音与噪声、实体键与触屏混用；邀请实际操作员完成继续扫码、查异常、导出三类任务并记录误触／停顿。尚未做现场计时，不捏造效率提升百分比。
