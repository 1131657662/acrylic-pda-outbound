## 背景与目标

现场 PDA 没有微信、邮件或文本编辑器，不能依赖复制粘贴在设备与 Web 之间传递长公钥，也不能要求手抄设备 UUID。现有 Web 公钥表单及 PDA 手工绑定只能作为高级维护入口，不再承担日常登记流程。

目标是让管理员和操作员只交换一个短登记码，就能完成设备身份核对、仓库选择、登记和本机绑定。两边可以异地、不同局域网，但必须访问同一套后台。登记不依赖电脑摄像头、手机或额外通信软件。

## 已确认操作流程

1. PDA 首次打开 App，确认已配置的服务环境，点击「开始登记」。
2. App 在 Android Keystore 生成或复用本机密钥，通过服务端挑战签名证明持有私钥，自动提交公钥并申请配对。
3. PDA 显示短登记码，初始设计为8位数字、分两组显示，例如 `4827 1953`；同时显示环境、有效时间和等待状态。
4. 管理员登录 Web 的「PDA 设备管理」，输入登记码，查看对应申请的型号、申请时间等辅助信息；选择获授权仓库，填写设备编号及名称，并确认登记意图。
5. 原 PDA 自动取得待绑定信息，显示服务环境、仓库及设备名称。操作员核对后点击「确认绑定」。管理员确认前不能绑定，PDA确认前不能获得正式设备使用资格。
6. 后台完成登记并返回对应身份；PDA核对响应与原申请、公钥及确认信息一致后，持久保存服务地址、设备 UUID 和公钥绑定，再进入人员登录页。
7. 后续人员登录仍使用账号密码和本机私钥证明。配对登记不替代登录，不自行增加操作员权限。

普通操作员不需要查看、复制或输入公钥、私钥、长摘要及 UUID。公钥与 UUID 可在高级身份详情保留，私钥不可导出。

## 地址与网络

- 正式包配置正式 HTTPS 服务地址，测试包配置测试地址，页面明确展示环境；开始开发时核对实际地址，不虚构已部署的域名。
- 如服务地址尚未确定，采用明确的构建或部署配置接入，并记录真实联调地址与交付限制；不得把电脑回环地址当成异地可达地址。
- 同一后台可服务异地 PDA 和 Web，不要求设备互相直连或处于同一 Wi-Fi；短登记码不能代替网络连接。
- 当前本机测试可继续使用 debug 已支持的 USB 回环转发。首次登记必须联网，断网显示可恢复状态，不宣称登记成功。
- 扫描服务器配置码或 Web 配对二维码是辅助方式，不是本次短码基础流程的前提。需另行核验 M71 对屏幕二维码的扫描效果；不假定型号名称已经证明能力。
- 地址配置和辅助扫码必须保留 HTTPS 证书校验、环境与域名核对，不因扫码而关闭安全校验或静默替换已有绑定。

## 安全与身份约束

- 私钥由 PDA Keystore 保管，后台只保存公钥。公钥与申请必须关联有效的私钥持有证明，不能凭任意客户端上传字段直接建立已启用身份。
- 短登记码仅供管理员查找申请，不是设备认证令牌、登录凭据或查询绑定结果的唯一依据。
- 未登记 PDA 只能执行受限的申请、挑战证明和本申请状态查询；不得浏览其他申请、设备、仓库、订单或获取管理权限。
- PDA 自身的轮询、确认和结果恢复须使用不可猜测的申请凭据及与原公钥绑定的证明；结果不能被只知道短码的其他设备领取。
- 初始有效期建议10分钟；服务端生成登记码，避免同时有效申请撞码，并对申请、短码查找及签名失败限速。具体阈值在实现时按现有安全模式确定。
- 管理员操作沿用 Web 会话、CSRF、`device:manage`、仓库范围、幂等请求和恢复代次校验；最终登记仍须重新核验权限及申请状态。
- 仓库、名称、设备代码和公钥属于待确认申请内容。确认后不得被另一管理员或并发请求静默更换；实质修改须重新核对。
- 两台 PDA 使用各自公钥、申请和设备身份，不能共享登记结果。型号或序列号仅作辅助辨认，不能代替密钥证明。
- 保留现有设备代码、公钥摘要的唯一性和订单占用约束；已绑定设备显示现有身份，不通过重新配对换密钥、迁仓、换机或解除订单占用。
- 记录申请、管理员确认、PDA确认和最终登记的必要审计；不把密码、私钥、申请凭据或可用认证令牌写入普通日志。

## 状态与异常恢复

页面必须区分：未申请、申请中、等待管理员、等待PDA核对、绑定中、已完成、已过期或取消、网络中断且结果待核对。具体服务端状态名在开发时与契约统一。

- 发送写请求前保留原申请及必要恢复信息；重复点击、超时或丢响应沿原请求恢复，不自动换键、重新生成身份。
- 后台已登记而 PDA 未收到响应时，原 PDA 可经本机证明取得同一登记结果；完成回执的恢复不能因短码过期而被简单切断。
- PDA 本地保存失败时不能显示完成；恢复后仍核对原结果并原子保存，防止只有半份绑定信息。
- 未完成申请过期时重新申请应复用现有 Keystore 密钥；先核对是否已有成功登记，避免把结果未知误当成从未登记。
- 两个管理员、两台设备、取消与确认的竞争必须由服务端原子裁决；仅有一份有效登记，原回执不可改写。
- 用户重开 App 或刷新 Web 后能核对并恢复本申请；具体存储范围、过期清理和恢复边界在实现说明中明确，不用清除 App 数据作为解决办法。

## 实现与验收范围

沿用现有 Kotlin/XML、Spring Boot、Vue 和身份权限模型，补齐配对接口、持久状态、Web 管理入口、PDA 首次登记页及必要迁移。先读取实际最新代码，不按旧版0.3.0或0.5.0路径假定当前实现。

必须验证以下行为，并区分自动化结果与现场操作结果：

1. 管理员和操作员仅通过短码完成登记，公钥、UUID和服务信息自动传递；随后真实设备证明登录成功。
2. 两台 PDA 同时申请不会交叉绑定，短码泄露、错误签名、过期申请、重复确认和越仓库操作不能取得错误身份。
3. 登记和本地保存各阶段的丢响应、断网、重开与重试恢复同一结果，不重复登记。
4. 已绑定设备和原订单数据保持，升级不清库、不换私钥、不改变占用。
5. 网络前提正确：分别记录本机或模拟器联调、不同网络连同一后台、M71真实操作的验证状态。没有异地环境时明确未验证，不能用回环测试替代。
6. PDA在实际480×800屏幕中登记码、状态和确认按钮可见，流程不需要微信、编辑器、电脑摄像头或长文本输入。
