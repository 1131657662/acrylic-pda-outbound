## 仓库与分支职责

项目使用同一个 GitHub 仓库：`https://github.com/1131657662/acrylic-pda-outbound.git`。用户于 2026-09-17 明确授权设为私有，已通过 GitHub 接口核验为 private；后续仍应在首次推送到新远端或可见性变更后核对，不能假定设置永远不变。

| 名称 | 职责 | 允许的状态 |
| --- | --- | --- |
| `main` | 保存经过验证、可交付的版本 | 相应交付范围已经验证，版本与限制有明确说明 |
| `codex/development` | 保存和备份当前开发进度 | 允许功能未完成或测试未通过，但必须在提交说明中注明 |
| `codex/<topic>` | 按需要隔离单项开发或修复 | 从开发分支创建，完成后合回开发分支，不代替长期开发分支 |

常规业务开发在 `codex/development` 或其短期分支进行。准备进入 `main` 时，以拟合入的实际代码和对应验证为准，不能因为文件名包含版本号或曾有旧版本通过测试，就认为当前版本已经可交付。

不要另建测试仓库，也不要额外建立职责相同的长期 `test`、`dev`、`develop` 分支。若用户以后改变约定，同步修改本文和根目录 `AGENTS.md`。

## 提交说明

标题采用 `类型(模块): 具体变化`，使用清晰的中文描述。类型可使用 `feat`、`fix`、`docs`、`test`、`build`、`chore`、`refactor`。范围单一的提交省略模块也可以。

每次提交正文应包含以下信息，按改动大小简写，但不能省略验证或已知失败：

```text
feat(pda): 增加结单上传结果恢复（开发中）

改动：说明本次解决的问题和实现范围。
验证：列出实际运行的检查及结果；未运行或失败须明确说明。
未完成/已知问题：记录后续工作、失败场景或适用限制；没有则写“无”。
版本/兼容：说明是否改变APK、接口或数据库版本及升级影响；无影响则注明。
```

以上为格式示例，不是本项目当前测试结果。文档提交可以简写为“验证：已检查文档及引用，未运行业务测试；版本/兼容：仅文档，无运行行为变化”。

- 每次提交围绕一个明确的功能、修复或文档主题，不把其他任务未完成的改动顺带提交。
- 用于保存开发断点的提交应注明“开发中”或“阶段备份”，明确已完成与未完成部分。
- 引用历史测试时写明对应版本或提交，不把旧结果写成当前代码的验证。
- 区分构建成功、单元测试通过、接口联调通过、模拟器通过、真机验收通过和已部署；只声明有证据的状态。
- 不因开发分支允许保存未完成代码而跳过原本必要的验证；确实尚未完成时如实注明。

## 测试版本与正式版本

测试版本使用明确的预发布标签，例如 `v0.3.0-alpha.1`，并在 GitHub Release 中标记为 Pre-release。上述名称只是格式示例，不能据此创建或声称已有发布。

测试标签固定到已完成该测试范围验证的具体提交。Release 说明必须包含对应提交、APK文件及SHA-256、已实现范围、验证结果、已知问题和升级注意事项。源码版本、APK内部版本、文件名及说明须一致。

正式版本在相应验收完成并合入 `main` 后使用正式标签，例如 `v1.0.0`；不能把预发布测试通过直接等同于完整系统上线验收。标签发布后不移动到其他提交；修订交付使用新版本。

APK及大型交付产物优先放在 GitHub Releases。代码仓库保存源码、构建配置、依赖锁文件、必要的结构快照及可公开的文档，不把安装包堆积当作版本历史。

## 提交与上传前检查

1. 确认当前分支、远端地址和工作区改动，识别是否存在其他任务正在修改的文件。
2. 使用明确路径暂存本次内容，并检查暂存差异及文件清单。
3. 排除 `.local/`、本机配置、密码、私钥、数据库、构建缓存和真实业务数据；`.gitignore` 不能自动清除已经进入历史的敏感文件。
4. 运行与改动相关的验证，记录真实结果；合入 `main` 或发布前复核版本对应的必要检查。
5. 按本页格式写提交说明，推送到职责正确的分支。

提交、推送、合并、打标签和发布是分别发生的动作，按用户当前已有授权执行，不重复询问已授权事项。完成报告应注明实际分支、提交号、验证状态，以及是否确实推送或发布；未执行的动作不能写成完成。
