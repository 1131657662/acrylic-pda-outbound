# C1 非空升级与验收矩阵

本文件定义未来实施门槛，**全部动态场景本批未执行**。当前只检查文档和源码引用，不能把第三轮43单元/60IT/153离线/116路径计为C1验证。方案见 [DESIGN](DESIGN.md) 和 [TRANSACTIONS](TRANSACTIONS.md)。

## 1. V33非空升级

迁移编号由总调度在 E2/C1 落地批统一分配；本目录不预占 V34、不提供可执行 SQL。只在新的合成非空 V33 副本演练，原库、恢复断点、原密钥和设备保持。MySQL DDL可能隐式提交，必须逐条记录恢复点，不假设 Flyway 事务可整体回滚DDL。

| 阶段 | 要做的事与停止条件 |
| --- | --- |
| P0清点 | 保存schema/checksum/旧表原列摘要、FK/唯一键、原正文/原回执文件hash；合成库必须含正式成功/取消、TEMP完整待审及占用、无正文ABORT、部分块ABORT、原授权/审计、旧api幂等键、原FH计数器。缺场景则不得开始验收统计 |
| P1来源基础 | 先接受E2已审来源与共同占用迁移，保留V33所有原事实；缺source归属/跨仓不一致/旧占用孤儿应报告并停止，不能建占位订单/assignment或猜原操作员 |
| P2追加台账 | 增加C1专表、索引和FK；现有api请求及旧回执不搬迁、不覆盖，不对每条历史请求补新命令或新签名。新route仅由新C1写者使用 |
| P3状态初始化 | decision_state可为经过一致性核对的每个TEMP scope初始化decision_version=0，表示“新机制下尚无决定”；明确记录migration-origin，不能说历史已审批。不存在的scope不创建；已完成事实不重开 |
| P4映射基线 | E2负责保存MIGRATED_BASELINE/observedAt等迁移可知来源，不回填伪造历史mappedAt/actor/签名。nullable canonical可作为基线0，已有canonical可作为基线1，但必须标记迁移观察且不声称当时存在mapping事件；受控新映射以后递增 |
| P5强约束 | 历史可证实关系核对通过后加组合FK/CHECK/NOT NULL；无法证明的证据仍未知或保持nullable，不能用默认UUID、空正文/空权限或当前人补齐非空列 |
| P6切换与回退 | 先完成独立复审与受控验证，再在开发环境接入新路由。已有C1新事实后不能运行不认识它的旧写者继续写相关来源；暂停新写后回退应用可以保留表/原字节，不自动DROP或降级覆盖。真实部署仍不在本授权内 |

如果最终选择与上述映射初值不同，E2/C1必须在同一协议批修正DTO、向量、旧库升级和currentEffect评估；本提案不允许读端自行从canonical非空即推导版本。C1依赖真实持久值，不在读取时临时“造出1”。

新FK需要显式核验：request→actor、receipt→request、receipt→同仓scope/source/submission/authorization、nullable canonical→同仓order、mapping→不可变历史事件、evidence→同来源不可变清单、decision_event→receipt。提交后检查双方引用闭包、同仓关系和receipt.resourceId对照。不能只对比行数，必须比较原值及原字节；不需要证明的旧签名不重签。

索引采用与真实访问匹配的等值前缀：原键查既有principal/route/key唯一索引；新receipt按api_request_id唯一定位，来源历史分页用warehouse_id/scope_id/recorded_at/id并固定cursor截点，decision事件用scope_id/resulting_decision_version。不以nullable canonical作为唯一身份或强制INNER JOIN订单，否则会遗漏ABORT证据。实际EXPLAIN、锁等候和大数据开销到新合成库再验，不声称本次已测性能。

| B 唯一原键 | 两连接提交顺序/锁等待/最终原键与receipt行、规范字节和原响应摘要；另测不同principal相同commandId | 同键同文一次；异文409且不改原值；别名route不能绕过；跨仓换body冲突或按授权拒绝；不同principal独立服务端receiptId，无全局客户端UUID冲突 |
