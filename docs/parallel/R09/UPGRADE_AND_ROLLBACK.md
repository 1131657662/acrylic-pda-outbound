# 升级、失败回退与恢复操作手册

此为待审阅的服务器操作方案，本轮未执行部署、迁移升级或外部告警启用。不要直接运行现有 `deploy/test/activate.sh` 来“验证配置”：它会切换版本、重启 API、修改 Nginx 并启用既有备份 timer。

2026-09-20只读核对：本轮固定源码32ff90f为API0.21/V28/Room14，现网记录仍API0.18/V23/code16；本任务没有切换。新源码备份已记录API与Worker的active-services.txt，六组件检查已接入。此前V21五组件归档继续可读，但不能把旧脚本的只停API解释为已保护Worker。

## 发布前准备

1. 明确目标环境、专用服务/库/账号/目录、负责人及维护窗口；读取当前进度和现场在途状态，核对仍在使用的 PDA 版本。保持其他项目服务、共享 MySQL 参数和业务数据不变。
2. 固定旧/新 release 的提交、dirty 状态、JAR/Web/APK 摘要、接口兼容、Flyway历史/目标迁移、Room版本和签名。准备可重新安装的旧程序本体，不把 `release.txt` 路径当成可用旧包。
3. 在隔离库克隆上实际应用升级路径，并检查数据、文件、旧/新客户端和未完成请求；Flyway validate 通过不等于数据迁移正确。DDL隐式提交可能留下部分迁移状态。
4. 保存数据库/业务文件/签名/配置同截点备份、归档验证和实际恢复证据；记录截点后的可能丢失窗口。备份中包含账号私钥时仅存受控加密介质。
5. 预先写出故障判定：启动、真实业务依赖、5xx/延迟、资源/OOM、迁移错误、签名或回执异常。`/auth/csrf` 返回200但 `serviceMode=UNAVAILABLE` 视为失败；CSRF本身可创建短期会话，不能把它称为完全无写入的数据库探针。

## 升级执行分支（后续获授权后）

- 先关闭本项目普通写入口并停止全部 API/Worker 写入者，记录在途操作及active-services.txt。32ff90f先停Worker再停API、恢复时先API再Worker；只恢复此前活跃项，未部署/禁用Worker保持原状。不能只停 HTTP 而让后台任务继续记账。
- 使用新发布包指定的备份/迁移入口，确认备份之后直到迁移和检查结束都不恢复普通写；迁移账号仅本库 DDL 权限，运行账号无 DDL。
- 只将程序切换到已校验目录；确认客户端契约、文件权限、签名和数据一致。检查失败保持写入关闭，保留日志与失败状态，不循环重启来掩盖故障。
- 成功后按审核后的步骤放开本项目入口，逐项核对实际写入与原请求重试。没有现场设备参与只能记服务器验证，不能记 PDA/异地/生产验收。

## 程序回退与数据库恢复必须分开

| 条件 | 可做动作 | 不可据此推断 |
| --- | --- | --- |
| 无数据库/数据格式变化，旧程序已验证兼容现存库和新写事实 | 停止本项目写入，切回已保存的旧 release，重启后检查 | 旧程序启动成功不代表所有在途客户端协议兼容 |
| 只有可前后兼容的增量迁移，旧代码在迁移后的库已隔离验证 | 可以回退程序，通常保留数据库升级后的结构 | 不需要也不应自动删除新增列/表或回退 Flyway历史 |
| 迁移部分失败、改变语义/数据格式、删除/重写字段，或旧代码兼容性不明 | 保持服务停止，保留失败状态，优先做向前修复；需恢复时进入下节 | 不存在可默认调用的 Flyway“直接降级”；修改历史checksum/repair不能代替修复证据 |
| 发布后已发生真实出库、取消、调整或确认，拟使用旧备份 | 登记丢失窗口，保留当前数据库/文件快照，进入完整受控灾后流程 | 禁止直接旧库覆盖新事实；不能把更新回退等同于无损恢复 |
| 签名/配置不兼容 | 核对原 keyId/材料及配置，与数据库和原回执共同恢复验证 | 不能新生成密钥冒充旧身份或让已有PDA重新配对来“解决”恢复 |

不提供一键 DROP、迁移降级、覆盖数据库或启动旧库写服务的脚本。这些动作依赖真实兼容证据和完整恢复能力，未包含在本轮授权范围。

## 数据库/文件恢复操作顺序

1. 保持本项目写入口停止，保存当前故障集；区分技术故障、数据损坏和错误业务操作，记录受影响仓库/设备/订单及证据。
2. 核对备份来源可信性、完整组件、加密介质解密权限、版本和关键材料。先在独立实例/新目录恢复本项目数据；共享 MySQL 需要 PITR 时也先恢复至隔离实例，绝不整体回滚共享生产实例。
3. 运行结构、数据、文件和业务一致性检查；恢复配置中的地址和账号仍指向原环境，须安全重配到隔离环境后才允许启动验证程序。不得执行归档里的 shell/env 代码。
4. 技术快照恢复通过只说明该截点可还原。如果截点之后可能存在任何现场事实，必须接入外部恢复代次、RECOVERING、设备证据对账、同ID重建及调整链/库存核验；本轮尚无完整流程，继续维持停写。
5. 后续由业务主管与运维按恢复案件确认影响范围、无法联系设备、未知批次、物理盘点和审计缺口，准备当前代次基线/授权并审批释放。无法证明独立安全范围时全受影响仓库继续隔离。
6. 记录启动/开放时间、RPO实际丢失范围与RTO各阶段耗时。没有异地文件/证明连续归档和足够规模演练，就不能声明系统RPO≤15分钟或RTO≤4小时达标。

## 备份/资源超限导致服务停止

R02 原备份脚本以 EXIT trap 尝试重启先前运行的服务；OOM、SIGKILL、宿主机故障或 systemd 强制结束可能绕过 trap。候选资源限制新增超时，故必须检查备份 unit 的 `Result`、API 的 `ActiveState`、最新归档和截点状态；不能仅检查上一份好备份。

只有确认这是普通备份失败、没有迁移/恢复进行、库和文件仍为原运行状态时，才可按目标环境授权及原活跃清单恢复 API/Worker。若处于 `--keep-stopped` 迁移窗口或数据库恢复，保持停写并按对应分支处理。检查失败应通知负责人，不能擅自解锁订单、释放库存、回收离线设备授权或启用自动重试写入。不要因恢复包内任务可执行就提前启动Worker：迁移/隔离/原签名/账务核验及完整恢复写入阻断尚未完成时，旧租约和重试必须继续保留而不能自行放行。
