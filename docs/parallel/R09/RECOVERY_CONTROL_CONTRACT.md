## 当前能力与不能替代的部分

`87e1893`的`server_state.recovery_epoch`是业务库中的整数，API以字符串返回；`ServerState.lockWritable`在事务中对该行持有共享锁，校验NORMAL及期望代次。现有Job租约有owner/token及提交事务保护。两者均应复用，但没有独立于旧业务备份的权威控制记录，也没有全写入口覆盖证明。

V2.3要求新的权威`serverRecoveryEpoch`为随机UUID。**不能直接把UUID写进现有整数列或仅替换响应文本**。主线需迁移传输代次及引用，兼容历史数字代次字符串；原签名正文、原`sourceRecoveryEpoch`、旧JWT、旧审计及ID不改。可以新增UUID控制身份并保存旧数字代次映射作迁移桥梁，但完成正式契约迁移前不得宣称UUID恢复协议已接入。

兼容门槛必须分别记录“当前传输代次”和“原事实代次”：旧数字值只能按安装身份及可信迁移记录映射到历史来源，不能将任意相同整数当作同一恢复会话。服务器、PDA、同步游标、Job及响应封装均完成同一契约后才能发布UUID；不支持UUID的旧客户端明确拒绝新作业并保留恢复资料，不能静默回退到数字1或通过重新登录解除本地阻断。升级前后的签名原文、原ID、旧epoch证据查询和丢响应重试须一并回归。

## 库外控制记录

独立受控目录/存储不属于业务数据库恢复集，使用单一协调写者、排他锁、原子落盘与fsync，保留异地不可覆盖历史。备份只记录当时控制记录的ID与摘要作为证据，恢复时不得把旧副本覆盖为权威当前记录。跨主机的单写者仲裁与存储能力须在选定环境验证，文件rename不等于跨主机共识。

建议记录：`formatVersion`、`installationId`、`recoverySessionId`、`epochId`（UUID）、`revision`（十进制字符串）、`phase`、`previousRecordSha256`、`recordSha256`、`snapshotId`/备份清单摘要、`affectedWarehouseIds`、`possibleLossFrom/Through`、操作人/请求ID、`createdAt`。时间只作证据，不作为互斥令牌。秘密、原始正文和业务明细不写普通日志。

每个命令带`commandId`、规范正文SHA-256及`expectedRevision`。同命令同摘要返回原结果；同ID异摘要冲突；revision不符返回CAS冲突，不重新生成epoch或自动放行。先持久追加历史，再推进当前指针；崩溃遇到半完成状态保持关闭，按原命令核对恢复，不以最新mtime猜当前记录。历史链摘要用于发现损坏，不替代权限、签名与异地可信副本。

普通重启仅加载原控制记录并核对DB投影与安装身份。缺失、回退、未知格式、验签失败或不一致时启动写服务失败；不能自动初始化“正常”。首次安装初始化与灾后换代必须区分。

## 控制状态与跨存储崩溃边界

这些是运维控制阶段，不是新增的对外`serviceMode`值；中间阶段对外均保持RECOVERING。

| 阶段 | 进入条件 | 允许动作/退出条件 |
| --- | --- | --- |
| NORMAL | 权威记录、DB投影、运行实例及能力矩阵一致 | 普通授权和业务写仍逐事务校验 |
| QUIESCING | 原命令CAS成功并开始关闭入口 | 阻止新普通事务，停止API/Worker/所有文件写者；等原事务排空。尚不标记新代次可用 |
| RECOVERING | 全写者停止、旧连接已失效，生成并持久化新UUID；隔离恢复目标与控制记录匹配 | 只允许受控认证、只读与恢复证据/案件事务。普通业务不恢复 |
| VERIFYING | 固定设备/批次/调整链清单和证据版本 | 重建、核对、缺口与实物处理；新证据会使旧核对结论失效 |
| RELEASE_READY | 本版本所有释放条件有证据及主管/运维确认 | 生成绑定清单摘要、revision与范围的释放决定，尚不开放普通写 |
| NORMAL（同一新epoch） | 受控释放完成DB投影及库外提交确认，实例重新验证 | 发布完整新基线并按业务规则重新授权；重启不再换epoch |

两个存储不能凭一次外部读取获得原子性。恢复换代前必须停止并排空所有旧写者，隔离旧实例/旧连接后才替换数据库。释放也必须分阶段：库外PREPARE释放 → DB以排他锁提交对应revision/epoch/范围 → 库外COMMIT释放 → 写实例核对两侧相同提交证据后开放。任一步崩溃、控制存储不可用或记录不一致均保持关闭；重试同命令完成核对。不能只设置DB为NORMAL就立即开放。

正常业务事务建议固定锁序：恢复门禁共享锁 → 身份/设备锁 → 来源/订单/批次锁 → 包周期/库存锁 → Job结果。切换协调者取恢复门禁排他锁并等待前序事务结束；发现现有不同锁序先由主线统一并发测试。单靠“提交前再读文件”存在检查后切换窗口，不能代替持锁事务及换代排空协议。

## 共享接口建议

以下是职责契约，非已实现Java签名：

- `RecoveryGate.loadAtStartup(installationId)`：取得可信控制快照；缺失/不匹配失败关闭。
- `RecoveryGate.lockOrdinaryWrite(expectedEpoch, operation)`：加入已有事务，持锁到提交，核对DB投影、当前控制revision/epoch、NORMAL及操作允许性；不得开启独立事务提前释放锁。
- `RecoveryGate.lockEvidenceWrite(sessionId, expectedEpoch, expectedRevision)`：仅用于明确恢复入口，校验案件/仓库范围、在线认证和证据能力；不复用普通提交白名单。
- `RecoveryFence`：绑定installation/session/epoch/controlRevision和Job租约token。Job领取/续租/回收/失败写/完成均校验。旧Job可保留历史，但旧token不得标记成功、发提醒、发布文件引用、扣账或推进游标。
- `RecoveryStatusView`：仅公开当前epoch/serviceMode与所需恢复标志；状态/监控端点不得创建Web会话、签令牌或返回内部路径/密钥。认证、错误、同步、提交查询都包含一致元数据。

认证在RECOVERING可以保留登录和证明身份的受控写（挑战、登录/刷新会话、必要审计），但不得附带新作业授权或临时资格签发。限流、来源设备签名、身份版本、仓库授权、管理员会话CSRF仍必需。恢复证据上传可用并不意味着允许配对/换机：代传按R07原来源证明和明确能力核验，不能用新设备身份替换原身份。

需盘点的写入口包括POST以及会写session/lastSeen/租约的GET、API幂等表、审计、同步outbox/基线、Job定时扫描、文件写入及数据库迁移。备份时停API/Worker仍是当前工具前提，本次93表恢复通过没有验证此门禁方案。

## 接入验收与未定实现项

最低组合测试：外部记录缺失/回退/部分落盘；DB旧快照与外部新UUID；普通重启；旧API事务与切换竞争；旧Worker持租约跨代次完成/失败/续租；认证允许但新授权拒绝；证据入口跨仓库/代传越权；释放两阶段各崩溃点；丢响应同ID恢复；V33正文前取消与待审来源；R07更正之前快照恢复。每个测试断言原事实/占用保留、无新放行、无重复账务，并检查事务结束后的真实数据。

待明确的是控制存储部署与跨主机隔离手段、历史密钥环、UUID迁移/旧客户端拒绝策略及主线调用点；这些是实现检查点，不重新询问已确定的现场停工、主管与运维核对、未知保持隔离等业务规则。R07故障代传最低证据及调整模型由其设计/业务线提供。服务器部署、既有审批阻断、M71及清理边界保持。
