# R07分段实施与主线采用断点

日期：2026-09-20。**设计交接稿；R07业务代码尚未实现。** 依据主项目剩余计划M3/M4/M5和[已提交依赖复核](BASELINE_UPDATE.md)。本页是建议实施顺序与完成门槛，不分配Flyway/Room/API版本，不替主线启动编码或对未决政策作批准。

## 1. 采用方式与共同约束

推荐将R07分成下表可独立验证的批次。主线先完成R06的M1上传恢复、M2确认/关联/拒绝，再固定共同来源与锁序；共同模型先行，原机可用交接先收口，更正及对账随后，故障证据/恢复控制与R09按接口并联推进。

| 组织方式 | 取舍 |
| --- | --- |
| 整个R07等待整个R09 | 会将普通交接、更正也挂在灾后全链上，且R09又等待R07结果结构，不采用 |
| 先做全部界面，再接证据/结果 | 容易把“批准”误当可扫码或解隔离，产生两套来源/账务入口，不采用 |
| 固定模型后分交接、更正、对账、故障恢复批次 | 推荐；每批有独立启用门槛、原请求恢复及兼容验证，具体缺证据只阻断相关路径 |

共同边界：原事实/原回执不可变；R05基础复用；TEMP原资格复用`temporary_work_origin`；正式化复用`OrderNumbers`；R08只读消费；R09拥有外部恢复控制与范围释放。原机可用交接不要求先实现故障机证据代传，日常更正不要求先完成全部灾后重建，但跨代次路径始终阻断到专用对账完成。

## 3. R07与R09的最小接口次序

1. **R09独立工具先行**：扩展固定已提交V29～V32的全库/文件检查，纳入TEMP原资格绑定、混合审计及编号计数器；不等待R07所有业务。
2. **双方先固定边界**：R09提供外部代次/模式/范围及证据接收状态；R07提供不可变来源、终态、交接、调整/账务/周期链和引用根，详见[引用契约](SOURCE_RESULT_CONTRACT.md)。此时共同校对API/Worker/认证写屏障调用点及文件归属。
3. **并联实现独立模块**：R07可先验证NORMAL下原机交接和更正；R09实现恢复控制、设备清单与证据分页/缺口。普通audit/archive恢复只复用已支持部分，不冒充完整重建。
4. **固定提交组合验证**：按恢复截点重建原成功/ABORT、结果/账务/周期和原交接激活；单独记录未联系设备、未知范围、补证据和释放证明。结果齐全才开放相应故障/跨代次路径。

因此“R09缺完整恢复”只阻断6及5中需要缺失事实重建的路径；“R07尚未全做完”也不阻断R09已提交模型的备份/监控。整单90天清理单列为M5，须在完整恢复、引用核对和可取回证明后另行开发验收，当前`localDeletionAllowed=false`保持。
