# PDA 订单流程修复设计

日期：2026-09-23。依据：[问题报告](../../PDA_ORDER_FLOW_ISSUES_2026-09-23.md)。本设计经用户确认方向后固定实施边界；代码、部署和现场验收另行进行。本设计不改变 R06 E2a 的生产 V35、隔离验收器、失败证据和写权。

## 目标与非目标

目标是让订单刷新、领取、准备及本机列表在弱网和历史数据下给出真实、可恢复的状态；完成 PDA-01 至 PDA-08 的产品代码修复和验证，并为 PDA-09 的后续交付提供诚实升级路径。优先保证已成功的写操作不被后续读取失败误报、原请求和原证据不丢、准备前有可信车号与业务号。

不承诺仅靠 App 代码解决外部 DNS 故障，不对未测的慢操作指定虚构瓶颈或时延目标；不改变订单占用、扫码防重、签名、审计、恢复代次及生产放行规则；不删除本机已完成订单、被拒领取事实或失败证据；不自动在真实订单上重演领取/上传，不部署 test 或生产。旧 code15/16 的硬编码兼容判断不能被新包反向修改，首个桥接包仍需经过核验的手动系统覆盖安装。

## 方案比较与选择

1. **仅改页面、隐藏历史、失败自动重试**：开发量小，但掩盖真实状态，可能生成新写请求且破坏证据，放弃。
2. **按结果状态分层修复**：补固定订单版本的展示契约，保留领取意图历史，分离写结果与刷新结果，按真实本机状态分类；测量后优化连接和列表。改动可切片验证，选用。
3. **重写整个同步/准备系统**：不能区分原问题和新回归，影响 R06 并行验收，放弃。

## 契约与本机状态

### 服务端授权展示

`AssignmentStore.View` 增加 `orderNo`、`vehicleNo`、`plannedTotal` 只读字段。`orderNo` 从同一 `order_id` 的 `outbound_order` 获取；车号和计划量从 assignment 的 `(order_id, revision)` 对应不可变 `order_revision` 获取，而非当前最新修订。`mine` 仍只返回本设备 active 授权，并延续 `forOperator` 对非原操作员剥离 `offlineToken` 的行为；新增字段不得扩大查询权限。已准备卡片仍以本机已验签 `planJson` 为最高可信来源。旧 `OB...` 业务号原样显示，不把内部 UUID 当订单号；接口新增字段保持向后兼容，并补 MockMvc/真实数据库及权限测试。此改动预期不需服务端 Flyway 迁移。

### 领取意图与 Room 17→18

将现有按 `orderId` 唯一的活动 `claim_intent` 改为按 `(orderId,userId,deviceId)` 唯一，以便不同操作员的旧意图互不覆盖；同一人员设备的 `UNKNOWN` 仍只能恢复原请求。新增仅追加的 `claim_intent_history`，保存被替换的旧意图原幂等键、正文、用户/设备、恢复代次、状态、原错误和归档时刻。Room17→18 迁移在事务中重建活动表并逐值复制原行、建历史表与索引；其余业务/同步/临时单表不变，禁用破坏性 fallback。旧 `UNKNOWN` 不迁到历史，不修改正文或键。

新增只读 `GET /pda/orders/{id}/claim-preview`，通过现有 `pda:assign` 与仓库隔离检查返回当前 READY 的车号、业务号、`rowVersion`；非 READY 不给出可领取预览，不附离线凭据。新领取先核验当前正式人员/设备、服务器恢复为 NORMAL，并从该端点取得新鲜版本。当前 `(orderId,userId,deviceId)` 的 `UNKNOWN` 只能以原键原正文恢复；`REJECTED` 只有在预览给出不同 `rowVersion`、同一当前恢复代次且操作员明确重新领取时，才在一个 Room 事务中把旧行追加到历史并替换为新意图/新键。同版本或网络无法核实则保留拒绝与处理提示。其他人员的旧意图独立保留；他人也必须取得新鲜 READY 预览才能提交自己的新意图，服务端继续原子裁决唯一占用。历史记录不纳入普通本机待处理卡片，异常列表可查看原拒绝与时间。测试迁移、断电重开、同单冲突后新发布、跨人、未知响应和重复点击。

### 本机任务投影

构建只读任务投影，把 `prepared_order` 与 `work_order`、当前 `local_submission`、召回/恢复控制及领取意图关联。优先级为恢复/召回阻断、未处理输入、提交结果未知/待上传、待审核、已验签成功、作业中、已准备、待准备、领取异常。冲突不凭远端一句“完成”抹去本机未上传/未知事实；显示来源与上次同步时间。当前任务优先，历史完成单独筛选；另一操作员的已准备资料可以看见但作业按钮须标明原人员并禁用，底层 `SessionWorkAccess` 继续校验。资料与审计仍留在库中。按状态/时间分页，不要求将所有历史视图一次加载到 Activity。

## 网络操作与性能

`refresh` 拆成可独立报告的“本机任务读取、服务端列表、订单/条码同步、审计/召回/归档”阶段。列表读取可先展示，但领取入口仍受当前认证、恢复控制与服务器版本裁决；任何阶段失败展示具体阶段、是否保留旧数据及最后成功时间，绝不能把空列表和刷新失败混同。扫码作业涉及的召回/恢复阻断不因 UI 请求顺序变化而跳过。

`claim` 和 `prepare` 分别持有“原请求结果/本机激活结果”与“后续刷新结果”。服务端已确认的领取立即从可领取视图移除并加入本机授权；刷新失败仅标同步失败，不把操作倒写成失败。确认结果未知保留原持久意图，禁止自动造新 POST；准备成功后列表更新失败仍能从本机验签资料恢复。下载失败保留占用、bundle 和原机记录。

按规范化服务地址缓存一个 `PdaNetwork`/`OkHttpClient`，服务地址改变时弃用旧实例；认证头按每个请求取得而非缓存旧会话，恢复观察回调保持当前实例语义。GET 可作明确手动重试；有副作用 POST 不做盲自动重试。把 `UnknownHostException` 等网络失败转换为中文的分阶段提示，同时不泄漏内部 URL/令牌；写请求未知时继续标“待核对”。记录脱敏阶段时长、请求数、大小和结果码，不记录授权头、签名、设备密钥、订单正文及可关联真实业务的全标识。

准备服务端仍生成完整固定仓库包与签名。先测首次 `PreparationService.prepare`、读取快照、压缩与保存、三段传输、校验、Room 激活及 ACK 的耗时/体积，在隔离库用真实规模 `EXPLAIN` 检查索引后才决定后续缓存/分批/超时调整。前台列表用稳定 ID、分段 Room 查询及可复用行，避免状态消息变化时全量 `removeAllViews()`；在 M71 按真实数量测帧耗时与滚动保持。
