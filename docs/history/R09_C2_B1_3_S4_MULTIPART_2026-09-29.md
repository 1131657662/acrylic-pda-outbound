## 0. 结论先行：S4 不需要任何产品代码改动

multipart 的解析与暂存发生在 `DispatcherServlet` 内（`StandardServletMultipartResolver.resolveMultipart` → 容器 `getParts()`），而 S3 的请求根过滤器已在**最外层**（`Ordered.HIGHEST_PRECEDENCE`）并为 `{REQUEST, ASYNC, ERROR}` 注册，因此"暂存 → handler → Session 保存 → 错误分派"本来就落在**同一个请求根**内。本轮**用真实容器把这句结论观测出证据**，没有为了"有改动"而新增产品代码：

## 2. 本轮发现（**已于 S7 轮撤回**）

> **2026-09-29 更正（S7 轮）**：本节定性**已撤回**。S7 轮查明其成因是本轮引入的 `RecoveryMultipartParseRecorder` 代理未解包 `InvocationTargetException`，把真实的 `MaxUploadSizeExceededException` 包成 `UndeclaredThrowableException`，从而绕过了应用的 413 处理器；修正探针后超限即返回 **413**（产品侧映射在 S4 之前即已生效）。详见 [S7 记录 §4](R09_C2_B1_3_S7_REFUSAL_MAPPING_2026-09-29.md)。下文原文保留，作为"测试仪表缺陷被记成产品缺陷"的教训。

**超限部件的拒绝映射与文档不一致**（**已撤回，见上**）：`spring.servlet.multipart.max-file-size=2MB`，上传 2.5MiB 部件（低于 3MB 请求上限）时，容器在解析阶段拒绝，实际观测响应为 **500 `INTERNAL_ERROR`**（应用通用处理器），而 `ApiErrors` 为 `MaxUploadSizeExceededException` 准备的是 **413 `FILE_TOO_LARGE`**；handler 未触达（`s3-multipart-large=0`，无新根、无泄漏）。**这是既有错误映射问题，与本轮根接线无关**（本轮未改映射）；设计 §4.4／第 20 行的拒绝码 HTTP 映射属后续批次，此处只如实记录，不宣称已修。
