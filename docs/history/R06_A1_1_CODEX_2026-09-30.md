## 4. 包可见性：只读诊断与后续等待方式

- **本次批准安装后的独立冷启动**：诊断不安装、不启动 app、不执行 instrumentation。2026-09-30 22:34:46（Asia/Shanghai）首样本 package/activity 服务尚未就绪；22:34:52 包、APK 路径与 runner 均可见；22:35:06 boot=1、当前 user=0 且 RUNNING_UNLOCKED，随后一直保持。说明这一轮早期不可见可由等待消除；不能用它倒推旧轮根因。
- 所有安装和验收发生在批准的两个 runner attempt 中；之后诊断只读。旧、新失败/观察窗口都保留，不重跑 instrumentation 来获得诊断结论。

**建议的有界就绪门**：锁定 emulator serial 与实际 AVD；每 5 秒只读轮询，最多 120 秒，要求 boot=1、`service check package` 精确返回 `Service package: found`、目标 user 已解锁、`pm list packages --user 0` 有精确 app 行、`pm path --user 0` 有 APK 路径、`pm list instrumentation` 有目标 runner。只重试这些查询，尚未满足时不下发测试。

超时后保存原始输出并分类：服务未就绪；package 设置不存在；存在设置但 `pkg=null`；app 可见但测试 runner 缺失。本批自包含专项已获安装授权，可在新证据前置中安装匹配 APK 后重新检查就绪；不得清 userdata、重建旧 G1 失败条件或盲重试测试断言。

诊断派生表首版误用 `found` 子串，使 `not found` 也显示 serviceReady=true；原始 sample-0 明确保留服务不存在。已从原始样本按完整字符串重算 `approved-audit/readiness-corrected.json`，并用完整包名排除 `.test` 后缀误判；原派生表未覆盖，纠正说明在 `diagnostic-summary-correction.txt`。未因此重跑任何设备测试。
