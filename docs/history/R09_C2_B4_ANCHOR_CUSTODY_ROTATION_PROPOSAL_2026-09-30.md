## 1. 现有事实（读源码得出，附路径）

| 事实 | 证据 |
| --- | --- |
| 锚点是**显式外部供给**的 32 字节秘密（hex，正则 `(?:[a-f0-9]{2}){32}`） | `server/src/main/java/com/acrylic/outbound/recovery/RecoveryEffectConfiguration.java:25`、`RecoveryLeaseLifecycle.java:35` |
| 配置键：`outbound.recovery.effect-gate.anchor`；**默认未设**；跨进程开启而缺失/形状不符 ⇒ **启动失败** `CONTROL_ANCHOR_REQUIRED` | `RecoveryEffectConfiguration.java:36-37, 25-27`、`RecoveryLeaseLifecycle.java:35-37` |
| 秘密**只**来自配置/环境，**不写入**可写树；可写树里只留**身份** `anchorId = sha256(secret)` | `RecoveryEffectConfiguration.java:42`、`RecoveryLeaseRoots.java:26-27, 47` |
| 启动校验：运行期秘密的 `anchorId` 必须与 `lease-root.json` 一致，否则 `CONTROL_ANCHOR_MISMATCH`（失败关闭） | `RecoveryLeaseRoots.java:67` |
| 进程记录／租约记录各带 `anchorTag`（HMAC-SHA256），读取时校验 | `RecoveryLeaseProcess.java:38,78`、`RecoveryLeaseScan.java:137,152` |
| `leases/index.json` 整体受 `indexTag` 保护；「索引里有而记录缺失」与「记录不在索引里」都被拒绝（H3′ 闭合） | `RecoveryLeaseRoots.java:37-43`、`RecoveryLeaseScan.java:43,99,127,159` |
| `provision` 用 `CREATE_NEW` 写 `fenced.lock` / `index.json` / `lease-root.json`（**已存在的 P5 目录不能再 provision**） | `RecoveryLeaseRoots.java:33-51` |
| `lease-root.json` 是**自哈希**的（`bindingSha256`），其内容包含 `anchorId` | `RecoveryLeaseRoots.java:44-51` |
| 设计原文即声明：秘密的**保管与轮换属运维政策**，且"锚点强度＝配置来源的强度" | [ANCHOR_SPEC §3.5](R09_C2_B1_2_ANCHOR_SPEC_2026-09-29.md) |

**由此推出的硬约束（技术事实，非政策选择）**：既然 `lease-root.json` 自哈希且内含 `anchorId`，**轮换秘密必然使既有 marker 失效**（`CONTROL_ANCHOR_MISMATCH`）⇒ **轮换必须伴随一次离线重锚（re-provision/rekey）**，且该动作**只能在所有写者停机、且无在途租约**时执行。

## 2. 待用户裁定的政策问题（本提案的建议在 §3–§5）

1. **存放位置**：秘密文件放哪、谁能读、如何避免与 P5/P3 可写树同源。
2. **轮换方式**：是否允许轮换、由谁发起、在途租约怎么处理。
3. **历史 keyring**：旧秘密留不留、留多久、谁能用。
4. **重锚（rekey）算不算新的"生产决定"**：是否需要与七类生产决定同级的审批。

## 3. 建议的保管政策（存放位置与准入）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 形态 | 32 字节随机值的 **hex 文本**，单独文件（如 `.local/` 之外的服务账号配置目录或密钥管理目录中的一个文件） | 与现有正则/长度校验一致；不引入新格式 |
| 位置 | **必须不在** P3 `authorityRoot`、P5 `leaseRoot`、`closedAuthority`、任何 `restoreRoots` 之内或可写可达处；运行时只以**环境变量或配置指针**引用 | 设计原文：写入同目录则锚点无意义（`ANCHOR_SPEC §3.1`） |
| 权限 | 文件 ACL 仅服务账号可读；**不入库、不入 APK、不进交付物、不进 Git** | 与项目既有私钥/密钥边界一致 |
| 轮换权限 | 需**独立授权**（与七类生产决定同级），不因内部测试通过而开放 | 与 AGENTS.md「生产决定能力不得因内部测试通过而开放」一致 |
| 备份 | 与原库/现网备份分离保管；备份介质上不得与 P5 可写树同处一份可写归档 | 防止"能改写备份即能改写锚点" |

## 4. 建议的轮换流程（可执行、可验收、fail-closed）

**前提（三项必须同时成立，否则拒绝开始）**
- P1：**所有写者已停机**；`leaseRoot/processes` 与 `leaseRoot/leases` 中**无在途租约**（无未退役进程记录、索引与实际记录一致）。
- P2：已确认 P3 `identity.json` 与 P5 `lease-root.json` 的一致性与身份基准；本次轮换**不修改**身份/安装/根路径。
- P3：新秘密已生成并落在 §3 的位置，权限正确；**旧秘密已按 §5 归档或销毁**。

**步骤**

| # | 动作 | 期望结果（唯一） |
| --- | --- | --- |
| R1 | 停写者，退役全部租约，确认无在途 | 索引与记录一致；无进程记录处于活动态 |
| R2 | 用**新秘密**执行离线重锚（rekey）：重建 `lease-root.json`（新 `anchorId`、新 `bindingSha256`），并用新秘密重打 `leases/index.json` 的 `indexTag`，同时重打**全部存活记录**的 `anchorTag` | 全部标签与新秘密一致；无残留旧标签 |
| R3 | 以**新秘密**启动、以**无秘密**再启动各一次 | 前者正常；后者 **失败关闭** `CONTROL_ANCHOR_REQUIRED` |
| R4 | 故意用**旧秘密**启动一次 | **失败关闭** `CONTROL_ANCHOR_MISMATCH` |
| R5 | 启动后读取一条既有租约记录 | 校验通过（标签已重打）；**不得**出现"读得到旧记录但校验失败" |

**在途租约处理（明确定义，不留灰区）**
- 轮换采用 **"停机重锚"** 模型：**不允许**"在途租约跨越轮换"。理由：`anchorTag` 是记录内容的一部分，秘密一换、旧标签立刻失效；不存在"半程兼容"的安全做法。
- 因此轮换**必须**在维护窗口内完成，且窗口内 P5 根**不对外提供写服务**。
- 若未来确需"零停机轮换"，那是一项**新机制**（例如双秘密并存窗口＋按 `anchorId` 分流校验），**必须单独立项、单独授权**，本提案**不**包含。

**重锚的动作归属**
- 现有 `provision` 用 `CREATE_NEW`，**不能**用于已存在的 P5 根。因此 R2 需要**一个新的、显式的离线重锚入口**（等价于 `provision` 的 rekey 变体），或在运维流程中"人工重建根目录"。
- **建议**：新增显式 rekey 入口，而不是让人工删除/重建 P5 根——后者会丢失索引与记录，使 H3′ 的"记录缺失可检出"失去意义。
- 该入口属**产品代码改动**，需在 **B9 授权**范围内实施；本提案只定义其行为契约。

## 5. 建议的历史 keyring 保留期

**建议：不保留运行期历史 keyring；旧秘密只作"只读归档＋限期销毁"。**

| 项 | 建议 |
| --- | --- |
| 运行期 | **只持有当前秘密**。不做多秘密并存校验（那属于 §4 的"零停机轮换"新机制） |
| 归档 | 旧秘密移入**只读归档**（与运行配置分离），仅用于"轮换前既有记录"的事后取证/审计复核 |
| 保留期 | **建议 90 天**（与本地留存口径对齐），到期**销毁**并留销毁记录（时间、执行人、覆盖的一次性介质/文件哈希） |
| 到期后的既有记录 | 已重打标签的存活记录不受影响；**未**重打标签的历史副本在 90 天后**不可再校验**——这是**接受**的取证代价，必须在运维文档中写明 |
| 审计 | 每次轮换产生一条记录：时间、发起人、旧/新 `anchorId`（**只记身份，绝不记秘密**）、在途租约数（应为 0）、R3–R5 的实测结果 |

**为什么不留永久 keyring**：永久保留旧秘密会把"一次泄露"变成"永久可用"，且需要一套 keyring 版本选择逻辑（新的攻击面）。用"轮换时重打存活记录"替代 keyring，能用更小的机制面达到同一目的。

## 6. 可验收的完成标准（实施 B9 时逐条留证）

1. 缺秘密启动 ⇒ `CONTROL_ANCHOR_REQUIRED`（失败关闭，无半启动）。
2. 旧秘密启动 ⇒ `CONTROL_ANCHOR_MISMATCH`（失败关闭）。
3. 轮换后新秘密启动 ⇒ 正常；既有存活记录读取校验通过。
4. 轮换期间无在途租约（R1 证据）；轮换后索引与记录仍一致。
5. 秘密**不在** P3/P5/closedAuthority/restoreRoots 任何可写树内（用搜索/哈希证据证明）。
6. 轮换审计记录存在，且**不含**任何秘密明文。
7. 默认值不变：`effect-gate.enabled`/`cross-process-enabled`/`lease.enabled`/`admission.enabled` 全部 **false**。
