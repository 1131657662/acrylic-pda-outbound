## 1. A2.3 落地内容

剩余计划 A2.3 的完成标准："出站消息与交接命令同事务/可恢复，有反例"。实施如下：

| 文件 | 改动 |
| --- | --- |
| `handover/HandoverStore.java` | 新增 `nextOutboxEntityVersion(order,epoch)`（取该 order 在共享版本空间中的下一个空闲 `entity_version`）、`insertOutbox(...)`（`INSERT … SELECT` 从 `outbound_order` 取 `warehouse_id`）、`serverRecoveryEpoch()`（读 `server_state`）；并**修复 `advanceCase` 的 `prepared_ticket_sha256` 写入缺陷**（见 §3） |
| `handover/HandoverActivation.java` | `Activate.execute` 在 `advanceCase` 之后、**同一事务内**写一条 `HANDOVER_ACTIVATED` 出站通知，payload 含 `caseId`／`orderId`／`workRound`／`assignmentId`／`assignmentEpoch`／`targetDeviceId`／`targetUserId`／`activatedAt` |
| `server/src/test/.../E2aHandoverOutboxIT.java` | 新增：驱动真实命令链端到端并断言 outbox 行为（含反例） |

**语义选择（写进代码注释）**：**只有 ACTIVATE 产生出站通知**——它是交接链里唯一的**订单状态变更**（`ORDER_ASSIGNED` 一类），REQUEST/APPROVE/PREPARE 都是只读/案卷内决策，不发通知。这避免了用猜测的业务语义向 PDA 同步流广播无关事件。

**同事务与可恢复性**：`insertOutbox` 在命令自身事务内执行（`HandoverCommandService` 的 `TransactionTemplate`），因此"资格变更"与"出站通知"**要么都落、要么都不落**；提交后崩溃则行保持 `published_seq IS NULL`，**可被既有 outbox 读取方恢复**（与 R05/R06/R07-3 共用同一 `order_sync_outbox` 与版本空间，取下一个空闲 `entity_version` 以免与其它链冲突）。

## 2. 定向验证（真实 MySQL，服务层端到端）

`E2aHandoverOutboxIT`（run 751）：**1 项 / 0 失败 / 0 错误 / 0 跳过 / 13.5s**，`.local/e2a-cross-20260925-751/outbox.txt` 原文：

```text
verification level=service layer end-to-end REQUEST->APPROVE->PREPARE->ACTIVATE; HTTP/worker not verified
REQUEST -> case=01a0f066-aded-73da-993b-6efe6f63e920 outboxDelta=0
APPROVE -> status=APPROVED outboxDelta=0
PREPARE -> status=TARGET_PREPARED outboxDelta=0
ACTIVATE -> status=ACTIVATED outboxDelta=1
outbox -> event=HANDOVER_ACTIVATED version=1 published_seq=null case=01a0f066-aded-73da-993b-6efe6f63e920
ACTIVATE again -> HANDOVER_STATE_INVALID outboxDelta=1
```

断言要点：三个只读/案卷内步骤**零通知**；ACTIVATE **恰好一条**；该行 `event_type=HANDOVER_ACTIVATED`、`published_seq IS NULL`（**待发即可恢复**）、payload 的 `caseId`／`workRound=2`／`targetDeviceId` 逐值正确；`(epoch,order,version)` 唯一——**同版本只有一行**；**再激活被 `HANDOVER_STATE_INVALID` 拒绝且 outbox 不增长**（反例）。

**已知限制（如实记录，不含糊）**：**"outbox INSERT 之后再回滚"未能在本 harness 演示**。所有拒绝守卫都在 insert **之前**；insert 之后唯一的步骤 `advanceCase` 因 `handover_case_no_reopen` 等触发器**无法失败**；要人为制造撕裂就必须**删掉数据库守卫**——harness 不做这种事。因此"同事务/回滚"由**构造方式（单事务、insert 在状态变更之后）＋反例（被拒命令零通知）**支撑，**不由撕裂写入实验**支撑。

## 3. 第三处产品缺陷（本批发现并修复，与 S38 同类）

**现象**（run 747）：`PREPARE` 抛 `DataIntegrityViolationException: Data truncation: Data too long for column 'prepared_ticket_sha256' at row 1`。

**根因**：`V42__handover_case_model.sql:26` 定义 `prepared_ticket_sha256 BINARY(32) NULL`（**却是一个摘要列**），而 `HandoverStore.advanceCase` 由 `HandoverActivation.Prepare` 传入的是**票据原始字节**（`HandoverReceiptCodec.bytes(...)`，长度远超 32 字节）并直接写库 ⇒ 必然截断失败 ⇒ **PREPARE 从未能成功**（与 S38 的 `disabled_at` 同属"代码与 schema 不一致"类）。

**修复**（`HandoverStore.advanceCase`）：入库前统一 `preparedTicketSha256 = sha256(preparedTicket)`；`activationReceipt` 侧保持不变（调用方本就传 digest，且 `activation_sha256` 已是 BINARY(32)）。注释写明两个 `*_sha256` 列存**摘要**、从不存原件。

**验证**：修复后 run 751 的 `PREPARE -> status=TARGET_PREPARED` 通过。
