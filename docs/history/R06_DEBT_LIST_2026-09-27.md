## TEMP 归档第 4 步定位结果（只查不修）

### 1) `CommandReceiptIntegrity.closure(r, receipt)` 到底要求什么（`CommandReceiptIntegrity.java:85` 附近）
逐条读实，它要求**三组闭合证据全部成立**：
1. **命令事件行**（`store.event(id)`）与回执逐字段一致：同 `scope_id`；`event.id == receipt.eventId`；`decision_kind` 一致；
   `resulting_decision_version == receipt.originalContext.decisionVersion + 1`；**`event.context_bytes` 逐字节等于回执的无签名规范字节**；`recordedAt` 相同；
2. **审计行恰好一条**：`store.audits(id).size() == 1`（**恰好一条**，0 条或 2 条都判不通过）；
3. 该审计的 `event_type` 等于 `CommandDecision.eventType(receipt)`、`actor_id` 等于 principal，且 details 的
   `originalResponseSha256`/`commandSha256` 与命令记录一致。
失败即 `CommandErrors.corrupt(...)` → **409 `COMMAND_RECEIPT_INTEGRITY_FAILURE`**（`CommandErrors.java:24`，日志含 `COMMAND_RECEIPT_INTEGRITY_FAILURE detail=… where=…`，这正是 attempt 172 的失败来源）。

### 2) 两侧构造闭合凭据的差异：**没有差异**
- 内部 driver 路径（`TemporaryArchiveDriver:23-28`）与生产路径（本批新增的 `@Bean` + 分派接线）**构造的是同一个
  `TemporaryArchiveEvidence(files, submissions, jdbc, commands, integrity)`**；

- `TemporaryArchiveEvidence:28` 对两者都执行 `var command = command(head); var decision = integrity.verify(command);`
  —— 即**同一条闭合校验**。故"生产路径少做了一步"**不成立**。

### 3) 判定：**夹具缺闭合凭据（方向 A）**，不是生产缺陷
