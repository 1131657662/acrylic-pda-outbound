## 2. 锁：三层语义、按根可嵌套、固定层号顺序

| 层 | 载体 | 语义 |
| --- | --- | --- |
| L1 JVM 内引用 | `HELD`（键＝`writers.lock` 文件身份）＋`references`＋`poisoned`（`RecoveryWriterLease.java:11-33,51-63`） | 同 JVM/同文件身份只保留一个描述符；根持 1 引用，子操作借用加计数 |
| L2 跨进程共享租约 | `writers.lock` 首字节**共享** `FileLock`（`tryLock(0,1,true)`，`RecoveryWriterLease.java:39`）＋`writers.json`（`RecoveryWriterProtocol.java:11-28`） | 声明“本进程有在途写者”；多进程可同时持有，不是互斥锁 |
| L3 控制推进独占 | ①`coordinator.lock` 独占 `tryLock(0,1,false)`（`RecoveryControlLock.java:22-35`）；②控制推进/关闭意图工具对 `writers.lock` 同字节的独占尝试 | ①使权威读取/登记/离线登记/关闭意图发布互斥；②写者未排空时失败并保留耐久意图 |

### 2.1 接口与前置条件

| 接口 | 签名 | 前置条件（运行时强制） | 误用结果 |
| --- | --- | --- | --- |
| `RecoveryWriterLease.acquire` | `static RecoveryWriterLease acquire(Path root)` | **调用线程必须已持该根协调锁**（源码首行 `requireOwner`，`RecoveryWriterLease.java:18-19`，它不自己取锁） | 未持锁 → `CONTROL_COORDINATOR_REQUIRED` |
| 取锁包装 | 调用方负责 | `RecoveryAdmittedDataSource.acquire()`（`:69-81`）、`RecoveryLeasedTransaction.acquire()`（`:44-51`）均在 `RecoveryControlLock.locked(...)` 内调用 | — |
| `RecoveryControlLock.locked` | `static <T> T locked(Path root, Read<T> read)` | 立即失败语义不变 | 占用 → `CONTROL_COORDINATOR_BUSY` |
| `RecoveryControlLock.lockedWaiting`（新） | `static <T> T lockedWaiting(Path root, long timeoutMillis, Read<T> read)` | `1<=timeoutMillis<=10000`；同根不得重入；层号不得逆序 | `CONTROL_LOCK_TIMEOUT_RANGE`/`CONTROL_COORDINATOR_REENTRANT`/`CONTROL_LOCK_ORDER_VIOLATION`/`CONTROL_COORDINATOR_BUSY` |

### 2.2 按根可嵌套与层号

现状单 JVM 信号量＋单值 `ThreadLocal<Path> OWNER`（`RecoveryControlLock.java:11-12,17,28-30`）不允许同线程嵌套两个根；K1/K4 需要“P3 锁内取 P2 锁”，故：按根信号量、线程级根集合（深度计数）、层号 P3=1／P2=2／P5 进程文件=3（瞬时），逆序即 `CONTROL_LOCK_ORDER_VIOLATION`。既有的同根重入失败语义与 `RecoveryControlProcess` 的 nested/threaded 断言保持。

## 4. 接纳流程、效果门与原子性

### 4.1 接纳（K1/K4 修订）

```
admit(kind):
  S0 启动门 READY、!FATAL；P5 进程记录持锁；RecoveryAuthorityIdentity 一致      [启动期]
  S1 DB 证据：evidenceSource.evidence().initial()                                [受限只读；无协调锁]
  ---- P3 协调锁（层号1，有界等待）内 ----
  S2 P2 证据（层号2）：requireUnclosed(bound) → admissionSnapshot() → match(files, S1)
  S3 a current := RecoveryControlHistory.load(location, checkpoint, INITIAL_ADMISSION)
     b require startupIdentity.equals(currentIdentity)            -> CONTROL_INSTANCE_STALE
     c require current.installationId == 配置 == S2.installation
     d RecoveryInitialAuthority.validate(current, P1)             -> kind/单记录/绑定
     e RecoveryWriterProtocol.validate(root,true)；RecoveryLeaseRoots.verify(...)
     f RecoveryControlIntents.requireAdmission(root)              -> CONTROL_CLOSING_INTENT
     f' RecoveryInitialCloseIntent.requireAbsent(root)            -> CONTROL_CLOSING_INTENT
     g probe(leaseRoot)            # 前探针（逐记录，见 §5.4）
     h publishLeaseRecord(...)     -> RECOVERY_LEASE_UNRECORDABLE
     i writer := RecoveryWriterLease.acquire(root)
     j registry.registerRoot(...)
     k probe(leaseRoot)            # 后探针；若发现孤儿 → 退役 g/h 记录（失败即围栏）并拒绝
  ---- 释放 P3 锁 ----
  S4 绑定本次分派线程（§6.3）；返回根租约
```

**线性化点（接纳）＝S3-k 完成**；其可证明语义见 §5.4 引理。

### 4.2 效果门（K1 新增，第二个线性化点）

任何**已接纳根**的持久化效果必须先经过效果门：

- **实现点**：`RecoveryConnectionHandler.commit()`（`RecoveryConnectionHandler.java:40-58` 的 `commit` 分支）在调用 `delegate.commit()` **之前**，在 P3 协调锁内执行一次完整 `probe(leaseRoot)`；
  - 发现孤儿 ⇒ 抛出 `RECOVERY_LEASE_OUTSTANDING`（该事务必须回滚；连接被毒化按既有语义处理），根进入围栏序列（§5.5）；
  - 未发现 ⇒ 继续 `commit`。
- **覆盖范围**：业务事务提交、Spring Session 的 `commitSession()`（其写经由被接纳数据源与事务模板，最终走该 `commit`）都在门内。
- **自动提交写**：在已接纳根内，`autoCommit == true` 的**变更语句**默认拒绝（`CONTROL_AUTOCOMMIT_WRITE_FORBIDDEN`）；仅当根显式登记子操作 `AUTOCOMMIT_WRITE` 时允许（迫使实现阶段把所有此类调用点逐一列名，而不是默默绕过）。
- **代价与约束**：每次提交一次 P5 探针（若干文件锁探测），无 P3 之外的新锁；探针不写任何文件。

### 4.3 证据连接隔离（不变）

`RecoveryEvidenceSource` 只接受迁移专用原池，构造期拒绝准入源；`RecoveryReadOnlyDataSource` 强制只读、只允许单条 `SELECT`/`WITH`、拒绝 `unwrap`、不取任何租约与协调锁；静态白名单限定 `MIGRATION_DATASOURCE` 引用集合。

### 4.4 拒绝码

沿用前版并新增：`CONTROL_AUTOCOMMIT_WRITE_FORBIDDEN`、`RECOVERY_LEASE_FENCED`、`CONTROL_INITIAL_CLOSE_DUPLICATE`、`CONTROL_INITIAL_CLOSE_CONFLICT`、`CONTROL_AUTHORITY_KIND_FORBIDDEN`（purpose 不符）、`RECOVERY_OPERATION_REQUIRED`（主数据源无根）、`CONTROL_LOCK_ORDER_VIOLATION`。映射到 HTTP：关闭意图/孤儿/围栏/无根一律 503（`RECOVERY_CLOSING`/`RECOVERY_LEASE_OUTSTANDING`/`RECOVERY_LEASE_FENCED`/`RECOVERY_OPERATION_REQUIRED`）。

### 5.2 引理：孤儿可观测性的单调性

**引理**：若某进程 P 在某时刻 t 之后不再存活，则对任意 t' > t，探针读取 `processes/P.json` 的独占锁必然成功（即判为孤儿）。
**依据**：①进程身份每次启动随机生成、绝不复用；②独占锁由 OS 在进程终止时释放；③已死进程不可能重新获取该锁；④P5 记录只增不改、退役只删除租约记录而不改进程记录。⇒ “孤儿一旦可观测，永远可观测”，且不可被后来的存活掩盖。

**推论**：任何单次探针对某条记录返回“存活”，只能被**更晚**的死亡推翻；不存在“先判孤儿、之后又变存活”的反向错误。

### 5.3 探针的逐记录步骤与它真正能证明什么（撤回 v3 结论）

探针（在 P3 锁内执行）逐记录：

1. 读 `leases/<id>.json`（含 `.pending`）：不可解析 ⇒ **孤儿**（fail closed）；`.pending`（非本次临界区自身）⇒ 孤儿。
2. 取该记录的 `processIdentity`：本进程 ⇒ 跳过；进程记录缺失/不可解析 ⇒ 孤儿。
3. 对该进程记录尝试独占 `tryLock`：失败（他人持有）⇒ **此刻判为存活**；成功 ⇒ 孤儿（取得后立即释放）。
4. 全部记录处理完毕后返回“无孤儿”。

**能够证明的**：在探针执行期间，若某条记录的属主在**其被处理时刻**已死，则该次探针判为孤儿。**不能证明的（v3 的错误）**：探针返回成功**不等于**“探针结束时刻不存在孤儿”——属主可能在“其被处理之后、探针结束之前”死亡（K1 的具体反例）。因此 **v3“线性化点＝后探针完成 ⇒ 扫描完成时无孤儿”的结论已撤回**。

### 5.4 K1 的修订保证（以效果门为线性化点）

定义两个判定点：**D1＝接纳后探针（S3-k）**、**D2＝每次持久化效果前的效果门（§4.2）**。保证表述为：

- **G1（接纳起点）**：若某孤儿在 D1 的相应记录处理时刻已可观测，则接纳被拒（或立刻撤销并围栏）。
- **G2（效果）**：任何已接纳根的持久化效果，都在 D2 处（P3 锁内）检查过孤儿；若在其可观测，则该效果**不得发生**（回滚＋围栏）。由 §5.2 单调性，D2 之前观测到的任何孤儿都不会消失。
- **G3（可证明的边界，明确陈述）**：若死亡发生在 D2 之后、该效果完成之前，则该效果与故障**并发**。任何基于文件锁/协调锁的协议都无法排除与在途提交并发的故障——这是环境属性，不是本设计的缺口。该类的**影响被界定**为：恰好这些已过判定点的效果；其后所有 D2 都会看到孤儿并拒绝，且所有新根被拒（G1）。设计不把这一类标为“已关闭”，而是标为**固有并发边界**（见[v4 定向复验](R09_C2_G0_V4_REVERIFY_2026-09-28.md)）。
- **不再依赖“再加一轮扫描”**：D2 使保证落在“效果”而非“扫描”，故扫描窗口不构成正确性依据。

### 5.5 围栏序列 `FENCED`（K1：取代“halt 失败仍全局阻断”）

触发：任何 UNKNOWN、效果门发现孤儿、退役决策期失败、身份/租约根不可信。步骤按序执行，每步都是**本地必然可执行且他人可观测**的：

| 步 | 动作 | 他人可观测性 |
| --- | --- | --- |
| F1 | 本进程置 FENCED：拒绝新根、新子操作、新借连接；已开始的连接工作只能收尾或回滚 | 仅本进程 |
| F2 | 尽力写 `leases/<id>.unknown.json`（审计；成败不影响后续步骤） | 可选 |
| F3 | **释放进程记录锁**（关闭其 `FileChannel`） | **所有其他进程的下一次探针**：其进程记录存在但锁可取得 ⇒ 该进程的全部租约判为孤儿 ⇒ 拒绝新根/效果 |
| F4 | 不释放 L2 写者引用（保留 `writers.lock` 共享锁），以同时阻止 L3-② 控制推进完成 | 控制推进继续失败并保留耐久意图 |
| F5 | `Runtime.halt(70)` 终止 JVM | OS 最终释放全部锁 |

- **若 F5 无法执行**：F1＋F3 已生效 ⇒ 其他进程在各自下一次探针处拒绝；本进程既不能接纳也不能借连接。**v3 中“halt 失败时租约仍在所以别人仍拒绝”的说法已撤回**——状态表明确允许“仍持进程锁的其他进程租约”为在途、不阻断；真正使他人阻断的是 **F3 的锁释放**。
- **若 F3 无法执行**（理论上不成立，通道已打开）：重试 F3；仍失败则直接 F5（halt 由 OS 释放锁）。两条路径都指向“他人可见的锁状态改变”。
- **同/跨 JVM 影响**：F5 终止整个 JVM ⇒ **同进程**所有在途操作一并终止且不退役（其结果未知，其租约因 F3 已释放进程锁而对他进程呈孤儿）；**其他进程**的在途操作可以完成其收尾，但任何新的持久化效果都会被效果门拒绝（G2）。

### 5.6 退役协议与终端语义（K1 尾部补正）

| 阶段 | 步骤 | 失败处置 |
| --- | --- | --- |
| **决策期** | ①根进入 `RELEASING`（禁新子操作）②全部子租约关闭、连接报告已确认终态（无毒化）③事务提交/回滚已确认、Session 保存已提交或已回滚 ④删除 `leases/<id>.json` 并**读回确认不存在** | 任一步出现**未确认结果** ⇒ **不删除**并执行围栏序列（F1–F5） |
| **决策后期** | ⑤释放 L1 引用 ⑥释放 L2 写者锁/关闭通道 | 由构造，此时**不存在未确认结果**、租约已退役；失败**不构成 UNKNOWN**：重试一次 → 仍失败则记录日志、把该 `Held` 置毒化（本 JVM 永不再接纳）、置 FENCED（不再开新工作），但**不需要跨进程阻断**（没有未退役租约可发布）。若进程随后死亡，OS 释放 L2，仍无孤儿遗留 |

**不变式（据此给出终端语义）**：*存活进程不存在“已结束但未退役”的租约*；决策后期失败只会留下一个**多余的 L2 写者锁**（仅延迟控制推进），不会留下未退役租约，也不会产生跨进程阻断需求。v3 中“任一步失败都不删除记录”的笼统表述已由本表取代。

### 5.7 R2 继承结论（不变）

`authorityKind` 校验在权威加载唯一入口（`purpose` 必填）＋`authorityKind × consumer` 允许表；初次权威不能被恢复链消费者加载，恢复权威不能被初次接纳门加载；就地替换身份由 `startupIdentity.equals(currentIdentity)` 捕获；真实关闭权威创建/切换必须在 P3 锁内且无在途租约（B9）。v2 的“模式变更必先完成独占控制推进”证明保持撤回状态，`RecoveryClosedProjection.register()` 同形接受 rev1/QUIESCING 且只持共享租约的事实（`RecoveryClosedProjection.java:47-48`、`RecoveryProjectionRows.java:45-65`、`RecoveryLeasedTransaction.java:44-51`）仍是该撤回的依据。

## 6. 根/子操作、绑定与请求生命周期

### 6.1 令牌与根租约

```java
public enum RecoveryOperationKind { HTTP_REQUEST, WORKER_JOB, FILE_WRITE, RENDER_PROCESS, INITIALIZATION }
public enum RecoverySubOperation { CONNECTION, TRANSACTION, SESSION_WRITE, EVIDENCE_READ, PROCESS_HANDOFF, AUTOCOMMIT_WRITE }
public enum RecoveryOperationPhase { SERVING, FINALIZING, RELEASING, RELEASED, FENCED }
public final class RecoveryOperationToken { /* operationId, kind, installationId, authorityRecordSha256, requestSha256 */ }
public final class RecoveryOperationLease implements AutoCloseable {
    public RecoveryOperationToken token(); public RecoveryOperationPhase phase();
    public void enterFinalizing(); public void enterReleasing();
    public RecoverySubLease registerSubOperation(RecoverySubOperation kind);
    public void bindDispatch(Thread thread);   // 深度计数 +1；本次分派专用
    public void unbindDispatch(Thread thread); // 深度计数 -1；归零即解绑
    public void close();                       // §5.6 退役协议
}
```

### 6.2 调用方判定（显式隔离旧连接层，保持 v3 结论）

主数据源（`@Primary`，`RecoveryRequestAdmittedDataSource`）：①线程绑定有效且根存活 → 借用并登记 `CONNECTION`；②有请求根但线程未绑定 → `RECOVERY_OPERATION_CONTEXT_LOST`；③**无线程绑定且无任何根标识 → `RECOVERY_OPERATION_REQUIRED`（拒绝，不回退）**；④令牌失效 → `CONTROL_OPERATION_RELEASED`；⑤越集子操作 → `CONTROL_SUBOPERATION_FORBIDDEN`；⑥根处于 FENCED → `RECOVERY_LEASE_FENCED`。旧连接层（`RecoveryAdmittedDataSource`，非 `@Primary`）仅测试/离线工具可用，静态白名单强制。

### 6.3 K2：根生命周期与**每次分派的线程绑定**分离

- **根生命周期**：接纳过滤器创建根 → 保留至 `requestDestroyed`（容器保证的最后边界），与“本分派是否结束”无关。
- **分派绑定**：过滤器进入本次分派时 `bindDispatch(当前线程)`；该次分派结束（`finally`）时**无条件** `unbindDispatch(当前线程)`——**不再以 `!isAsyncStarted()` 为条件**（v3 的错误：异步初始分派返回时把 A 的有效根留给可能被复用的容器线程）。
- **嵌套 ERROR 分派**：同一线程上的嵌套分派使深度 +1/−1，外层作用域不被提前清除；`doFilterNestedErrorDispatch` 路径同样成对增加/减少。
- **异步**：初始分派返回即解绑；异步工作线程未绑定 ⇒ 其连接借用按 §6.2-③ 拒绝（fail closed）；容器发起 ASYNC 分派时过滤器再次进入并绑定**该分派**的线程。
- **清理**：`requestDestroyed` 清除该根的全部绑定（防御性，覆盖异常路径）；根退役前确认绑定深度为 0。
- **新增规格（K2）**：请求 A 开启异步且**尚未结束**，其原容器线程被复用于请求 B ⇒ 断言：B 只能使用 B 自己的根；该线程上任何落在 A 的异步窗口内、且不属于任何分派作用域的借用被拒（不得继承 A）；A 的异步分派进入时只绑定 A 的该次分派。

### 6.4 关闭后规则

新根禁止（`RECOVERY_CLOSING`）；已接纳根的后继借用（含最终 Session 保存、错误分派提交）允许；令牌单次、根在 `requestDestroyed` 退役、未绑定线程拒绝、子操作白名单；已接纳根的**新持久化效果**须过效果门。

## 7. UNKNOWN 与多进程

触发点沿用 `RecoveryConnectionHandler.poison(...)` 与 `RecoveryTransactionLease.close()`。行为：F1 置 FENCED → F2 尽力写审计记录 → F3 释放进程记录锁 → F4 保留 L2 → F5 halt（§5.5）。阻断依据在故障前建立（P5 租约＋进程锁），且**跨进程阻断的实际成立条件**是“他人探针时该进程的进程记录锁可取得”（由 F3 或进程死亡保证），不依赖 halt、不依赖故障时写入成功。排空判据仍为合取（无本实例事务／`liveRoots==0` 且子操作 0／无本进程 L2 持有／无渲染子进程／无未入 DB 引用的暂存活动／P3 无 `.pending`／P5 无孤儿与未退役租约）；B1 不实现排空声明，不新增解除端点（解除属生产释放，未授权）。
