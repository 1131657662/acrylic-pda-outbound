## 2. 锁：三层语义、按根可嵌套、固定层号顺序

| 层 | 载体 | 语义 |
| --- | --- | --- |
| L1 JVM 内引用 | `HELD`（键＝`writers.lock` 文件身份）＋`references`＋`poisoned`（`RecoveryWriterLease.java:11-33,51-63`） | 同 JVM/同文件身份只保留一个描述符；根持 1 引用，子操作借用加计数 |
| L2 跨进程共享租约 | `writers.lock` 首字节**共享** `FileLock`（`tryLock(0,1,true)`，`RecoveryWriterLease.java:39`）＋`writers.json` 身份（`RecoveryWriterProtocol.java:11-28`） | 声明“本进程有在途写者”；**多进程可同时持有**，不是互斥锁 |
| L3 控制推进独占 | ①`coordinator.lock` 独占 `tryLock(0,1,false)`（`RecoveryControlLock.java:22-35`）；②控制推进对 `writers.lock` 同字节的独占尝试（`control_store.py:49`） | ①使权威读取/登记/离线登记互斥；②使控制推进在写者未排空时失败并保留耐久意图 |

### 2.1 接口与前置条件（v2 的错误已修正）

| 接口 | 签名 | 前置条件（运行时强制） | 误用结果 |

### 2.2 按根可嵌套（R1 的实现前提）

现状 `RecoveryControlLock` 用**单一 JVM 信号量**（`LOCAL = new Semaphore(1)`，`:11,17`）与单值 `ThreadLocal<Path> OWNER`（`:12,28-30`），因此同一线程无法嵌套两个不同根（P3 内再取 P2 会 `CONTROL_COORDINATOR_BUSY`）。R1 需要把 S2 移进 P3 临界区并在其中取 P2 锁，故定案：

- 信号量改为**按根**（每根一个 JVM 内互斥，保持“同 JVM/同根唯一描述符”的既有目的）；OWNER 改为**按线程的根集合/栈**，`requireOwner(root)` 判定集合成员。
- 引入固定**层号**：P3 协调锁＝1、P2 协调锁＝2、P5 进程文件锁（瞬时）＝3；`lockedWaiting` 记录线程当前最大层号，请求更低层号即 `CONTROL_LOCK_ORDER_VIOLATION`。
- 锁序只允许 **P3 → P2 → P5（瞬时取用后立即释放）**；禁止反向，且由层号校验在运行时强制。
- 既有断言不变：`locked` 的立即失败语义、`RecoveryControlProcess` 的 nested/threaded 用例（同根重入仍是 `CONTROL_COORDINATOR_BUSY` 或新码，二选一在实现时以既有断言为准并保持其失败语义）。

### 3.2 P3 `identity.json` formatVersion 2（B01 + R4 扩展）

```json
{ "formatVersion": 2, "authorityKind": "INITIAL_NORMAL_INSTALL",
  "installationId": "<uuid>", "restoreRoots": ["<abs>", "..."],
  "closedAuthority": "<abs>", "leaseRoot": "<abs>", "initialCommandSha256": "<64hex>" }
```

- `authorityKind ∈ {INITIAL_NORMAL_INSTALL, RECOVERY}`：供给时点确定、不可变。
- `closedAuthority`：真实关闭权威路径（绝对）。
- `leaseRoot`（R4 新增）：**唯一 P5 根**。运行期配置必须与之逐字相等，否则拒绝（`RECOVERY_LEASE_ROOT_UNBOUND`）；这使“相同 P3／不同 P5”不再可能（除非替换信任身份，见 §5.4 的检测）。
- Java：`RecoveryControlFormat.version()` 按文件类型区分（identity 接受 1/2，其余仍只接受 1）；v1 identity 不得用于初次接纳（`CONTROL_INITIAL_AUTHORITY_KIND_REQUIRED`）。

### 3.3 P2 允许名与“正常 vs UNKNOWN 拒绝文件”

`InitialNormalStore.layout()`（`:95-102`）精确允许 7 个名字，语义分三类：

| 名字 | 类别 | 语义 |
| --- | --- | --- |
| `coordinator.lock` | 正常/必备 | 1 字节锁文件；缺失或非 1 字节 → `CONTROL_LOCK_INVALID`/`CONTROL_WRITER_LOCK_INVALID` 类错误 |
| `initial-normal-request.json`(+`.pending`) | 正常 | 已发布/正在发布的初次请求；`.pending` 存在 → `INITIAL_NORMAL_INCOMPLETE`（**拒绝**） |
| `initial-normal-committed.json`(+`.pending`) | 正常 | 完成证明；仅在数据库提交并读回一致后发布；`.pending` 存在 → 拒绝 |
| `initial-normal-unknown.json`(+`.pending`) | **UNKNOWN 拒绝文件** | 出现即**永久拒绝**（`INITIAL_NORMAL_UNKNOWN`），不自动清除、不重试；它出现在允许集里是为了给出精确诊断，而不是允许接纳 |

### 3.5 “供给 → 登记 → 核验 → 首次接纳”四步（含 R1 的互斥）

| 步 | 输入 | 守卫 | 唯一结果 |
| --- | --- | --- | --- |
| 供给 P3/P5 | 身份、restoreRoots、`closedAuthority`、`leaseRoot`、P1 | 绝对/非链接/本地固定盘；互不重叠；`closedAuthority` 父目录存在且条目不存在；`authorityKind=INITIAL_NORMAL_INSTALL`；P5 目录空且由供给建立 `lease-root.json` | v2 identity + 锁文件 + `writers.json`(v2) + 单条绑定 P1 的 QUIESCING 引导记录 + 空 `intents/` + `admission.json`(1,ZERO_HASH) + P5 标记；否则拒绝且不落盘 |

### 4.1 接纳流程（S2 移入 P3 临界区）

```
admit(kind) -> RecoveryOperationLease
  S0 启动门 READY、!FATAL；P5 进程记录已建立且持锁；leaseRoot 身份校验通过        [启动期]
  S1 数据库侧证据：evidenceSource.evidence().initial()                            [受限只读；无协调锁]
  ---- 以下全部在 P3 协调锁（层号1，有界等待）内 ----
  S2 文件侧证据（P2 锁，层号2）：
       requireUnclosed(boundClosedAuthority) → 父目录存在/条目不存在
       admissionSnapshot(): committed、无 UNKNOWN/无 .pending、installation 一致
       InitialNormalVerification.match(files, S1)
  S3 控制权威与登记：
       a current := RecoveryControlHistory.load(location, checkpoint, INITIAL_ADMISSION)
       b require startup.equals(current)                        -> CONTROL_INSTANCE_STALE
       c require current.installationId == 配置 == S2.installation
       d RecoveryInitialAuthority.validate(current, P1)          -> kind/单记录/绑定
       e RecoveryWriterProtocol.validate(root, true)             -> 协议 v2
       f RecoveryControlIntents.requireAdmission(root)           -> CONTROL_CLOSING_INTENT
       g leaseProbe(root=leaseRoot)  # 前探针：无孤儿                  -> RECOVERY_LEASE_OUTSTANDING
       h publishLeaseRecord(leaseRoot, operationId)              -> RECOVERY_LEASE_UNRECORDABLE
       i writer := RecoveryWriterLease.acquire(root)             [L1 命中或新开]
       j registry.registerRoot(...)
       k leaseProbe(root)  # 后探针：仍无孤儿；若发现孤儿 → 退役 g/h 记录（失败即 halt）并拒绝
  ---- 释放 P3 锁 ----
  S4 绑定当前线程；测试探针；返回根租约
```

- **线性化点**：接纳＝后探针（S3-k）成功完成；离线登记＝在其 P3 临界区内发布完成/UNKNOWN 记录。
- **共同互斥**：接纳（S2+S3）与离线登记（其全部步骤）都在**同一把 P3 协调锁**内 ⇒ 二者不可能交错。这直接关闭“接纳完成 S2 → 登记者看到 P5 为空 → 登记发布 UNKNOWN → 接纳进入 S3 并登记根”的时序：登记要么在接纳之前完成（接纳随后 S2 读到 UNKNOWN 并拒绝），要么在接纳之后（登记随后看到在途租约并 `INITIAL_NORMAL_APPLICATION_ACTIVE`）。
- 锁内只做文件读、P5 记录发布、内存登记与一次瞬时 P5 存活探针（无 DB I/O、无业务写、无用户代码）；DB 证据（S1）在锁外。
- **失败恢复**：登记中途死亡 → `.pending` 或 UNKNOWN 遗留 → 接纳拒绝；接纳在 h 与 k 之间死亡 → 该租约的属主进程记录锁被 OS 释放 → 后续接纳判为孤儿并拒绝。

### 4.2 证据连接隔离（不变）

`RecoveryEvidenceSource` 只接受迁移专用原池，构造期拒绝 `RecoveryAdmittedDataSource`（`CONTROL_EVIDENCE_SOURCE_FORBIDDEN`）；内部 `RecoveryReadOnlyDataSource` 强制 `setReadOnly(true)`、只允许单条 `SELECT`/`WITH`、拒绝 `unwrap`、不取任何租约与协调锁；静态白名单测试限定 `MIGRATION_DATASOURCE` 引用集合 = {`RecoveryAdmissionConfiguration`, `RecoveryEvidenceSource`}。

### 4.3 拒绝码

沿用 v1/v2 并新增/修正：`RECOVERY_INITIAL_AUTHORITY_REQUIRED`、`RECOVERY_INITIAL_AUTHORITY_INVALID`、`RECOVERY_CLOSED_BINDING_UNTRUSTED`、`RECOVERY_LEASE_OUTSTANDING`、`RECOVERY_LEASE_UNRECORDABLE`、`RECOVERY_LEASE_ROOT_UNBOUND`、`RECOVERY_OPERATION_CONTEXT_LOST`、`RECOVERY_OPERATION_REQUIRED`（主数据源无根）、`CONTROL_LOCK_ORDER_VIOLATION`、`CONTROL_SESSION_CLEANUP_UNCOVERED`（启动失败）、`CONTROL_AUTHORITY_KIND_FORBIDDEN`（purpose 不符）。

## 5. 证明（R1/R2/R4 重写）

### 5.1 事实表

| --- | --- | --- | --- | --- |
| P3 意图/历史/锚点 | 控制推进（Python） | **P3 协调锁**（`control_store.py:40`） | revision/hash/意图变化 | S3-a/b/f（同临界区） |

### 5.2 R1：离线登记与首次接纳的互斥（关闭 S2→S3 交错）

1. 接纳的 S2 与 S3 **都在 P3 协调锁内**；离线登记的全部步骤（P2 读、DB 事务、P5 无在途检查、完成/UNKNOWN 发布）**也在同一把 P3 协调锁内**（写侧改造，见 §3.6 第 11 项）。
2. P3 协调锁是 `coordinator.lock` 上的**独占** OS 锁（`RecoveryControlLock.java:22-35`），跨进程互斥。
3. ⇒ 接纳与登记是全序的：**登记在前** → 它必然已发布完成或 UNKNOWN；接纳随后在 S2 读到 UNKNOWN（拒绝）或读到完成（继续，且此时 P5 已无在途租约，登记与任何后续接纳不再交错）。**接纳在前** → 它已在 S3-h 发布租约；登记随后在锁内检查 P5 非空 → `INITIAL_NORMAL_APPLICATION_ACTIVE`（拒绝）。
4. 因此不再使用“检查目录为空”作为互斥替代；“P5 为空”只作为**锁内的一致性证据**，不是同步原语。
5. 线性化点：接纳＝S3-k；登记＝完成/UNKNOWN 发布。两者在同一锁内，故不存在“双方都遵守协议却被交错”的情形——v2 之所以被反例推翻，正是因为它让双方分别持不同锁（P2 vs P3）。

### 5.3 R2：`authorityKind` 的消费者边界与模式变更重证

**v2 结论撤回**：`RecoveryClosedProjection.register()` 在数据库绑定为空时接受 `revision=1 / QUIESCING / previousRecordSha256=ZERO_HASH`（`RecoveryClosedProjection.java:47-48`），并写入 `recovery_installation_binding`＋epoch 映射＋投影，同时把 `server_state` 置 `RECOVERY_PENDING`（`RecoveryProjectionRows.java:45-65`）；其事务只持**共享**写者租约（`RecoveryLeasedTransaction.java:44-51` → `RecoveryWriterLease.java:39`）。因此 v2 “模式变更必须先完成独占控制推进”**不是现存调用链的事实**。

**唯一入口强制（R2 修订）**：所有权威读取都经 `RecoveryControlHistory.load(location, checkpoint, purpose)`（Python 同构 `control_history.load(location, trusted, purpose)`），`purpose` 为**必填**参数：

| consumer | purpose | 允许的 `authorityKind` |
| --- | --- | --- |
| 接纳门（本设计新组件） | `INITIAL_ADMISSION` | 仅 `INITIAL_NORMAL_INSTALL` |
| 离线初次登记（`InitialNormalRegistration`、`InitialNormalStore`） | `OFFLINE_REGISTRATION` | 仅 `INITIAL_NORMAL_INSTALL` |
| `RecoveryClosedProjection`、`RecoveryNormalRegistration`、`RecoveryProjectionRows/History` | `RECOVERY_CHAIN` | 仅 `RECOVERY` |
| `RecoveryLeasedTransaction`、`RecoveryControlReader`、`RecoveryAdmissionVerifier.of(...)`、`RecoveryAdmissionVerifier.verify()` | `RECOVERY_CHAIN`（构造/调用必填） | 仅 `RECOVERY` |
| Python `control_store.inspect/apply`、`control_intents`、`control_writers` | `RECOVERY_CHAIN` | 仅 `RECOVERY`（对 `INITIAL` 权威一律 `CONTROL_AUTHORITY_KIND_FORBIDDEN`） |
| Python 初次供给（`control_initial.py`） | `OFFLINE_REGISTRATION` | 仅 `INITIAL_NORMAL_INSTALL`，且只允许一次性供给 |

凡不符即 `CONTROL_AUTHORITY_KIND_FORBIDDEN`（在事务/租约之前拒绝）。

**模式变更与框架写的重证（三段式，替换 v2 第三段）**：
1. 同一权威身份上，`INITIAL_NORMAL_INSTALL` 与恢复链消费**互斥**（上表 + 唯一入口）：初次权威不能被投影消费 ⇒ 初次权威上不可能出现 `RECOVERY_PENDING` 之类模式变更。
2. 初次接纳要求 `authorityKind=INITIAL` 且 P4 `recovery_installation_binding` **无行**（`INITIAL_NORMAL_CLOSED_HISTORY`）⇒ 只要恢复链已登记过投影，初次接纳即永久失效；反之，初次权威期间恢复链无法消费。
3. 从 `INITIAL` 切换到 `RECOVERY` 需要**另一套权威身份**（不同 `identity.json`）与配置变更＋重启；重启后初次接纳被拒、旧进程随之结束，故不存在“同身份、同时接纳与投影”。
4. 附加检测：接纳每次重读身份并与启动快照比对（`startup.equals(current)`）⇒ 就地替换身份文件被 `CONTROL_INSTANCE_STALE` 捕获；真实关闭权威条目的出现使 S2 直接拒绝（`INITIAL_NORMAL_CLOSED_AUTHORITY`）。
5. 真实关闭权威的**创建/切换**同样受共同约束：必须在 P3 协调锁内、且无在途租约（§3.6 第 24 项，B9 实施；本轮只冻结规则）。
6. 残余（显式）：授权操作者直接改文件/改库不在威胁模型内（与项目对 `server_state` 的既有口径一致）。框架写（Session 保存/错误分派提交）在请求根内、由 §6.3 的租约覆盖；其模式约束由本条 1–4 提供，而不再依赖 v2 的独占推进论证。

### 5.4 R4：P5 身份、状态与失败协议

**身份绑定**：`leaseRoot` 同时出现在 P3 identity v2 与 `<leaseRoot>/lease-root.json`（`{formatVersion, installationId, authorityRoot, leaseRoot, bindingSha256}`）；启动与每次接纳要求三者一致，否则 `RECOVERY_LEASE_ROOT_UNBOUND`。⇒ “相同 P3／不同 P5”“空目录替换”都在配置/身份层被拒；同一安装的所有进程被强制使用同一 P5。

**状态与失败表**（每项都能由状态转换与强制点推出）：

| 观测 | 判定 | 结果 |
| --- | --- | --- |
| `leases/<id>.json` 存在，属主进程记录缺失 | 孤儿（无法证明存活） | 拒绝 `RECOVERY_LEASE_OUTSTANDING` |
| 属主进程记录存在但不可解析 | 孤儿（fail closed） | 拒绝 |
| 属主进程记录存在且其独占锁**可被取得** | 属主已死 → 孤儿 | 拒绝 |
| 属主进程锁被**其他存活进程**持有 | 在途操作（正常并发） | 不阻断 |
| 本进程自己的在途租约 | 跳过 | 不阻断 |
| `leases/*.pending`（非本次临界区自身正在发布的） | 发布未完成 → 孤儿 | 拒绝 |
| 租约记录不可解析 | 孤儿（fail closed） | 拒绝 |
| `lease-root.json` 缺失/不匹配 | 配置/身份错误 | 启动失败或 `RECOVERY_LEASE_ROOT_UNBOUND` |
| **退役删除失败（本进程仍存活）** | **不得留待“下次判孤儿”**（v2 说法被推翻：扫描会跳过本进程记录、并把存活进程的记录视为在途） | 立即进入 quarantined：本进程拒绝所有新根并 **halt**；其租约随即成为其他进程可见的孤儿 |
| 退役后校验未确认（文件是否真的不存在无法确认） | 同上 | 同上 |

**退役协议**（顺序固定，避免先删唯一阻断依据）：
1. 根进入 `RELEASING`：不得再登记子操作；
2. 全部子租约关闭；所有连接处理器报告已确认终态（无毒化）；
3. 事务提交/回滚已确认；Session 保存已提交或已回滚；
4. 删除 `leases/<operationId>.json` 并**读回确认不存在**；
5. 任一步出现未确认结果 ⇒ 不删除、进入 quarantined 并 halt；
6. 删除确认后，才释放 L1 引用（L2 写者锁最后释放）。
⇒ 不变式：**存活进程不存在“已结束但未退役”的租约**；无法退役 ⇒ 该进程停止存在，租约变为孤儿。

**扫描→死亡交错的线性化边界**：接纳在登记前后各做一次存活探针（S3-g / S3-k）。若某进程在 S3-g 之后、S3-k 之前死亡，S3-k 会发现孤儿 ⇒ 立刻退役刚建的记录（失败即 halt）并拒绝，业务写尚未开始。若死亡发生在 S3-k 之后，则属**接纳后故障**，该操作按“已接纳操作收尾”处理（允许），其租约在退役时若无法确认则 halt。⇒ 边界＝S3-k 完成，无需“OS 释放锁也要拿 P3 锁”这一不成立的前提。

**`halt` 的作用域（明确）**：`Runtime.halt(70)` 终止**整个 JVM** ⇒ **同进程**所有在途操作一并终止且不退役（其结果未知，其租约成为孤儿，方向保守）；**其他进程**的在途操作可以继续完成收尾，但不能开始新根；所有进程与新进程此后拒绝。设计**不主张**“同进程未涉 UNKNOWN 的操作仍能收尾”。

**明确残余**：①授权操作者的文件系统/数据库直接改写不在威胁模型内；②`halt` 在理论上无法执行的极端情形退化为“租约记录仍在 ⇒ 仍拒绝”，方向不变。

### 6.2 R3：显式隔离的旧连接层（取消“上下文缺席＝权限”）

**数据结构**（admission 启用时）：

| Bean | 类型 | 语义 | 使用者 |
| --- | --- | --- | --- |
| 主数据源（`@Primary`） | `RecoveryRequestAdmittedDataSource`（新） | **每个 `getConnection()` 必须能解析到本线程的有效根**；解析失败（无根/失效令牌/无绑定）一律拒绝，**永不回退** | 请求路径、Spring Session、业务 JdbcTemplate |
| 旧连接层（显式命名，非 `@Primary`） | `RecoveryAdmittedDataSource`（既有，语义逐字节保留） | 连接级租约（协调锁＋`requireAdmission`＋L1）；**不要求根** | 105 回归、隔离测试、离线/运维工具 |

- 判定表（主数据源）：①线程绑定有效且根存活 → 借用并登记 `CONNECTION` 子操作；②线程无绑定但**本请求存在根令牌**（上下文丢失）→ 拒绝 `RECOVERY_OPERATION_CONTEXT_LOST`；③既无线程绑定、也无任何根标识 → **拒绝** `RECOVERY_OPERATION_REQUIRED`（这正是 R3 的修正：缺席不再是权限）；④`operationId` 存在但根已释放/身份不符 → 拒绝 `CONTROL_OPERATION_RELEASED`；⑤子操作类型越集 → `CONTROL_SUBOPERATION_FORBIDDEN`。
- 旧连接层不可从请求路径到达：静态测试断言生产请求路径包（`com.acrylic.outbound.*` 除 `recovery` 与显式白名单）不注入/不按名获取该 bean；其使用集合冻结为 {测试源, 离线工具, `RecoveryAdmissionConfiguration` 定义处}。
- 需要无根 DB 访问的合法非请求路径必须使用**显式能力**：迁移原池（Flyway）、初始化能力（`BootstrapAdmin`）、只读证据代理、启动提示（只读且失败可容忍）；B1 实施清单逐项列出这些调用点（§9 第 20 行）。
- **绑定生命周期**：接纳过滤器在进入时 `bindThread(当前线程)`；其 `finally` 在 `!request.isAsyncStarted()` 时 `unbindThread`（防止容器线程复用后残留）；`requestDestroyed` 清除该根的全部绑定；根退役前必须确认无绑定残留。
- 四个必备负例：①有请求上下文、无线程绑定 → `RECOVERY_OPERATION_CONTEXT_LOST`；②线程绑定与请求上下文**都不存在**（异步生产者线程）→ `RECOVERY_OPERATION_REQUIRED`；③已释放令牌 → `CONTROL_OPERATION_RELEASED`；④同一容器线程复用后（前一个请求已完成）→ 再次借用被拒（证明绑定已清理）。四者均**零业务写**。

### 6.3 请求生命周期（按实际依赖，R5 修正断言）

依赖证据见[残余阻断复验](R09_C2_G0_RESIDUAL_BLOCKERS_2026-09-28.md) §2：`SessionRepositoryFilter` 继承 Spring Session 自有 `OncePerRequestFilter`，`DEFAULT_ORDER=-2147483598`，`commitSession()` 在 `doFilterInternal` 体内（链后与异常路径），覆写 `doFilterNestedErrorDispatch`；Spring Web 的 `OncePerRequestFilter` 默认跳过 ERROR/ASYNC（`shouldNotFilter*` 均返回 true）⇒ 我们的过滤器**显式覆写为 false**（v1/v2 均已如此说明）；Boot 注册会话过滤器时使用 `SessionProperties.Servlet.filterOrder`（默认 `-2147483598`）与 `filterDispatcherTypes`（默认 `{ASYNC, ERROR, REQUEST}`）。

1. `RequestIdFilter`（`@Order(HIGHEST_PRECEDENCE)`）写 `requestId`。
2. `RecoveryRequestAdmissionFilter`（`@Order(Ordered.HIGHEST_PRECEDENCE + 10)`，普通 Servlet 过滤器，不入 `SecurityFilterChain`，两个 `shouldNotFilter*` 覆写为 false）：请求属性中已有本过滤器写的根令牌 → **复用**该根并 `bindThread(当前线程)`；否则执行 §4.1 接纳。
3. 业务链（含 `SessionRepositoryFilter` 的 `commitSession()` 与其嵌套 ERROR 提交）在根存活期内运行；**最终 Session 保存就发生在该过滤器体内**，属该根的子操作。
4. 过滤器 `finally`：`enterFinalizing()`；若 `!isAsyncStarted()` 则 `unbindThread`（不释放根）。
5. `RecoveryRequestRootListener.requestDestroyed()`：`enterReleasing()` → 退役协议（§5.4）→ 释放根。这是容器保证的“所有分派结束之后”的唯一边界；ERROR/ASYNC 在新线程时由第 2 步复用分支补绑定。
6. ASYNC：Spring Session 过滤器在异步分派会再次执行 `doFilterInternal`（根仍存活）；异步工作线程若未绑定，其连接借用按 §6.2-②/③ 拒绝（fail closed）。
7. 异常退出：链异常同样走第 4/5 步；连接毒化按 §7 处理。

### 6.4 关闭后规则

新根禁止（`RECOVERY_CLOSING`，任何业务写之前）；已接纳根的后继连接借用（含最终 Session 保存、事务收尾、错误分派提交）允许；令牌单次、根在 `requestDestroyed` 退役、`operationId` 不复用、未绑定线程拒绝、子操作白名单；Worker/文件/渲染的新任务禁止启动（各自批次规则收尾）。

## 7. UNKNOWN 与多进程（R4 已并入 §5.4，此处只列行为）

触发点沿用 `RecoveryConnectionHandler.poison(...)` 与 `RecoveryTransactionLease.close()`。UNKNOWN 行为：置位 L1 毒化 → **尽力**写 `leases/<id>.unknown.json`（审计，成败不影响阻断）→ 不退役租约 → **halt**（§5.4）。阻断依据在故障前已建立（P5 租约 + 进程锁），孤儿判定不依赖时间、不依赖故障时写入成功。排空判据仍为合取（无本实例事务 / `liveRoots==0` 且子操作 0 / 无本进程 L2 持有 / 无渲染子进程 / 无未入 DB 引用的暂存活动 / P3 无 `.pending` / P5 无孤儿与未退役租约）；B1 不实现排空声明，不新增解除端点（解除属生产释放，未授权）。
