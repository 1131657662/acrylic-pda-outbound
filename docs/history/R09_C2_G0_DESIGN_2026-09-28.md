## 2. 术语纠正：三类锁，不再混称“写者独占锁”

原提案与历史文字把 `writers.lock` 笼统称为“写者独占锁”，不准确。定稿按三层分别定义（源码坐标：`RecoveryWriterLease.java:18-45,51-61`、`RecoveryControlLock.java:16-39`、`docs/parallel/R09/CLOSING_INTENT.md`）：

| 层 | 载体 | 语义 | 谁能同时持有 |
| --- | --- | --- | --- |
| L1 JVM 内引用 | 进程内 `HELD`（按 `writers.lock` 文件身份为键）＋`references` 计数＋`poisoned` | 同一 JVM/同一文件身份只保留一个描述符，避免第二次 `close` 掉 POSIX 锁；一个根操作持 1 个引用，子操作借用使计数增加 | 同 JVM 内任意多个根/子操作共享同一 `Held` |
| L2 跨进程共享租约 | `writers.lock` 首字节上的**共享** `FileLock`（`tryLock(0,1,true)`，`RecoveryWriterLease.java:39`） | 声明“本进程有在途写者”。多个进程**可以同时**持有；`writers.json` 仅记录锁文件身份与安装身份，用于发现锁文件被替换 | 多个进程可同时持有（不是互斥） |
| L3 控制推进独占锁 | ①`coordinator.lock` 上的**独占** `FileLock`（`tryLock(0,1,false)`）＋JVM 信号量＋`ThreadLocal` OWNER；②控制推进（Python `ControlStore.apply`）对 `writers.lock` 同字节的**独占**尝试（`control_writers.exclusive`） | ①使“读权威＋登记租约”与“追加控制命令”在同一时刻只有一个执行者；②使控制推进能在写者未排空时失败并保留耐久意图 | 各自同一时刻唯一 |

因此“关闭意图后仍能启动新写者”不是缺陷，而是 L2 共享语义的必然：拒绝新写者的机制是 **L3-②失败后保留的耐久意图**（`admission.json` 已推进、`current.json` 未推进），Java 侧由 `RecoveryControlIntents.requireAdmission` 拒绝（`targetRevision > revision` → `CONTROL_CLOSING_INTENT`）。B1 的关闭竞争测试正是驱动这一链路（§9.2）。

### 3.3 初次 NORMAL 与租约的合法衔接（定案）

1. **准入只承认独立初次路径**：接纳必须调用 `RecoveryAdmissionVerifier.verifyInitial(...)` 语义的双侧证据（文件侧 P2 + 数据库侧 P4），**禁止**用 `RecoveryAdmissionVerifier.verify()` 的 `RELEASE_READY` 投影、`recovery_installation_binding`、`recovery_control_projection` 或 `normal-admission.json` 作为接纳依据。理由：`verify()` 面向关闭链终态，用它接纳等于用 `RELEASE_READY` 绕过独立初次登记要求。
2. **接纳对 P2 严格只读**：接纳路径不得写入 P2 任何文件（`InitialNormalStore.prepare/completeLocked/unknownLocked` 均不在接纳调用链上）；B1 测试以目录树哈希前后比对断言零写入。
3. **登记责任只在显式离线协调器**：只有 `InitialNormalRegistration.register()`（经 `RecoveryNormalRegistration.registerInitial`）可以在 P4 写 `recovery_initial_normal` 并把 `server_state` 置回 `NORMAL`（`RecoveryNormalRegistration.java:9-20`、`RecoveryRows`）。它**不是** Spring bean、无路由、不在启动时运行、**不取写者租约**（用传入的初始化能力连接）。应用进程不得在启动或首次请求时自动登记。
4. **初始化能力与业务能力分离**（定案）：`InitialNormalRegistration`、Flyway、`BootstrapAdmin` 使用**初始化能力**（迁移专用原池，`RecoveryAdmissionConfiguration.MIGRATION_DATASOURCE`），且该能力只允许在启动阶段由显式许可触发；业务入口必须使用准入数据源。二者不得互相借用。
5. **不得伪造恢复历史**：接纳要求关闭链缺席（§3.2 第 5 行），且不得为通过接纳而生成 `history/`、`intents/`、`admission.json` 之外的任何控制记录；P3 的既有记录只读。
6. **不新增初次原件目录文件**：`writers.poison.json` 落在 P3，不落 P2；P2 允许集代码级冻结（§8 中 `InitialNormalStore` 只增只读方法，不改 `layout` 允许集）。

## 4. 接纳原子性与证据连接隔离

### 4.1 接纳流程（三步，锁内/锁外明确）

```
admit(kind) -> RecoveryOperationLease
  S0  启动门：state==READY && !fatal                                  [无锁，内存]
  S1  证据（数据库侧）：evidenceSource.evidence().initial()            [受限只读连接；无协调锁]
        -> 非 null；service_mode==NORMAL；closedHistory==false；recovery_initial_normal 行在场
  S2  证据（文件侧）：store.admissionSnapshot()                        [P2 协调锁，仅文件读，随即释放]
        -> committed==true；无 UNKNOWN/无 .pending；installation 与配置一致
        -> InitialNormalVerification.match(files, S1) 逐项相等
  S3  控制权威 CAS —— 全程在 P3 协调锁内（有界等待，§4.4）：
        a current := RecoveryControlHistory.load(location, checkpoint)
        b require startup.equals(current)                  -> CONTROL_INSTANCE_STALE
        c require current.installationId == 配置 == S2.installation
                                                           -> CONTROL_INSTALLATION_MISMATCH
        d require RecoveryWriterProtocol.validate(root, true)
                                                           -> CONTROL_ADMISSION_PROTOCOL_REQUIRED
        e require RecoveryWriterPoison.absent(root)         -> CONTROL_WRITER_POISONED/_UNCONFIRMED
        f require RecoveryControlIntents.requireAdmission   -> CONTROL_CLOSING_INTENT/_INTENT_INCOMPLETE
        g writer := RecoveryWriterLease.acquireLocked(root)  [L1 命中或新开；references++]
        h registry.registerRoot(kind, writer, {installation, recordSha256, requestSha256})
     <--- 线性化点：h
  S4  绑定当前线程到根；测试探针钩子；返回根租约
```

**锁内/锁外职责**：锁内只做文件读 + 内存登记（无 DB I/O，无业务写，无用户代码）；DB 证据读（S1）在锁外，用受限只读能力；P2 读取（S2）用 P2 自己的协调锁且**不与 P3 锁嵌套**（顺序执行，无交叉持锁）。

### 4.2 为什么不存在“检查后窗口”（不以窗口小为理由）

1. **意图与登记互斥**：控制推进（Python `ControlStore.apply`，`control_store.py:38-53`）与接纳步骤 S3 都必须在 P3 的**同一独占协调锁**内执行。因此“读意图”与“登记根租约”之间不可能插入任何控制推进——两者是同一临界区的两半。
2. **权威变化由 CAS 捕获**：S3-b 重读权威并与构造期快照比对，任何控制推进都会改变 `revision`/`recordSha256`，从而在登记前失败。
3. **证据侧不引入新窗口**：S1/S2 的证据由不可变对象构成——P1 原件字节、P2 完成文件、P4 的 `recovery_initial_normal` 行（既有 update/delete 守卫在 C1 已验）与 `server_state` 模式。`server_state` 的后续变化由既有写入守卫在每次业务写时再次判定（`ServerState.lockCurrentWritable`/`requireWritable`，`ServerState.java:17-40`），不依赖接纳时的快照。
4. **接纳之后不再撤销**：登记完成后权威若继续推进（关闭意图落盘），该操作已属“已接纳”，按 §5.4 允许收尾；此时控制推进的 L3-② 独占尝试必然失败并保留耐久意图，正是对外语义“拒绝新操作、等最后写者退出”。

因此正确性来自 1–2 的互斥与 CAS，不来自时间窗口大小。`lockedWaiting` 的有界等待只影响可用性（并发接纳的排队），不影响上述判定。

### 4.3 证据连接隔离（受限只读能力）

新增 `RecoveryEvidenceSource`：

- 构造参数是**迁移专用原池**（`@Qualifier(RecoveryAdmissionConfiguration.MIGRATION_DATASOURCE)`）；构造时若发现传入的是 `RecoveryAdmittedDataSource`（或其包装），立即抛 `CONTROL_EVIDENCE_SOURCE_FORBIDDEN`（配置期失败，不进入运行）。
- 对外只暴露 `RecoveryAdmissionEvidence evidence()`，**不暴露** `DataSource`、`JdbcTemplate` 或连接；内部把原池包成 `RecoveryReadOnlyDataSource`：
  - 每个连接 `setReadOnly(true)`；
  - 语句规范化后必须是单条 `SELECT`/`WITH`，否则抛 `CONTROL_EVIDENCE_WRITE_FORBIDDEN`；
  - `unwrap`/`isWrapperFor` 对非代理类型一律拒绝；
  - 不参与任何租约（不取 L1/L2/L3），也不调用协调锁。
- 防扩散强制点（B1 测试，`RecoveryEvidenceIsolationTest`）：静态扫描 `server/src/main/java` 中对 `MIGRATION_DATASOURCE`/`recoveryMigrationDataSource` 的引用，允许集合在 B1 冻结为 {`RecoveryAdmissionConfiguration`（定义迁移池并注入 `RecoveryEvidenceSource`），`RecoveryEvidenceSource`}；出现第三处即测试失败。
- 禁止递归的强制点：`RecoveryEvidenceSource` 构造拒绝准入源；`RecoveryReadOnlyDataSource` 永不含准入逻辑；接纳路径不得调用 `RecoveryAdmittedDataSource.getConnection()`/`admit(...)`（`RecoveryAdmissionPathIsolationTest` 静态扫描接纳组件的方法引用）。

### 4.4 锁内专用接口与防误用

| 接口 | 签名 | 前置条件（运行时强制） | 误用结果 |
| --- | --- | --- | --- |
| `RecoveryControlLock.lockedWaiting` | `static <T> T lockedWaiting(Path root, long timeoutMillis, Read<T> read) throws IOException` | `timeoutMillis` ∈ [1, 10000]；同一线程不得已在协调锁内 | 越界抛 `CONTROL_LOCK_TIMEOUT_RANGE`；重入抛 `CONTROL_COORDINATOR_BUSY`（JVM 信号量 `tryAcquire(timeout)` 失败） |
| `RecoveryWriterLease.acquireLocked` | `static RecoveryWriterLease acquireLocked(Path root) throws IOException` | `RecoveryControlLock.requireOwner(root)` 通过（即调用线程正持该根协调锁） | 未持锁抛 `CONTROL_COORDINATOR_REQUIRED`；协议/毒化不满足抛既有码 |
| 现有 `RecoveryWriterLease.acquire` | 不变 | 自行取协调锁并执行 `requireAdmission` | 语义与 105 连接层回归保持完全一致 |
| 现有 `RecoveryControlLock.locked` | 不变（立即失败语义） | — | 既有断言（含 `RecoveryControlProcess` 的 nested/threaded 用例）继续成立 |

`lockedWaiting` 的等待策略：JVM 信号量 `tryAcquire(timeout)`；文件锁以 10 ms 步进在剩余预算内重试 `tryLock`；预算耗尽抛 `CONTROL_COORDINATOR_BUSY`（接纳映射为可重试拒绝）。B1 测试同时覆盖“等待后成功”和“超时失败”两个方向。

### 4.5 拒绝码与 HTTP 映射（定案）

写出口为 `ApiResponses.writeWithoutState(request, response, BusinessException)`：**不读数据库**（`ApiResponses.body` 现会 `state.current()`，在拒绝路径上会再次借连接，必须绕开），响应体沿用既有 `ApiEnvelope` 形状，`epoch=null`、`mode="UNAVAILABLE"`。

| 触发 | envelope code | HTTP | 说明 |
| --- | --- | --- | --- |
| 启动门未就绪（启动中/迁移/初始化许可未完成） | `RECOVERY_STARTUP_INCOMPLETE` | 503 | §7.1 |
| 持久毒化记录在场/不完整 | `RECOVERY_WRITER_UNKNOWN` / `RECOVERY_WRITER_UNKNOWN_UNCONFIRMED` | 503 | §6 |
| 待决关闭意图 | `RECOVERY_CLOSING` | 503 | 新根拒绝 |
| 协调锁有界等待耗尽 | `RECOVERY_ADMISSION_BUSY` | 503 + `Retry-After: 1` | 可重试 |
| 权威/身份失配或不可用 | `RECOVERY_AUTHORITY_STALE` | 503 | `CONTROL_INSTANCE_STALE`/`_AUTHORITY_CHANGED`/`_UNAVAILABLE`/`_INSTALLATION_MISMATCH` |
| 双侧证据缺失或不一致 | `RECOVERY_EVIDENCE_MISSING` | 503 | `INITIAL_NORMAL_*` |
| 令牌失效/线程未登记/子操作类型不允许 | `RECOVERY_OPERATION_FORBIDDEN` | 503 | §5 |
| 接纳内部异常（未归类） | `RECOVERY_ADMISSION_FAILED` | 503 | 不泄漏内部细节 |

既有 `SERVER_RECOVERY_REQUIRED`（503，`ServerState.java:36-37`）继续用于业务写时的模式判定，含义不变。

## 5. 根操作、子操作与关闭后收尾

### 5.1 操作令牌与根租约（接口契约）

```java
public enum RecoveryOperationKind { HTTP_REQUEST, WORKER_JOB, FILE_WRITE, RENDER_PROCESS, INITIALIZATION }
public enum RecoverySubOperation { CONNECTION, TRANSACTION, SESSION_WRITE, EVIDENCE_READ, PROCESS_HANDOFF }
public enum RecoveryOperationPhase { SERVING, FINALIZING, RELEASED }

public final class RecoveryOperationToken {           // 不可变值对象；构造器包可见
    public UUID operationId();
    public RecoveryOperationKind kind();
    public UUID installationId();                     // 身份绑定
    public String authorityRecordSha256();            // 接纳时的 P3 链头
    public String requestSha256();                    // 接纳时的 P2 原件摘要
}

public final class RecoveryOperationLease implements AutoCloseable {
    public RecoveryOperationToken token();
    public RecoveryOperationPhase phase();
    public void enterFinalizing();                    // SERVING->FINALIZING；幂等；RELEASED 抛 CONTROL_OPERATION_RELEASED
    public RecoverySubLease registerSubOperation(RecoverySubOperation kind); // 见 5.2
    public void bindThread(Thread thread);            // 显式跨线程传播；RELEASED 抛 CONTROL_OPERATION_RELEASED
    public void close();                              // 最终释放；幂等；不抛异常
}

public final class RecoverySubLease implements AutoCloseable {
    public RecoverySubOperation kind();
    public void close();                              // 计数减一；幂等
}
```

**权限约束**：令牌只能由 `RecoveryOperationRegistry` 在接纳线性化点内铸造；构造函数包可见，令牌不可序列化、不写入任何 HTTP 报文/日志正文、不作为请求参数；令牌**不是**授权凭据——授权来自注册表中“根仍存活 + 身份绑定一致 + 调用线程已绑定 + 子操作类型在允许集内”。

### 5.2 子操作登记、引用计数与跨线程传播

- 根租约持 `RecoveryWriterLease` 的 1 个引用（L1 `references`）。`registerSubOperation` 使该引用计数再 +1 并记录子租约；`RecoverySubLease.close()` 使计数 −1。根 `close()` 释放自身引用；引用归零才真正释放文件锁（既有 `RecoveryWriterLease` 行为）。
- 允许集（B1 冻结）：`HTTP_REQUEST → {CONNECTION, TRANSACTION}`；`INITIALIZATION → {}`（初始化不使用租约）；`WORKER_JOB/FILE_WRITE/RENDER_PROCESS` 的集合在 B6–B8 前不得被使用。越集抛 `CONTROL_SUBOPERATION_FORBIDDEN`。
- 线程绑定：根创建时绑定接纳线程；`bindThread` 可显式追加（供后续批次移交子进程/工作线程）。未绑定线程尝试 `registerSubOperation` → `CONTROL_OPERATION_THREAD_FORBIDDEN`（**fail closed**，不静默放行）。
- 适配层：`RecoveryOperationRegistry` 用 `ThreadLocal<UUID>`（仅存 `operationId`）+ `Map<UUID, Root>` 完成“当前线程属于哪个根”的**查找**。它是查找适配，不是授权：`operationId` 失效即查不到根；根状态、身份绑定、类型白名单都在注册表内判定。释放时清除该根的所有线程绑定。
- 子操作登记是幂等可审的：注册表对外提供 `liveRoots()`、`liveSubOperations(operationId)`、`rejectionCount()`（B1 仅测试使用，无生产端点）。

### 5.3 HTTP 生命周期（含最终 Session 保存）

1. `RequestIdFilter`（`@Order(HIGHEST_PRECEDENCE)`，`common/RequestIdFilter.java:14-24`）先运行，写入 `requestId`。
2. `RecoveryRequestAdmissionFilter`（新，`@Order(Ordered.HIGHEST_PRECEDENCE + 10)`，注册为普通 Servlet 过滤器，**不放进 SecurityFilterChain**，以免 `permitAll` 的 CSRF/登录端点绕过接纳）执行 §4.1 接纳，把令牌写入请求属性，并 `bindThread(当前线程)`。
3. 过滤器顺序必须落在 Spring Session 的 `SessionRepositoryFilter` 之前（其顺序值晚于 `HIGHEST_PRECEDENCE + 10`；具体数值在 B1 冒烟中以容器注册顺序实测断言，见 §9.1），使租约覆盖到 `SessionRepositoryFilter` 退出前的最终保存。
4. 业务链返回后，过滤器在 `finally` 内 `enterFinalizing()`（幂等），**不释放租约**。
5. `RecoveryRequestRootListener`（新，`ServletRequestListener`）在 `requestDestroyed` 中释放根租约——这是容器保证的“所有分派（REQUEST/ERROR/ASYNC）结束之后”的唯一边界，因此最终 Session 保存在任何分派下都被覆盖。
6. `shouldNotFilterErrorDispatch()` 与 `shouldNotFilterAsyncDispatch()` 均返回 `false`：ERROR/ASYNC 分派走同一过滤器链而不被静默跳过；由于 `OncePerRequestFilter` 的已过滤属性，过滤器体不会重复执行，根仍存活（由第 5 步释放）。ASYNC 若在未绑定线程上产生 DB 访问，则在借连接处 `CONTROL_OPERATION_THREAD_FORBIDDEN` 拒绝（fail closed），而不是无保护放行。

### 5.4 关闭后规则（允许/禁止清单）

| 类别 | 关闭意图落盘后 | 依据 |
| --- | --- | --- |
| 新根操作（新 HTTP 请求、新任务、新文件操作） | **禁止**，`RECOVERY_CLOSING` 503，且在任何业务写之前 | S3-f |
| 已接纳根在后继连接借用（含最终 Session 保存、事务提交/回滚） | **允许** | 根存活，不再重查意图（§4.2-4） |
| 已接纳根开展“无关新业务” | **禁止**：令牌不可跨请求复用（根在 `requestDestroyed` 释放、注册表条目删除、`operationId` 唯一不复用）；未绑定线程一律拒绝；子操作类型白名单 | §5.2 |
| 已接纳根启动无关新任务/新文件写/子进程 | **禁止**（B1 无此类调用方；类型白名单使其在 B6–B8 也必须显式声明） | §5.2 |
| 框架写入（Session 保存、错误响应中的 Session 写、multipart 暂存） | 属于已接纳根的收尾，**允许**（且仅在已接纳根内） | §5.3 |

### 5.5 Worker/文件/渲染规则（设计定稿，不进 B1）

- Worker：根租约 = 一次 `runOnce`（claim→handler→complete/fail）全程；`BackgroundJobLeases.renew` 的 `REQUIRES_NEW` 以子操作借用同一根，不新建根。关闭意图下：不开始新 claim；已 claim 的作业按 §5.4 收尾（含失败登记）。
- 文件入口：根租约 = 一次“先落文件后落库”的完整动作；未入 DB 引用的临时文件必须在同一根内完成或登记为 UNKNOWN。
- 渲染子进程：根租约 = 启动前到进程树退出确认；`ExportRendererProcess` 的定时 `renew` 属于该根的收尾子操作。跨进程/跨平台证据另列。

## 6. UNKNOWN 与多进程语义

### 6.1 触发点（沿用既有判定，不新增“成功即安全”的路径）

`RecoveryConnectionHandler` 的 `poison(...)`（提交/回滚/关闭/`setAutoCommit`/`abort`/连接类 SQLState `08` 失败）与 `RecoveryTransactionLease.close()` 的未确认完成（`RecoveryTransactionLease.java:31-38`）。这些既有判定不变。

### 6.2 两层毒化与影响矩阵（定案）

| 层 | 状态载体 | 作用域 | 何时设置 | 何时清除 |
| --- | --- | --- | --- | --- |
| A 进程内 | L1 `Held.poisoned`（既有） | 本 JVM/本文件身份 | 立即 | **从不清除**；进程退出即消失（因此单靠 A 不足以跨进程） |
| B 耐久 | P3 `writers.poison.json`(+`.pending`)（新） | 所有进程、所有重启 | UNKNOWN 被判定后立即尝试发布 | **应用不得清除**；只有 §6.4 定义的外部授权流程可处理，本轮不实现 |

| 对象 | 出现 UNKNOWN 后 |
| --- | --- |
| 同 JVM 新根操作 | 拒绝：L1 `CONTROL_WRITERS_ACTIVE`；若耐久记录已落盘则 `RECOVERY_WRITER_UNKNOWN` |
| 其他进程新根操作 | 拒绝：接纳 S3-e 读到耐久记录 |
| 存量操作（同 JVM） | 不强制中止：可完成当前连接工作与其收尾；其 `close()` 不会清除毒化（`RecoveryWriterLease.java:55` 已保证），也不会释放文件锁 |
| 存量操作（其他进程） | 不受影响（各自 L1 独立），但若它们发起新根则被拒绝 |
| 新进程启动（准入启用） | **启动失败**：`RecoveryAdmittedDataSource` 构造期先读耐久记录，存在即抛 `CONTROL_WRITER_POISONED`/`_UNCONFIRMED`，上下文不启动，端口不提供服务（生产默认关闭准入时不适用，但那时也无准入面） |
| 控制推进 | 因毒化进程不释放 L2 共享锁，`exclusive` 尝试失败 → 保留耐久意图；即“等最后写者退出”无法自动达成，必须 §6.4 外部流程 |

**耐久记录不得被“一次 `INNODB_TRX=0` 或锁已释放”替代**：排空是合取声明（§6.5）。

### 6.3 耐久记录格式与发布协议

`writers.poison.json`（canonical JSON，`RecoveryControlJson` 规则）：

```
formatVersion=1, installationId, operationId, kind, causeCode, authorityRevision, recordSha256,
detectedAt, evidenceSha256, poisonSha256(自哈希，计算时剔除自身)
```

- 发布用 `RecoveryControlDisk.publish(root, name, bytes, codes)`：先 `CREATE_NEW` 写 `name.pending` + `force`，再原子改名到 `name`（Windows `MoveFileExW` + `WRITE_THROUGH`，不覆盖已存在目标；POSIX `ATOMIC_MOVE`），最后 `force` 目标并同步目录。该算法从 `InitialNormalDisk.publish` 提取（`InitialNormalDisk.java:29-75`），`InitialNormalDisk` 改为委托并**保持其错误码与可观察行为不变**（既有 `InitialNormalStoreTest` 为回归）。
- 只读语义：`.pending` 在场视为“未确认毒化”（`CONTROL_WRITER_POISON_UNCONFIRMED`），目标在场视为“已确认毒化”（`CONTROL_WRITER_POISONED`）；二者与目标冲突时以“已确认”优先但仍然拒绝。
- 幂等：重复发布同一记录必须内容相同（`same()` 比对），不同内容抛 `CONTROL_WRITER_POISON_CONFLICT`。文件不可变，应用不得删除或改写。

### 6.4 写入失败与记录不完整（分支定案）

| 分支 | 磁盘状态 | 进程行为（定案） | 其他进程/重启 |
| --- | --- | --- | --- |
| 发布成功 | 目标在场 | 事务标记未确认；不释放 L2；继续按 §6.2 拒绝新根 | 全部拒绝，重启亦拒绝 |
| 改名失败/进程在 `pending` 后死亡 | `.pending` 在场 | 启动期检查把 `.pending` 视为未确认毒化 → 拒绝 | 全部拒绝 |
| 写 `pending` 失败（磁盘满/权限） | **无任何标记** | in-process L1 立即置位（拒绝新根）；当前操作的连接不释放、不报成功；**fail-stop**：置 `RecoveryStartupGate` 为 FATAL（所有后续借用/接纳拒绝），并由非请求线程执行 `SpringApplication.exit(context, () -> 1)`，避免继续服务 | **残余缺口**：无耐久标记，新进程无法自动得知 → 必须由运维按“外部强制隔离”（停机 + 控制权威隔离）处理；本设计不新增解除端点，也不自动清除 |
| 记录存在但内容损坏/安装不符/自哈希不符 | 文件在场 | 视为未确认毒化（拒绝），不尝试修复、不覆盖 | 拒绝 |

**不得新增**：解除端点、自动清除、自动重试排空、生产释放权限。耐久记录的清除（若将来需要）属生产释放能力，须独立授权与独立证据；本轮仅登记该边界。

### 6.5 排空判据（合取，不得单条宣布）

“已排空”只有在下列全部成立时才可声明，并须留下逐项原始证据：①`INNODB_TRX` 无本实例事务；②注册表 `liveRoots()==0` 且 `liveSubOperations==0`；③本实例 L2 共享锁已释放（`HELD` 为空且 `writers.lock` 上无本进程锁）；④无渲染子进程/子进程树已退出确认；⑤无“未入 DB 引用”的暂存文件活动；⑥P3 无 `.pending` 遗留（包括毒化与意图）；⑦耐久毒化记录不在场或已被授权流程处理。B1 **不实现**排空声明，只实现拒绝与记录。

### 6.6 协议改动清单

见 §3.5 第 1、2 条（Java 允许集 + Python 双侧语义）。B1 的 Python 侧改动必须与 Java 同批、同证据链，且 Python 侧测试（`docs/parallel/R09/tests/test_control_intents.py`、`test_control_writers.py` 一类）保持绿或按新语义扩展。

## 7. 启动与框架边界

### 7.1 强制顺序与竞争结果

顺序固定为：**显式许可 → 迁移 → 初始化 → 业务入口**。

| 阶段 | 强制点 | 失败行为 |
| --- | --- | --- |
| 0 进程启动 | `RecoveryAdmittedDataSource` 构造：读 P3 权威、`writers.json` 协议 v2、身份绑定、耐久毒化记录 | 任一不满足 → 上下文启动失败（不降级为无保护连接池） |
| 1 迁移许可 | 仅当 `OUTBOUND_MIGRATE=true` 才跑 Flyway；使用迁移专用原池 | 许可缺失 → 不迁移；库结构缺失时后续接纳失败拒绝，绝不自动建表/自动登记 |
| 2 初始化许可 | 仅当 `outbound.bootstrap.enabled=true` 才跑 `BootstrapAdmin`；连接来源改为**初始化能力**（§3.5 第 10 条） | 许可缺失 → 不初始化；空身份库下业务写被既有守卫与接纳拒绝 |
| 3 业务入口 | `RecoveryStartupGate` 在 (1)(2) 阶段结束且权威/身份/毒化检查通过后置 `READY`；未 READY 期间所有请求 503 `RECOVERY_STARTUP_INCOMPLETE` | 启动异常 → 进程退出，不进入 READY |

竞争结果表：

| 竞争 | 结果 |
| --- | --- |
| 两进程同时持迁移许可 | Flyway 自身锁（`flyway_schema_history` + DDL 锁）串行化；失败方因迁移异常**启动失败退出**，不提供服务 |
| 无迁移许可进程 vs 未迁移库 | 每次请求接纳失败 → 503；不建表、不登记、不自动 NORMAL |
| 迁移进行中 + 业务进程已监听 | 业务进程 READY 前一律 503（第 3 阶段门），迁移完成后仍需接纳证据通过 |
| 两进程同时初始化（Bootstrap） | DB 侧 `app_user` 唯一约束与空库校验串行化；失败方 `CommandLineRunner` 抛异常 → 启动失败退出；事务回滚，无半套用户/授权 |
| 业务进程 + 关闭意图待决 | 启动可成功（权威可读），但每个请求 503 `RECOVERY_CLOSING`；不因重启恢复允许态 |
| 业务进程 + 耐久毒化在场 | 启动失败（阶段 0），端口不提供服务 |

### 7.2 B1 隔离测试前提

B1 一律使用**预置非空库**，应用 `OUTBOUND_MIGRATE=false`、`outbound.bootstrap.enabled=false`；P2/P3 由供给步骤预置（§3.4）；数据库、账号、端口、storage 根逐轮独立，不复用旧 attempt 目录；执行前按 §12 全量查重。测试期间的关闭意图由独立控制工具写入（§9.2），不由产品代码提供入口。

### 7.3 框架边界逐项

| 路径 | 批次 | 测试条件 | 隔离方式 | 冻结结论 |
| --- | --- | --- | --- | --- |
| Session 最终保存 | B1 | 真实 HTTP + 非空 MySQL；屏障卡在 SERVING→FINALIZING 后的首次借用 | 专用库/schema/账号 | 纳入：由请求级根租约覆盖至 `requestDestroyed` |
