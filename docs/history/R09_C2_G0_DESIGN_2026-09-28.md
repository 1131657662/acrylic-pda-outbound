## 2. 锁的准确语义（三层，接口描述已纠正）

| 层 | 载体 | 语义（依据） | 并存者 |
| --- | --- | --- | --- |
| L1 JVM 内引用 | 进程内 `HELD`（键＝`writers.lock` 文件身份）＋`references`＋`poisoned`（`RecoveryWriterLease.java:11-33,51-63`） | 同 JVM/同文件身份只保留一个描述符，防止第二次 `close` 掉 POSIX 锁；根持 1 引用，子操作借用加计数 | 同 JVM 任意多根/子操作共享同一 `Held` |
| L2 跨进程共享租约 | `writers.lock` 首字节**共享** `FileLock`（`tryLock(0,1,true)`，`RecoveryWriterLease.java:39`）；`writers.json` 记录锁文件身份与安装身份（`RecoveryWriterProtocol.java:11-28`） | 声明“本进程有在途写者”；**可被多个进程同时持有**，不是互斥锁 | 多个进程 |
| L3 控制推进独占 | ①`coordinator.lock` 独占 `tryLock(0,1,false)`＋JVM 信号量＋`ThreadLocal` OWNER（`RecoveryControlLock.java:11-39`）；②控制推进对 `writers.lock` 同字节的独占尝试（`control_store.py:49`、`control_writers.exclusive`） | ①使“读权威＋登记租约”与“追加控制命令”互斥；②使控制推进在写者未排空时失败并保留耐久意图（`control_admission.py:14-31`） | 各自唯一 |

**接口纠正与前置条件**（v1 表述已修正）：

| 接口 | 签名 | 前置条件（运行时强制） | 误用结果 |
| --- | --- | --- | --- |
| `RecoveryControlLock.locked` | `static <T> T locked(Path root, Read<T> read)` | 无（立即失败语义，保持不变） | 已被占用 → `CONTROL_COORDINATOR_BUSY` |
| `RecoveryControlLock.lockedWaiting`（新） | `static <T> T lockedWaiting(Path root, long timeoutMillis, Read<T> read)` | `1 <= timeoutMillis <= 10000`；调用线程不在任何协调临界区内 | 越界 `CONTROL_LOCK_TIMEOUT_RANGE`；重入/占用超时 `CONTROL_COORDINATOR_BUSY` |
| `RecoveryWriterLease.acquire` | `static RecoveryWriterLease acquire(Path root)` | 不变（自取协调锁→协议 v2→`requireAdmission`→L1 命中或 open） | 语义与 105 回归完全一致 |
| `RecoveryWriterLease.acquireLocked`（新） | `static RecoveryWriterLease acquireLocked(Path root)` | 调用线程已持该根协调锁（内部再调 `RecoveryControlLock.requireOwner(root)` 强制） | 未持锁 → `CONTROL_COORDINATOR_REQUIRED`；协议/准入不满足 → 既有码 |

## 3. 身份、权威、目录布局与“初次租约权威”的合法闭合（B01）

### 3.1 五个持久面

| P3 控制权威根 | `outbound.recovery.root` | `identity.json`(v2)、`coordinator.lock`、`current.json`、`history/`、`writers.json`、`writers.lock`、`intents/`、`admission.json`、`normal-admission.json` | 与 P2/P1/restoreRoots/P5 不重叠 |
| P4 数据库 | `OUTBOUND_DB_*` | `server_state`、`recovery_initial_normal`、`recovery_installation_binding`、`recovery_normal_admission`、`recovery_control_projection` | B1 不改 schema |
| **P5 操作租约目录（新）** | `outbound.recovery.lease-root` | `processes/<processIdentity>.json`（＋进程生命周期独占锁）、`leases/<operationId>.json`(+`.pending`)、`leases/<operationId>.unknown.json`(+`.pending`) | 必须与 P1/P2/P3/restoreRoots/checkpoint 不重叠（复用 `RecoveryControlPaths.overlap` 语义） |

P5 取代 v1 中“P3 内新增 `writers.poison.json`”的方案：**P3 允许集不变**，因此 `RecoveryControlHistory.layout` 与 Python `control_history.layout` 都不需要为毒化记录改动（B05 的协议面因此缩小）。

### 3.2 P3 `identity.json` 升级到 formatVersion 2（B01 核心）

v1（Java `RecoveryControlRecords.identity`、Python `control_history.load`）都要求**精确字段集** `{formatVersion installationId restoreRoots initialCommandSha256}`，因此新增字段必须升版：

```json
{ "formatVersion": 2, "authorityKind": "INITIAL_NORMAL_INSTALL",
  "installationId": "<uuid>", "restoreRoots": ["<abs>", "..."],
  "closedAuthority": "<abs>", "initialCommandSha256": "<64hex>" }
```

- `authorityKind ∈ {INITIAL_NORMAL_INSTALL, RECOVERY}`：**由供给时点确定并不可变**。
- `closedAuthority`：真实关闭权威路径（绝对路径），由供给时点写入，运行期只读。
- Java：`version()` 目前只接受 `1`；需按文件类型区分版本（identity 接受 1/2，其余仍只接受 1）；v1 identity **不得用于初次接纳**（`CONTROL_INITIAL_AUTHORITY_KIND_REQUIRED`）。
- Python：`control_paths.ControlLocation.identity()` 产出 v2；`control_history.load` 接受并按版本校验字段集；`control_store._bootstrap` 通过 `{**location.identity(), 'initialCommandSha256': …}` 自动带上新字段。

### 3.3 P2 文件允许集（逐名冻结，`InitialNormalStore.java:15-17,95-102`）

`coordinator.lock`(1 字节)、`initial-normal-request.json`、`initial-normal-request.json.pending`、`initial-normal-committed.json`、`initial-normal-committed.json.pending`、`initial-normal-unknown.json`、`initial-normal-unknown.json.pending` —— 共 7 个名字，**B1 不得增删**；`layout()` 对未知产物抛 `INITIAL_NORMAL_UNKNOWN_ARTIFACT`。

### 3.4 身份/路径绑定（接纳必须同时成立）

| 绑定 | 校验点 | 失败码 |
| --- | --- | --- |
| 配置 `installationId` == P3 identity | `RecoveryControlRecords.identity` + 快照比对 | `CONTROL_INSTALLATION_MISMATCH` |
| P3 `authorityKind == INITIAL_NORMAL_INSTALL` | 接纳步骤 S3-a（见 §4.1） | `CONTROL_INITIAL_AUTHORITY_KIND_REQUIRED` |
| P3 历史**恰好 1 条**记录、phase=QUIESCING、`current.json` 锚点=1、无 `intents/` 条目、`admission.json.targetRevision=1` 且 `intentSha256=ZERO_HASH` | S3-a（复用 `RecoveryControlIntents.validate` 的空意图分支） | `CONTROL_INITIAL_HISTORY_REQUIRED` / 既有意图码 |
| P3 首条记录的 command 逐字段绑定 P1 | S3-a：`commandId==P1.commandId`、`epochId==P1.epochId`、`installationId==P1.installationId`、`evidenceSha256==P1.sourceEvidenceSha256`、`manifestSha256==P1.sourceEvidenceSha256`、`snapshotId==P1.commandId`、`recoverySessionId==P1.epochId`、`affectedWarehouseIds==["INITIAL-INSTALL"]`、`possibleLossFrom==possibleLossThrough==requestedAt`、`requestedAt <= P1.requestedAt` | `CONTROL_INITIAL_BOOTSTRAP_MISMATCH` |
| 配置 `closedAuthority` == P3 `closedAuthority`（规范化后逐字相等） | S2 前置校验 | `RECOVERY_CLOSED_BINDING_UNTRUSTED` |
| `closedAuthority` 的**父目录存在且为目录** | S2（`requireUnclosed` 之前） | `CONTROL_CLOSED_PARENT_MISSING` |
| `closedAuthority` 及其 `.pending` 变体**不存在** | S2：`store.requireUnclosed(boundClosed)`（**强制**，见 §3.5） | `INITIAL_NORMAL_CLOSED_AUTHORITY` |
| P2 原件 installation == 配置 == P4 `recovery_initial_normal.installation_id` | 复用 `InitialNormalVerification.match` | `INITIAL_NORMAL_DATABASE_*` / `RECOVERY_INITIAL_INSTALLATION_MISMATCH` |
| P4 `service_mode=NORMAL` 且 `recovery_epoch==P1.numericEpoch` | 同上 | `INITIAL_NORMAL_DATABASE_STATE` |
| P4 关闭链缺席（`recovery_installation_binding` 无行） | 同上 | `INITIAL_NORMAL_CLOSED_HISTORY` |
| P3 写者协议 v2 | `RecoveryWriterProtocol.validate(root, true)` | `CONTROL_ADMISSION_PROTOCOL_REQUIRED` |
| P5 无孤儿租约、本进程租约可登记 | §7.2 | `RECOVERY_LEASE_OUTSTANDING` / `RECOVERY_LEASE_UNRECORDABLE` |

**为什么这闭合了 B01**：初次允许态不再由“QUIESCING 恢复历史”推断，而是由 (a) 供给时声明的 `authorityKind=INITIAL_NORMAL_INSTALL`、(b) 恰好一条且逐字段绑定可信原件的引导记录、(c) P2 完成文件与 P4 初次行三者同时成立；恢复权威（kind=RECOVERY 或记录数>1）**结构上无法**满足初次接纳。`closedAuthority` 由信任身份固定，运行期不能替换成任意（不存在的）目录；且必须“父目录存在 + 条目不存在”才成立，因此“传一个不存在的路径绕过关闭事实”不再可行。

### 3.5 “供给 → 登记 → 核验 → 首次接纳”四步（输入/守卫/唯一结果）

| 步 | 输入 | 守卫（全部必须成立） | 唯一结果 |
| --- | --- | --- | --- |
| 供给 P3(初次) | 配置身份、restoreRoots、`closedAuthority` 绝对路径、P1 原件 | 路径绝对/非链接/本地固定盘（`control_paths.checked`）；restoreRoots 非空且与 P3 不重叠；`closedAuthority` 父目录存在、条目不存在；`authorityKind=INITIAL_NORMAL_INSTALL` | 生成 v2 identity + `coordinator.lock`/`writers.lock`(1 字节) + `writers.json`(v2) + 单条绑定 P1 的 QUIESCING 引导记录 + `current.json`(锚点1) + 空 `intents/` + `admission.json`(targetRevision=1, ZERO_HASH)；否则拒绝并不落盘（`CONTROL_INITIAL_BOOTSTRAP_*`） |

## 4. 接纳原子性与证据连接隔离

### 4.1 接纳流程（四步，锁内/锁外明确）

```
admit(kind) -> RecoveryOperationLease
  S0 启动门：state==READY && !FATAL；P5 进程记录已建立且持锁            [无锁，内存/启动期完成]
  S1 数据库侧证据：evidenceSource.evidence().initial()                  [受限只读连接；无协调锁]
       -> 非 null；service_mode==NORMAL；closedHistory==false；recovery_initial_normal 行在场
  S2 文件侧证据：store.admissionSnapshot()                              [P2 协调锁，仅文件读，随即释放]
       -> 先 requireUnclosed(boundClosedAuthority)；父目录存在；条目不存在
       -> committed==true；无 UNKNOWN/无 .pending；installation 与配置一致
       -> InitialNormalVerification.match(files, S1) 逐项相等
  S3 控制权威 CAS + 租约登记 —— 全程在 P3 协调锁内（有界等待）：
       a current := RecoveryControlHistory.load(location, checkpoint)
       b require startup.equals(current)                       -> CONTROL_INSTANCE_STALE
       c require current.installationId == 配置 == S2.installation
       d require RecoveryInitialAuthority.validate(current, P1) -> kind/单记录/QUIESCING/绑定
       e require RecoveryWriterProtocol.validate(root, true)     -> CONTROL_ADMISSION_PROTOCOL_REQUIRED
       f require RecoveryControlIntents.requireAdmission(root)   -> CONTROL_CLOSING_INTENT/_INTENT_INCOMPLETE
       g require noOrphanLease(leaseRoot)                        -> RECOVERY_LEASE_OUTSTANDING
       h require publishLeaseRecord(leaseRoot, operationId)       -> RECOVERY_LEASE_UNRECORDABLE
       i writer := RecoveryWriterLease.acquireLocked(root)        [L1 命中或新开；references++]
       j registry.registerRoot(kind, writer, {installation, recordSha256, requestSha256, leaseRecord})
     <--- 线性化点：j
  S4 绑定当前线程到根；测试探针；返回根租约
```

锁内只做文件读 + P5 记录发布 + 内存登记（无 DB I/O、无业务写、无用户代码）；DB 证据读（S1）在锁外，用受限只读能力；P2 读取（S2）用 P2 自己的协调锁且**不与 P3 锁嵌套**；P5 的进程文件锁只在 S3-g 内**瞬时**获取后释放（锁序固定为 P3 协调锁 → P5 进程文件锁，无反向路径）。

## 5. 接纳线性化证明（B06）

### 5.1 事实表：可变性、写者、所持锁、失效方式、校验位置

| 接纳事实 | 谁可变 | 必须持有的锁 | 失效方式 | 登记时校验位置 |
| --- | --- | --- | --- | --- |
| P3 关闭意图（`admission.json`/`intents/`） | 控制推进（Python `ControlStore.apply`） | `coordinator.lock` 独占（`control_store.py:40`） | 新意图 → `targetRevision>revision` | S3-f（同一 P3 临界区内） |
| P3 历史/锚点/身份 | 控制推进；供给 | 同上 | revision/hash 变化 | S3-a/b |
| P3 `authorityKind`/`closedAuthority` | 仅供给时点（identity 不可变） | —（写入时由供给流程保证） | identity 被替换 → hash/身份不符 | S3-d + §3.4 路径比对 |
| P2 请求/完成文件 | 显式离线协调器（`InitialNormalStore.prepare/completeLocked`） | P2 `coordinator.lock` | 新增/替换 → 字节冲突码 | S2（P2 临界区内） |
| P2 UNKNOWN 标记 | 登记路径 `unknownLocked()` | P2 `coordinator.lock` | 出现即永久拒绝 | S2（同一临界区，`layout()` 内） |
| P4 初次行 / 模式 / epoch | 显式离线协调器（DB 事务）；模式仅由受认可路径置回 NORMAL | 数据库事务 + `server_state FOR UPDATE`（`RecoveryProjectionRows.lockState`） | 行变更/模式变更 | S1 读 → S2 `match()`；**每次业务写**再由 `ServerState` 校验 |
| P5 租约集合 | 任意已接纳进程（登记/退役）；UNKNOWN 后不再退役 | P3 协调锁（登记）+ P5 进程文件瞬时锁（存活判定） | 记录残留/孤儿 | S3-g/h |
| L2 写者租约 | 每个已接纳根 | 自身 L1 引用计数 | 引用归零释放 | S3-i（L1 命中即复用） |

### 5.2 证明一：P3 意图 vs 根登记

- 意图唯一写者是控制推进，其在 `control_store.py:40` 进入 `coordinator.lock` **独占**后才执行 `prepare()`（追加意图并推进 `admission.json`）。
- 根登记（S3-f 检查 + S3-j 登记）在同一把独占 `coordinator.lock` 的**同一临界区**内完成。
- 独占锁的互斥性 ⇒ 临界区内不可能插入他人对该权威的推进；“检查意图”与“登记根租约”是同一临界区的两半，**不存在可被插入的时点**（不是“窗口很小”）。
- 登记后出现的意图属“已接纳操作的收尾”范畴（§6.4），且此时控制推进的 L3-② 独占尝试会因 L2 被持有而失败（`CONTROL_WRITERS_ACTIVE`），耐久意图保留等待最后写者退出（`CLOSING_INTENT.md:9,15`）。

### 5.3 证明二：P2 UNKNOWN vs 根登记

- P2 的唯一写者是离线协调器路径，且它必须持 P2 `coordinator.lock`（`InitialNormalStore.locked`）；接纳的 P2 读取（S2）持同一把锁 ⇒ 与“读文件侧证据”互斥。
- 因此 UNKNOWN 只可能出现在 S2 **之前**（S2 读到 `INITIAL_NORMAL_UNKNOWN` 并拒绝）或 S2 **之后**。后者的排除不靠时间窗口，而靠**跨根互斥规则**：登记路径要求 P5 `leases/` 为空（`INITIAL_NORMAL_APPLICATION_ACTIVE`），而任何已接纳的根都在 P5 留下租约记录；因此“应用正在服务”时无法完成登记，UNKNOWN 不可能在接纳生存期内产生。
- 反向也成立：接纳（S3-g）要求无孤儿租约，而登记不会留下租约记录（登记不使用租约），故登记不会误伤接纳的判据。
- 残余前提（显式声明）：该证明假设登记与接纳不同时由**同一操作者**用不同工具绕过 P5；直接改 P2/P3 文件或 SQL 改 `server_state` 属项目明确禁止的非受认可恢复，不在威胁模型内（`ServiceModeStartupNotice.java:16` 已记录同一口径）。

### 5.4 证明三：数据库模式变化 vs 根登记（含框架写）

- 接纳**不主张**模式稳定：模式不是接纳的授权来源，而是每次业务写在事务内用 `server_state FOR SHARE` 重新判定的条件（`ServerState.java:21-33`）。
- **框架写（Spring Session）不经该守卫**（`JdbcIndexedSessionRepository` 用自己的 `JdbcTemplate` 直接写 `SPRING_SESSION`），所以框架写的模式约束只能由接纳门承担。结构证明：
  1. 受认可的模式变更是恢复链投影写入（`RecoveryProjectionRows`），它只能由取得**写者租约**的事务执行（`RecoveryLeasedTransaction` → `RecoveryWriterLease.acquire`），并且只能由控制推进驱动（关闭/恢复阶段）。
  2. 控制推进要完成历史与指针提交，必须取得 `writers.lock` 的**独占**（L3-②）；任何存活根都持 L2 共享锁 ⇒ 推进在写者未排空时**不能完成**。
  3. 根租约覆盖整个操作（含最终 Session 保存，§6.3）⇒ 只要框架写可能发生，L2 就被持有 ⇒ 模式变更无法完成。
  4. 推进完成后：初次路径的接纳条件（单记录 QUIESCING）已被破坏，新根一律拒绝；此后不再存在任何经初次路径的框架写。
  ⇒ 结论：**框架写要么发生在模式变更之前（属已接纳操作的允许收尾），要么不可能被接纳**。这不是窗口论证，而是“推进必须独占写者锁 + 租约覆盖框架写 + 推进后接纳条件永久失效”的三段式。
- 也不依赖“再次读一次”：接纳不重复读模式；模式责任在写入点（业务写守卫）或结构互斥（框架写）。

### 5.5 证明四：P5 孤儿租约 vs 根登记

- 租约记录在**故障前**建立（S3-h），登记与检查同处 P3 临界区（S3-g/h）⇒ 任一接纳的临界区要么看到孤儿并拒绝，要么它自己在孤儿产生前完成（属“已存在操作”）。
- UNKNOWN 触发 fail-stop（§7.3）⇒ 进程文件锁由 OS 释放 ⇒ 其未退役租约对所有后续接纳（含新进程启动）成为孤儿 ⇒ 阻断不依赖任何故障时写入成功。
- 唯一非阻断情形是“接纳的临界区在孤儿可观测之前已结束”，此时该操作与故障操作同属“故障前已接纳”，按 §6.4 允许收尾，不属新根。

| 反例 | 屏障/故障点 | 唯一预期 |

### 6.2 调用方判定表（B03：禁止无绑定静默回退）

`RecoveryAdmittedDataSource.getConnection()` 的分支判定，按“线程绑定 → 当前请求上下文 → 无上下文”顺序：

| 情形 | 判定依据 | 进入分支 | 结果 |
| --- | --- | --- | --- |
| A 合法旧连接层调用（无请求、无线程绑定；如 105 回归、运维/测试直连） | 线程无绑定 **且** `RequestContextHolder` 无可观察请求 | **旧连接级租约路径**（`acquire()`：协调锁 + `requireAdmission` + L1） | 语义与 v1/105 完全一致 |
| B 有效请求根 | 线程绑定有效且根存活（身份、相位、白名单通过） | 根租约借用：`registerSubOperation(CONNECTION)`（计数 +1） | 不重查准入；关闭后仍可收尾 |
| C 失效令牌 | 线程带 `operationId` 但注册表无此根/已 RELEASED/`installationId` 不符 | **拒绝** | `CONTROL_OPERATION_RELEASED` / `_FORBIDDEN`；**绝不回退到 A** |
| D 请求上下文丢失 | 线程无绑定，但 `RequestContextHolder` 有当前请求且该请求带根令牌 | **拒绝** | `RECOVERY_OPERATION_CONTEXT_LOST`；**绝不回退到 A** |
| E 未绑定异步线程 | 线程无绑定，且 Spring 的异步请求属性可见（`WebAsyncManager` 继承属性） | **拒绝**（fail closed） | 同 D；若需支持，须显式 `bindThread` 并另立批次 |
| F 子操作类型越集 | 线程绑定有效但类型不在白的允许集 | **拒绝** | `CONTROL_SUBOPERATION_FORBIDDEN` |

- 105 既有语义保留：分支 A 是唯一“无上下文”路径，判定条件比 v1 更严（必须**同时**无绑定且无可观察请求），因此不会把 D/E 误判成 A。
- 强制 S7/S8 拒绝：D/E 由“请求上下文存在但线程未绑定”明确判定，不依赖时序；C 由注册表判定。
- 生产代码不得清除线程绑定；静态测试断言注册表仅由门/过滤器/监听器/子租约修改。

### 6.3 HTTP 生命周期（按实际依赖证据重写，B02）

依赖证据（jar 路径与 SHA-256 见[纠错记录](R09_C2_G0_CORRECTION_REVERIFY_2026-09-28.md) §2）：

- `SessionRepositoryFilter` 继承的是 **`org.springframework.session.web.http.OncePerRequestFilter`**（不是 Spring Web 的那个），`DEFAULT_ORDER = -2147483598`（= `Integer.MIN_VALUE + 50`）。
- 其 `doFilterInternal` 在**方法体内**先 `chain.doFilter(wrapped…)`，随后 `commitSession()`；异常表中 `38–48 → 56 any` 分支同样在 `commitSession()` 后重抛 ⇒ **最终 Session 保存发生在该过滤器体内、链返回之后（或异常路径）**，不在容器外层回调。
- 其 `doFilterNestedErrorDispatch` 覆写为再次调用 `doFilterInternal`（嵌套 ERROR 分派也会提交 Session）。
- Spring Session 的 `OncePerRequestFilter.doFilter`：属性名 = `getClass().getName()+".FILTERED"`；已过滤且 `DispatcherType==ERROR` → `doFilterNestedErrorDispatch`（随后 return）；已过滤且非 ERROR → 直接 `chain.doFilter`；未过滤 → 置属性 → `doFilterInternal` → finally 移除属性。**没有** `shouldNotFilter*` 钩子。
- Spring Web 的 `OncePerRequestFilter`：`shouldNotFilterAsyncDispatch()` 与 `shouldNotFilterErrorDispatch()` **默认都返回 true**（跳过），`skipDispatch` 用 `isAsyncDispatch`/`jakarta.servlet.error.request_uri` 判定。⇒ **我们的过滤器必须显式覆写两者为 false**，否则 ERROR/ASYNC 分派完全不经过我们。

定稿生命周期：

1. `RequestIdFilter`（`@Order(HIGHEST_PRECEDENCE)`）先写入 `requestId`。
2. `RecoveryRequestAdmissionFilter`（`@Order(Ordered.HIGHEST_PRECEDENCE + 10)`，普通 Servlet 过滤器、不放进 `SecurityFilterChain`，覆写两个 `shouldNotFilter*` 为 false）：
   - 请求属性中**已有本过滤器写入的根令牌**（属性在释放前不移除）→ **复用**该根，`bindThread(当前线程)`，不新建根、不重复登记；
   - 否则执行 §4.1 接纳，写入令牌并绑定线程。
3. 业务链（含 `SessionRepositoryFilter` 与其 `commitSession()`、其嵌套 ERROR 提交）在根存活期内运行。
4. 过滤器体内 `finally` 只做 `enterFinalizing()`（幂等），**不释放**根。
5. `RecoveryRequestRootListener.requestDestroyed()` 释放根：这是容器保证的“所有分派（REQUEST/ERROR/ASYNC）结束之后”的唯一边界；ERROR 分派若在新线程运行，第 2 步的复用分支会为该线程补绑定，从而使该分派内的 Session 写仍被覆盖。
6. ASYNC 分派：属性已被 Spring Session 过滤器移除后会再次进入其 `doFilterInternal`（即异步分派也会提交 Session）——我们的根此时仍存活（由第 5 步释放），但**异步工作线程**若未绑定则其任何连接借用按 §6.2-E 拒绝；B1 定案为 fail-closed，并对该路径提供专门容器证据（§10.2 S8）。
7. 异常退出：链抛异常时同样走第 4/5 步（`finally` + `requestDestroyed`），根必被释放；`RecoveryConnectionHandler` 的毒化判定照旧（§7）。

### 6.4 关闭后规则（允许/禁止清单）

| 类别 | 关闭意图落盘后 | 依据 |
| --- | --- | --- |
| 新根操作 | **禁止**，`RECOVERY_CLOSING` 503，在任何业务写之前 | §4.1 S3-f |
| 已接纳根的后继连接借用（含最终 Session 保存、事务收尾） | **允许** | 根存活；§5.2 证明登记后不再重查意图 |
| 已接纳根开展无关新业务 | **禁止**：令牌单次、根在 `requestDestroyed` 退役、`operationId` 不复用、未绑定线程拒绝、子操作白名单 | §6.2 |
| 框架写入（Session 保存/错误分派提交/嵌套 ERROR 提交） | 属已接纳根收尾，**允许** | §6.3、§5.4 |
| Worker/文件/渲染的新任务 | **禁止启动**；已启动者按各自批次规则收尾（不进 B1） | §6.5 |

### 6.5 Worker/文件/渲染规则（设计定稿，不进 B1）

同 v1：Worker 根＝一次 `runOnce` 全程（`REQUIRES_NEW` 续租借同一根）；文件入口根＝“先落文件后落库”完整动作；渲染根＝启动前到进程树退出确认。三者均使用 P5 租约记录与同一孤儿规则。

## 7. UNKNOWN 与多进程语义（B05）

### 7.1 触发点

沿用既有判定：`RecoveryConnectionHandler.poison(...)`（提交/回滚/关闭/`setAutoCommit`/`abort`/SQLState `08`）与 `RecoveryTransactionLease.close()` 的未确认完成。判定逻辑不变。

### 7.2 P5 操作租约登记：故障前建立的跨进程阻断依据

- **进程记录**：进程启动、服务就绪前，创建 `processes/<processIdentity>.json`（`processIdentity` 每次启动随机、绝不复用），并**持有该文件的独占 OS 锁直到进程结束**。内容是安装身份与启动信息，不是证据。
- **租约记录**：每次接纳（§4.1 S3-h）在 P3 临界区内创建 `leases/<operationId>.json`（暂存 + 原子改名），字段：`formatVersion, installationId, operationId, kind, processIdentity, authorityRecordSha256, requestSha256, startedAt, leaseSha256`。
- **孤儿判定**：受理扫描时，对每条租约记录找其 `processIdentity` 的进程记录：
  - 进程记录缺失/不可读 → 孤儿；
  - 进程记录存在但**独占锁可被取得**（持有者已死）→ 孤儿；
  - 独占锁被他人持有且非本进程 → 存活中的在途操作，**不算孤儿**（正常并发）。
  - 本进程自己的租约记录一律跳过。
- **登记=阻断前提**：创建租约记录失败 ⇒ 拒绝接纳（`RECOVERY_LEASE_UNRECORDABLE`），绝不在没有耐久记录的情况下放行任何操作。⇒ “故障时写标记失败”不再影响阻断保证，因为**阻断依据在故障前就已建立**。
- **退役**：仅当根关闭且确认“无未决结果”（所有子操作已关闭、无毒化连接、事务提交/回滚已确认、Session 保存已提交或已回滚）时删除租约记录；删除失败（含权限/占用）⇒ **保留记录**（下次判定为孤儿 → 拒绝），方向始终是“拒绝”。
- **阻断范围**：任一孤儿 ⇒ 所有进程的新根拒绝（S3-g）、新进程启动失败（阶段 0）——即使用户要求覆盖的四种情形（标记无法创建、进程死亡、其他进程仍运行、新进程启动）。

### 7.3 UNKNOWN 的行为（fail-stop，不依赖故障时写入）

1. 立即置位本进程 L1 毒化（既有语义）；
2. **尽力**写 `leases/<operationId>.unknown.json`（原因、时间、授权 revision/hash）——**审计用途**，其成败不影响阻断；
3. 不退役该租约记录；
4. **fail-stop**：以固定退出码终止 JVM（`Runtime.getRuntime().halt(70)`，不跑关闭钩子、不做优雅关闭、不释放任何租约），使进程记录锁由 OS 释放 ⇒ 该租约立刻成为所有其他进程/新进程可观测的孤儿。

| 对象 | UNKNOWN 后 |
| --- | --- |
| 同进程新根 | 拒绝（L1 `CONTROL_WRITERS_ACTIVE`；halt 后进程不存） |
| 其他进程新根 | 拒绝（孤儿判定 `RECOVERY_LEASE_OUTSTANDING`） |
| 新进程启动（准入启用） | **启动失败**，不提供服务 |
| 已接纳且未涉 UNKNOWN 的操作 | 允许完成收尾；其租约正常退役 |
| 控制推进 | L2 未被释放（halt 前持有）→ 独占尝试失败、耐久意图保留；halt 后控制推进可推进，但孤儿仍阻断接纳 |

### 7.4 明确不保证 / 不做的

- 不保证“故障瞬间之前已完成临界区的接纳”被阻断：它们是故障前已接纳的操作（§5.5）。
- 不新增解除端点、不自动清除孤儿、不提供生产释放；孤儿记录的清除属生产释放能力（七类生产决定与生产释放继续关闭，`localDeletionAllowed=false`）。**注意**：这里“未授权”的是**解除**权限；**阻断**保证不依赖任何权限或故障时写入。
- 不把“一次 `INNODB_TRX=0`”或“锁已释放”当作排空声明（见 §7.5）。
- 残余前提：若 `halt` 本身无法执行（理论上不可发生）或操作系统未释放文件锁（断电后重放场景），阻断依据退化为“租约记录仍在”（仍拒绝）——两条路径都指向拒绝。

### 7.5 排空判据（合取）

同 v1 七项（无本实例事务 / `liveRoots==0` 且子操作 0 / 本进程 L2 已释放 / 无渲染子进程 / 无未入 DB 引用的暂存活动 / P3 无 `.pending` / P5 无孤儿与未退役租约）。B1 不实现排空声明。

## 8. 启动与框架边界

### 8.1 强制顺序与竞争结果

顺序：**显式许可 → 迁移 → 初始化 → 业务入口**（同 v1）；新增阶段 0 的 P5 检查（进程记录建立 + 无孤儿租约）。竞争结果表同 v1（两进程迁移、无许可 vs 未迁移库、迁移中监听、双初始化、关闭意图待决、孤儿在场），其中“孤儿在场”为新进程**启动失败**。

### 8.2 B1 隔离测试前提

预置非空库；`OUTBOUND_MIGRATE=false`、`outbound.bootstrap.enabled=false`；**并显式 `spring.session.jdbc.cleanup-cron=-`**（§8.3）；P2/P3/P5 由供给步骤预置；数据库/账号/端口/storage 根逐轮独立；执行前按 §12 完整查重（本轮不分配任何编号）。

### 8.3 Session 过期清理（B04 纠正）

**实际依赖事实**（javap 证据见纠错记录 §2）：`JdbcIndexedSessionRepository.DEFAULT_CLEANUP_CRON = "0 * * * * *"`，Boot `JdbcSessionProperties.DEFAULT_CLEANUP_CRON` 同名同值；`afterPropertiesSet()` 在 `cleanupCron != "-"` 时创建自有 `ThreadPoolTaskScheduler`（线程名前缀 `spring-session-`）并按 `CronTrigger` 调度 `cleanUpExpiredSessions()`；`setCleanupCron` 要求非空且合法。⇒ **清理调度默认存在**，它是一条**框架自有线程上的 DB 写路径**，且不经 `ServerState` 守卫。

定案：

| 项 | 决定 |
| --- | --- |
| 生产默认 | **不改**（本轮零配置变更；`application.yml` 保持现状） |
| B1 隔离测试 | 显式 `spring.session.jdbc.cleanup-cron=-` **禁用**，并在冒烟中断言**实际生效**：进程内不存在名为 `spring-session-*` 的线程，且无该仓库的调度任务 |
| B1 启动守卫（新） | 准入启用（`outbound.recovery.admission.enabled=true`）且清理未禁用 ⇒ **启动失败** `CONTROL_SESSION_CLEANUP_UNCOVERED`（避免“未被租约覆盖的框架写”在生产配置下悄然开启） |
| 生产默认清理路径 | 单列为**未覆盖入口**，后续批次处理（须为其建立自有根：kind=`SESSION_CLEANUP`、子操作 `SESSION_WRITE`、显式 `bindThread`）；本轮不补实现，也不再以“未配置 cron”宣称该路径不存在 |

### 8.4 ERROR/ASYNC/multipart 逐项

| 路径 | 批次 | 依据/条件 | 隔离方式 | 冻结结论 |
| --- | --- | --- | --- | --- |
| Session 最终保存 | B1 | §6.3 证据：在 `SessionRepositoryFilter.doFilterInternal` 体内、链后与异常路径 | 专用库/账号/端口 | 纳入，由请求根覆盖至 `requestDestroyed` |
| 嵌套/独立 ERROR 分派 | B1 | 同过滤器覆写 `doFilterNestedErrorDispatch`；Spring Web 默认跳过 ERROR ⇒ 我们显式不跳过 | 真容器触发错误响应 | 纳入：复用同一根；新线程由复用分支补绑定 |
| ASYNC 分派 | B1 | Spring Session 过滤器在异步分派会再次执行 `doFilterInternal`；工作线程默认未绑定 | 测试专用 `b1probe` 异步端点（生产无异步控制器） | **fail-closed**：未绑定线程的 DB 访问拒绝（§6.2-E），响应 503 `RECOVERY_OPERATION_FORBIDDEN`；不因“生产无异步代码”宣称覆盖 |
| multipart 暂存 | B1 | 解析在 `DispatcherServlet` 内（我们的过滤器之后） | 真 HTTP 上传 + 测试控制器读取部件 | 纳入请求根范围；不配置 `spring.servlet.multipart.location` |
| Session 过期清理 | 后续批次 | §8.3 | 测试期禁用并验证 | **不纳入 B1 实现**；生产默认路径单列未覆盖 |
