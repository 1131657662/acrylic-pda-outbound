## 1. 现状（只有读的结论，均已核对源码）

| 事实 | 源码位置 | 含义 |
| --- | --- | --- |
| 锚点只以 **`anchorId = sha256(anchor)`** 落盘，**不落锚点本身** | `RecoveryLeaseRoots.verify()`：`require(sha256(anchor).equals(text(marker,"anchorId")), "CONTROL_ANCHOR_MISMATCH")`；`provision()` 写 `anchorId` | 换锚后**旧锚无法从盘上恢复**，只能由外部重新提供 |
| 锚点由**外部显式供给**（配置项），从不写进可写控制树 | `RecoveryEffectConfiguration.Settings`：`@ConfigurationProperties("outbound.recovery.effect-gate")`，`private String anchor`；仅在 `crossProcessEnabled` 时校验 64 位十六进制；`RecoveryLeaseRoots.anchor()` 注释"never persisted inside the writable P5/P3 trees" | 锚点保管在系统之外（密钥管理/配置源） |
| 只有**当前一代**参与校验 | `verify()` 只比对当前 `anchorId`；无代次号、无历史条目 | **没有运行期历史 keyring** |
| 被锚点封存的对象共 **3 类** | ① 进程记录 `processes/<pid>.json`：`RecoveryLeaseProcess`（`:38` 写 `anchorTag=hmac(anchor,value)`）② 租约记录 `leases/<uuid>.json`：`RecoveryLeaseScan:152` ③ 锚定索引 `leases/index.json`：`RecoveryLeaseScan:99/159`、`RecoveryLeaseRoots:42` | 重锚需要**逐条重打**这三类 |
| 进程记录**永不删除** | `RecoveryLeaseScan:79-81`"Process records are never touched — a dead process's record stays as the evidence that it existed" | ⇒ 重打集合**单调增长**，不随时间自然缩小 |
| 租约记录在每次 `check()` 内**同步**退休孤儿 | `RecoveryLeaseScan:61-65`：发现孤儿即 `retireOrphans` 并抛 `RECOVERY_LEASE_OUTSTANDING`（fail-closed） | ⇒ 存活租约数由"当前在途操作"决定，规模小 |

## 2. 两个候选方案（互斥，需择一）

### 方案 A：运行期多代 keyring（零停机轮换）

- **机制**：盘上新增 `keyring.json`（受与 `lease-root.json` 同级保护），保存 **N 代**条目 `{generation, anchorId, wrappedAnchor}`；每个受封存对象增加 `generation` 字段；校验时"按对象自身的 generation 取对应锚点"；新增显式 `rotate` 入口把当前锚点移入历史、写入新代。
- **优点**：轮换**无需停机**；旧对象在保留期内仍可读。
- **缺点/风险**：
  1. **必须把锚点本身落盘**（或落成被另一把密钥包裹的密文）——这与"锚点从不进入可写控制树"的现有设计**正面冲突**；一旦落盘，控制树被读取即等于锚点泄露（现有模型的威胁假设是"树可被篡改但不可读"）。
  2. 受封存对象要加 `generation` 字段 ⇒ **格式变更**，与既有 `formatVersion` 校验、`files.sha256` 证据快照、以及"格式变更必须显式拒绝"的既有约定冲突；需要一次受控迁移。
  3. 多代并存意味着**旧代不失效**，轮换的"止损"价值下降（旧锚泄露后仍能用）。
- **适用**：存在**无法停机**的硬约束，且能接受"包裹后的锚点落盘"。

### 方案 B：停机重锚 ＋ 重打存活记录（B4 提案原建议；推荐）

- **机制**：维护窗口内 ①停写 ②以**新锚点**启动 ③对三类对象**逐条重打**（进程记录全部、存活租约记录、索引）④校验通过后恢复。**不新增 keyring 文件、不落锚点**。
- **关键前置（当前缺失，必须补）**：重打需要**旧锚点**去验证/解密既有对象——而旧锚**不在盘上**。因此重打必须满足其一：
  - **(B1) 外部同时提供新旧两把锚点**（推荐）：运维在维护窗口从密钥源取旧锚＋新锚，重打工具用完即弃；盘上永不落锚点。
  - **(B2) 重打前先"读出并验证"旧对象**：用旧锚验证通过后直接用新锚重写（仍需旧锚在场）。
  - **(B3) 放弃旧对象**：仅用新锚重建 `processes/`／`leases/`／`index.json` 为空树。**代价**：丢失"死进程曾存在"的证据链与锚定索引——与"进程记录永不删除"的既有约定冲突，**不建议**。
- **优点**：不动格式、不落锚点、与既有 fail-closed 约定一致；**与 B4 提案一致**。
- **缺点**：需要**维护窗口**；重打时长随**进程记录总数**线性增长（见②的实测）。

## 3. 推荐与需要用户裁定的事项

**推荐方案 B（停机重锚＋重打存活记录），并采用前置 (B1)**：外部在窗口内同时提供新旧锚点，盘上永不落锚点；这与现有"锚点从不进入可写控制树"的威胁模型一致，且无需格式变更。

需要裁定的三点（本页不代替决定）：

| # | 待裁定 | 选项 |
| --- | --- | --- |
| ① | 是否需要"运行期历史 keyring" | **A**（落盘包裹锚点、格式变更、零停机）还是 **B**（不落锚点、需窗口、格式不变） |
| ② | 旧锚点的保留期限与销毁方式 | B4 提案建议"只读归档 90 天后销毁"；是否照此 |
| ③ | 重打是否允许丢弃死进程记录 | **不允许**（保留证据链，时长随记录数增长）还是**允许**（(B3)，放弃证据） |
