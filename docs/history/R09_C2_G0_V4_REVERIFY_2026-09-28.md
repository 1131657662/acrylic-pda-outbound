## 3. K1：重证 P5 接纳与退役

- **反例时序（v3 成立）**：(1) 接纳 B 执行后探针（S3-k），逐记录处理；(2) 处理到进程 A 的记录时 A 仍持有其进程记录锁 ⇒ 判“在途、不阻断”；(3) **A 在此之后死亡**；(4) B 继续处理其余记录并成功返回；(5) B 完成接纳 ⇒ 此时 A 的租约已是孤儿，但本应阻断的接纳已通过。v3 的 S13-③ 只覆盖“前后探针**之间**死亡”，未覆盖“后探针**内部**、某条记录已处理之后的死亡”。
- **次要矛盾（v3 成立）**：v3 称“`halt` 无法执行时租约仍在，所以其他进程仍拒绝”，但 v3 状态表明确把“仍持进程锁的其他进程租约”判为在途、**不阻断** ⇒ 本机隔离不会自动变成跨进程拒绝。
- **退役尾部（v3 成立）**：v3 说“任一步失败都不删除记录”，但步骤 5–6（释放 L1/L2）在删除之后，失败时已无法兑现该描述。
- **涉及状态与锁**：P5 租约记录与进程记录（独占锁）、P3 协调锁、`commit()` 的持久化效果点。
- **修订强制点**：
  1. **撤回** v3“线性化点＝后探针完成 ⇒ 扫描完成时无孤儿”的结论；明确探针只能证明“在其处理某条记录的时刻，该记录的属主存活/已死”（§5.3 逐记录步骤）。
  2. 新增**孤儿可观测性单调性引理**（死者的进程锁一旦可取得就永远可取得；进程身份不复用）⇒ 任何在判定点之前可观测的孤儿都不会消失。
  3. 新增**效果门**（§4.2）：已接纳根的**每次持久化效果**（`RecoveryConnectionHandler.commit()`、因而覆盖业务事务与 Spring Session 的 `commitSession()`）在提交前于 P3 锁内再探针一次；发现孤儿 ⇒ 回滚＋围栏。自动提交的变更语句默认拒绝，须显式登记 `AUTOCOMMIT_WRITE`。
  4. **围栏序列 F1–F5**（§5.5）：F1 本进程 FENCED（拒新根/新子操作/新借用）→ F2 尽力写审计记录 → **F3 释放进程记录锁**（他人下一次探针即判孤儿）→ F4 保留 L2（同时阻止控制推进完成）→ F5 halt。**跨进程阻断的实际成立条件是 F3 或进程死亡**，不依赖 halt、不依赖故障时写入成功；删除“halt 失败仍全局阻断”的错误结论。
  5. **退役分决策期/决策后期**并给终端语义（§5.6）：决策期任一未确认结果 ⇒ 不删除＋围栏；决策后期（释放 L1/L2）失败**不构成 UNKNOWN**，处置为“重试→仍失败则日志＋本 JVM 置毒化＋FENCED”，**不需要跨进程阻断**（无未退役租约），并说明由此留下的只是一个会随进程结束消失的多余 L2 写者锁。
- **唯一结果**：任何已接纳根的持久化效果，要么在其效果门处看到孤儿并**回滚＋围栏**，要么其效果门时点无孤儿可观测。
- **失败分支**：F3 失败（理论不成立）⇒ 重试 F3，仍失败直接 F5（OS 释放锁）；F5 失败 ⇒ F1＋F3 仍生效，他人仍在下一次探针拒绝；决策后期失败 ⇒ 无孤儿遗留（终端语义如上）。
- **未来测试屏障/断言**：S17（提交前制造孤儿 ⇒ 唯一码 `RECOVERY_LEASE_OUTSTANDING`、无业务行落库、围栏记录、DB 前后摘要一致）；S18（在后探针内部 kill A ⇒ 该次探针可返回成功，但 A 的下一次效果门/新根被拒、A 的租约对其余进程为孤儿）；另测 F3 后“进程记录存在但锁可取得 ⇒ 其他进程判孤儿”的正/反两向。
- **本轮判定**：**设计级成立**，并具名一项**固有并发边界（G3）**：死亡若发生在某效果的判定点之后、该效果完成之前，则该效果与故障并发——任何基于锁的协议都无法排除“与在途提交并发的故障”；v4 将其显式列为环境属性与影响范围（恰好这些已过判定点的效果，其后所有判定点均拒绝），**不标为已关闭，也不以“窗口小”淡化**。

## 4. K2：分离根生命周期与分派绑定

- **反例时序（v3 成立）**：(1) 请求 A 开启异步，初始分派过滤器 `finally` 因 `isAsyncStarted()==true` **不解绑**；(2) 该容器线程被线程池复用给请求 B；(3) A 的根仍存活、绑定仍在 ⇒ B 在该线程上的借用会命中 A 的根，而“根仍有效”无法证明它属于当前执行。
- **涉及状态与锁**：注册表的线程→根绑定、根生命周期（`requestDestroyed`）、过滤器分派边界、嵌套 ERROR 分派。
- **修订强制点**：绑定改为**按分派**且**深度计数**——`bindDispatch(线程)` 进入本次分派时 +1，`finally` **无条件** −1；归零即解绑；嵌套 ERROR 分派成对 +1/−1，外层作用域不被提前清除；根生命周期仍保留到 `requestDestroyed`；`requestDestroyed` 防御性清除全部绑定；退役前要求深度为 0。**不再以 `!isAsyncStarted()` 作为解绑条件。**
- **唯一结果**：异步未结束时，其原线程被复用后不携带 A 的绑定；B 只能使用 B 自己的根；A 的 ASYNC 分派进入时只绑定该次分派。
- **失败分支**：绑定表无条目（未进入分派）时借用 ⇒ `RECOVERY_OPERATION_REQUIRED`（fail closed）；深度归零后残留 ⇒ 由 `requestDestroyed` 清除并计入拒绝统计（视为缺陷信号，测试断言为 0）。
- **未来测试屏障/断言**：S15——A 异步在飞、原线程被 B 复用；在 A 的异步窗口内、无分派作用域处借用被拒（`RECOVERY_OPERATION_REQUIRED`）；A/B 各自根数为 1；轨迹证明 B 未继承 A。
- **本轮判定**：**设计级成立**。

## 5. K3：补齐关闭意图的合法调用链

- **反例时序（v3 成立）**：(1) 初次接纳只接受 `authorityKind=INITIAL_NORMAL_INSTALL`；(2) Python `apply()` 对 INITIAL 一律 `CONTROL_AUTHORITY_KIND_FORBIDDEN`；(3) 真实关闭权威创建/切换属 B9；(4) 但 S4a 要求“独立控制工具发布关闭命令并得到 `CONTROL_WRITERS_ACTIVE`、留下耐久意图” ⇒ 按 v3 规定的调用链**无法到达**；测试若直接写 `admission.json` 就是伪造生产接线。另经源码核对：INITIAL 权威也不能借 `intents/` 表达“仅关闭”（`RecoveryControlIntents.validate` 要求合法阶段转移，见 §2）。
- **涉及状态与锁**：P3 `identity.json`、`history/`、`current.json`、`intents/`、`admission.json`、`writers.lock`（L3-②）。
- **修订强制点（独立的最小受限能力，本轮只定设计）**：
  - **入口**：`ops/control_close_intent.py`（新）＋`ops/control_cli.py` 子命令；`purpose=INITIAL_CLOSE_INTENT`。
  - **锁序**：P3 协调锁（`coordinator.lock` 独占，有界）→ 只读校验 → 暂存＋原子发布意图产物 → 释放前对 `writers.lock` 做一次 L3-② 独占尝试（结果仅作信息反馈）。
  - **文件变更（仅此一项）**：新增 `initial-close-intent.json`（暂存名 `initial-close-intent.json.pending`），内容 `{formatVersion, installationId, authorityKind=INITIAL_NORMAL_INSTALL, targetRevision(=current+1), currentRecordSha256, reason, operatorId, requestedAt, intentSha256}`；**不改** `history/`、`current.json`、`intents/`、`admission.json`、`writers.json`。
  - **Java 消费**：`RecoveryControlHistory.layout` 允许集加入该文件名（含 `.pending`）；新增 `RecoveryInitialCloseIntent` 校验（仅对 INITIAL 权威有效、自哈希正确、target 自洽、幂等/冲突码）；`requireAdmission` 在其在场时拒绝新根（沿用 `CONTROL_CLOSING_INTENT`，HTTP 映射 `RECOVERY_CLOSING`，使应用语义与恢复型一致）。
  - **Python 消费**：`ops/control_history.py` 允许集同步；`ops/control_store.py` 的 `apply/inspect` 继续拒绝 INITIAL（不因该能力放宽）。
  - **错误码**：`CONTROL_AUTHORITY_KIND_FORBIDDEN`（恢复型工具用于 INITIAL）、`CONTROL_INITIAL_CLOSE_DUPLICATE`、`CONTROL_INITIAL_CLOSE_CONFLICT`、`CONTROL_WRITERS_ACTIVE`（信息性，产物仍发布）、`CONTROL_COORDINATOR_BUSY`。
  - **权限边界**：该能力**只能**发布该意图产物；不得推进恢复阶段、不得创建/切换真实关闭权威、不得解除孤儿、不得提供生产放行、不得删除或改写产物（无“取消关闭”路径）。
- **唯一结果**：INITIAL 权威下，可经真实协议入口发布关闭意图；`history/` 与 `current.json` 不变；此后新根 503 `RECOVERY_CLOSING`；在途根按 §5.6 收尾。
- **失败分支**：锁忙 ⇒ `CONTROL_COORDINATOR_BUSY`（不发布）；已有产物且内容不同 ⇒ 冲突码（保留原产物）；L3-② 失败 ⇒ `CONTROL_WRITERS_ACTIVE`（信息性，产物保留）；暂存写入失败 ⇒ 仅留 `.pending` ⇒ Java 侧视为关闭意图在场（fail closed，方向为拒绝）。
- **未来测试屏障/断言**：S16——工具在根存活期间发布意图；断言产物在场、`history/current/intents/admission` 逐字节未变、L3-② 返回 `CONTROL_WRITERS_ACTIVE`、新请求 503；Python 侧同批用例覆盖幂等与冲突。

## 6. K4：把在途守卫前移

- **反例时序（v3 成立）**：(1) 离线登记取 P3 锁，先做 P2 文件与 DB 事务；(2) 之后才做 P5 无在途检查；(3) 此时若已有在途租约（接纳先完成），登记却**已经产生副作用**才拒绝 ⇒ 与“接纳先完成时登记必须拒绝且 P2 不被改动”的复验要求冲突。共同持 P3 只解决交错，不补救检查前已发生的副作用。
- **涉及状态与锁**：P5 租约集合、P2 文件、P4 事务、P3 协调锁。
- **修订强制点**：登记在 P3 临界区内的顺序固定为 ①身份/kind/形状校验（只读）→ ②**P5 在途/孤儿检查**（只读）→ ③之后才取 P2 锁并做 P2/P4 写入与登记事务 → ④锁内发布完成或 UNKNOWN。四步表（设计 §3.5）、接纳伪代码（§4.1）、证明（§5.1）与 S13-① 预期统一为此顺序。
- **唯一结果**：存在在途租约时，登记的**全部副作用为零**（P2 目录树哈希不变、P4 行数与摘要不变）；不存在在途租约时，检查结果在整个临界区内有效（任何接纳都需同一把 P3 锁，无法在检查与写入之间发布租约）。
- **失败分支**：①/②失败 ⇒ 唯一码（`RECOVERY_INITIAL_AUTHORITY_*`／`INITIAL_NORMAL_APPLICATION_ACTIVE`／`RECOVERY_LEASE_OUTSTANDING`）且零副作用；③之后中途失败 ⇒ 既有 `.pending`/UNKNOWN 语义（接纳拒绝）。
- **未来测试屏障/断言**：S13-①——接纳先完成（持租约）时并发登记，断言登记拒绝、**P2 树哈希与 P4 摘要不变**；反向断言登记先完成时接纳 S2 读 UNKNOWN 并拒绝。
- **本轮判定**：**设计级成立**。
