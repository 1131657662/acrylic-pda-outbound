# M71 Demo 真机操作与测试指南

日期：2026-09-16｜当前交互：B（0.1.6 起）｜依据：[完整 Demo 计划](DEMO_PLAN.md)｜安装：[安装说明](DEMO_INSTALL.md)

**Demo现场验收已完成（2026-09-16）：**按键映射（含正面扫描键）、B模式现场复验、真实断电恢复均通过，见[M71_ACCEPTANCE_REPORT.md](M71_ACCEPTANCE_REPORT.md)。取下电池立即黑屏，重启后仍为12包、3610kg、待处理0，明细、输入、审计及按键配置与断电前一致。按Q17结束Demo，不再要求现场操作；下文扩展测试步骤保留为参考，100ms/200ms初始时延目标未达记录保留，不启动额外自动测试。

## 1. 核心规则

**扫描校验通过后自动保存；手输 F1 校验后回车或大按钮确认。看到“已保存（本地）”才算保存成功。**声音只是辅助。Demo 所有订单都不可作为车辆离场凭据。

| 操作 | 结果 |
| --- | --- |
| 扫描完整条码 | 写入输入事实、自动校验、持久自动意图、最终事务保存；无需回车 |
| 实体 Enter | 仅绑定当前手输/旧人工候选；已自动保存时不重复计包 |
| 重复、错产品、满计划 | 显示原因，禁止成功音；回车或大按钮确认当前错误后恢复队列；后续自动项按自身持久策略保存，手输项仍需单独确认 |
| 手输 F1 | 首次进入手输，输入完整条码；再按 K1/F1 校验，然后 Enter 保存 |
| 辅助 F2 | 恢复未完成确认、确认失败、放弃未确认项、撤销最后一包、备注、更新测试授权 |
| K1/K2 | 通过全部按键验证向导采集 keyCode/scanCode/source 并确认应用；未完成时保持旧配置，不视为完整实测通过 |
| 更多 → 订单汇总 | 每产品独立计划、包数、重量；总上限为计划之和，没有 116 包硬编码 |
| 更多 → 冻结 | 固定本地测试证据，之后不能继续保存；不是服务器成功回执 |

存储故障时暂停输入。已确认项不能放弃或删除，应先恢复查询其是否已保存，再决定补做或拒绝。被业务明确拒绝的确认不会转成可重试存储错误。

## 2. 每台设备先记录

建立唯一测试编号，例如 `M71-设备序列号-20260915-A01`。每次记录 APK SHA-256、Android 构建号、扫码头型号/固件、扫码配置、实体键码、density/fontScale、音量、电量、温度、剩余空间、数据库规模、操作者及开始结束时间。

现场操作员负责条码与实际按键；测试人员负责已知顺序清单、录像/录音和日志；负责人据证据签署通过/失败。不能只记录“感觉不卡”。

## 3. 首次接入，约 10～20 分钟

1. 启动，等待库存导入完成，在诊断页记录 WAL / FULL 和设备信息。
2. 从内置 sku 样本选择已知在库且属于计划产品的包，预先写下完整条码。新建各产品计划明确的测试单。
3. 扫一包不按回车：校验通过自动变为 1 包并响 PASS；再按回车不增加数量。
4. 持续长按回车，不得多保存；空候选按回车，再扫描另一包，不能把上次回车借给新包。
5. 同一包快速扫两次，应看见重复错误或第二次尝试记录，不能用时间防抖丢掉尝试。
6. 按 K1/K2、正面和左右扫描键，检查真实 keyCode/scanCode/source/deviceId/action/repeatCount。某些扫描键由系统消费，记录这一事实，不猜键码。
7. 手输一个合法条码，不按 F1 直接 Enter 应拒绝保存；F1 校验后 Enter 才保存。损坏条码需逐字对照。
8. 进入手输或弹窗时扫描，应拒收且提示；切到后台后不得伪称继续可靠扫码。

### 双通道必须单独验收

首选仅广播、关闭自动回车。分别在主屏、手输、弹窗测试厂家键盘注入和结束符。若厂家服务自动注入的 Enter 与人工按下无法可靠区分，判设备接入未通过，先解决厂家配置/接口。此 Demo 不会凭猜测声称能区分两种完全相同的键事件。

## 4. 软件负载与真实负载分开测

更多 → 软件压测 → 选择速率。0.1.3 起，程序先生成隔离合成库存和独立期望序列，再通过应用内部专用 Android 广播 `com.acrylic.m71demo.SOFTWARE_SCAN` 输入，沿用条码 String Key，0.1.6 起由同一自动策略处理，不模拟 Enter；0.1.3～0.1.5 的模拟确认仅为历史机制。接收端不对外导出；输入来源写为 `TEST_INJECTION`，不属于厂家实际广播或人工回车。M71 禁止普通应用发送厂家扫码 Action，0.1.2 首轮因此中止并已保存证据，不能计为通过。真实扫码仍使用厂家 Action，单独验收。

| 速率 | 每轮时间 | 预期数量 |
| --- | --- | --- |
| 1 包/秒 | 10 分钟 | 600 |
| 2 包/秒 | 10 分钟 | 1,200 |
| 3 包/秒 | 10 分钟 | 1,800 |
| 4 包/秒 | 10 分钟 | 2,400 |

压测期间留在主屏，不扫描实物、不手输、不按确认或弹出对话框。切到后台会停止软件输入，必须将该轮标为中止。生成库存和准备时间不计入连续输入时间；末条输入后等待队列排空再导出。

0.1.4 修复模拟确认时序：只有对应 `captureId` 的广播输入成功入队后，才等待 50ms 并发出该条测试确认；2 秒接收超时即中止，不向下一条借用确认。确认仍由独立事件进入业务队列。PSS 采样改到后台线程。验收必须核对实际广播间隔、总持续时间和完整数量，不能因为等待回执使实际速率下降就宣称达标。0.1.3 的 80 次接收 / 74 次保存 / 6 条未确认失败记录已保留，见 [真机验收记录](M71_ACCEPTANCE_REPORT.md)。

0.1.5 只在进程内缓存最近一份字段和签名完全相同、已成功验签的测试授权，逐次检查时间与业务资格。启动后首次输入、稳定运行和重启恢复须分别记录；不能剔除首分钟慢记录。若使用 `cmd package compile` 等改变 ART 编译状态，必须保留前后状态，将结果标为单独的诊断对照；不得替代普通安装的验收结论，也不得将其自动加入安装脚本作为“已修复”。

随后用真实扫码头、应用自动保存和外部已知条码顺序，分别完成同样四档测试。软件通过不能代替真实光学输入、人工节奏和实体键。至少三轮连续 4 包/秒复测，并做 30 分钟混合操作；设备能力达不到时如实记失败并优化复测，不降低吞吐、耐久或数据一致要求。

### 历史库

更多 → 诊断 → 历史库，预置 36 万条扫码和 108 万条审计、900 张各 400 包的合成历史订单，覆盖 90 天。先预留至少 2GB 可用空间；生成期间不切单、不接收业务输入，可关闭应用中止，保留已完成整单。再次生成会新增一组，不覆盖旧数据。

此数量是容量压测夹具，不是用户承诺日量。来源为 `HISTORY_FIXTURE`，状态为 `CONFIRMED_TEST_FIXTURE`，所有历史均为合成，不是云端确认。按整单事务生成，限制每批 400 行对象，不把 36 万条加载到内存。生成后记录实际文件大小、WAL 和 PSS，重复关键负载及导出。

## 5. 成功标准与计算

每轮先执行 `verify_export.py`，按安装说明指定导出目录、外部期望序列和诊断文件。脚本核对字符、输入顺序、确认/保存/审计关联、唯一性、原设备、周期、克数及各产品汇总，并计算可观测时延。

| 指标 | 验收/工程目标 |
| --- | --- |
| 字符、顺序、重复、漏收/确认/保存 | 外部基准 → 广播 → 输入 → 确认 → 保存逐项一致，差额 0 |
| 4 包/秒 10 分钟 | 2,400 合法输入、对应有效确认和有效保存，无忙碌拒收、队列溢出 |
| 自动完整输入接收→耐久保存；人工回车→耐久保存分别计算 | P95 ≤100ms，P99 ≤200ms；同时保留最大值 |
| 每包数据库服务总耗时 | 接收、预校验、确认、最终保存合计均值 ≤125ms 的工程目标 |
| 广播回调 | P99 ≤5ms 的工程目标 |
| 停止输入后 | 已确认有效项 1 秒内排空，不以丢弃实现 |
| 内存 | 进程总 PSS 峰值 ≤250,000,000 字节，记录采样间隔与观测局限 |

0.1.6 和 MANUAL 路径预校验有单独持久事务，共四段；0.1.7 的 AUTO 将预校验/意图合并，共三段。测量包含全部业务处理，不能只统计最终 INSERT。比较单调时钟时须同一设备启动段；手机显示时间回拨不影响 `orderScanSeq`。诊断采样丢弃、缺文件、缺外部序列都必须标“证据不足”。PSS 每秒采样有采样盲点，可增加 `dumpsys meminfo`/分析工具观测，不能称其覆盖任意瞬时尖峰。

0.1.6 的 `autoReceiveToCommit` 从完整字符串进入应用记录时间起算，包括排队、接收/预校验/意图/最终事务；`confirmToCommit` 只统计 MANUAL。自动内部登记意图不算物理回车；跨 boot 样本另计不混算延迟。P95/P99 初始目标未降低，完整样本超标须记“技术目标未达”并分析，不按单纯平均值宣布达标。V2.3 §16.1把它们与4包/秒、零遗漏、顺序及内存等必须门槛分开，不能自动把技术目标升级为无限调优的硬门槛。广播到达前的光学解码不包含在此指标中。

### B 模式新增必测

扫描不用回车即可保存；重复只失败不增包；错误后 B/C 广播保持 RECEIVED，处理错误后按原序号自动恢复；手输候选阻止后到自动项越序；自动保存后的迟到回车不能确认后一手输候选；自动意图各故障点重启仅完成一次；旧库 BROADCAST+MANUAL 候选仍待人工确认。自动策略/输入来源在导出中一致，审计有且只有对应的持久保存意图。正面扫描键须由用户按实际位置重新核实。

数据核对脚本的内部一致通过不自动判定性能达标。软件负载在本机模拟器上的结果只作开发回归；M71 四档、历史库和实体链路必须各自签署。

## 6. 音效

在诊断页试听保存/错误音，确认预载完成。应用音效可以关闭；厂家扫描头的识别音需在厂家设置单独检查。

- 事务完成后才调用 SoundPool；播放失败显示提示，不回滚已经保存的明细，也不重存。
- 诊断记录 `SOUND_REQUEST`、streamId；0 表示未播放。静音时记录 `SOUND_DISABLED`。
- 事务完成 → play 调用：P95 ≤20ms 初始目标。
- 用外部录音/录像校准事务反馈标记与真实扬声器起音，记录仪器采样率/帧率和误差。实际起音 P95 ≤100ms、P99 ≤150ms 初始目标。
- `SoundPool.play()` 返回和日志时间不是声学起音；没有外部测量时该项必须写“未验证”。4 包/秒时检查无长音排队、错误优先、戴手套仍能看懂反馈。

## 7. 故障、重启和断电

更多 → 诊断 → 单次故障注入。选择点位，再选择“模拟存储错误”或“终止本应用进程”。注入仅触发一次。

| 点位 | 故障后预期 |
| --- | --- |
| BEFORE_CAPTURE（D0） | 可能没有持久输入，不能曾显示已保存；与外部清单核对 |
| AFTER_CAPTURE（D1） | 按原条码/来源/序号恢复；AUTO 策略复核后自动保存一次，MANUAL 仍待人工确认 |
| AFTER_CONFIRM / BEFORE_SAVE（D2） | 确认已持久，按原上下文恢复一次；过期/周期改变明确拒绝 |
| DURING_SAVE（D3） | 明细、guard、数量、重量、审计、终态全部提交或全部回滚 |
| AFTER_SAVE（D4） | 即使没来得及显示/响音，已提交明细仍唯一存在 |
| AFTER_FEEDBACK（D5） | 已成功反馈记录可恢复，不能因重启再保存一份 |
| BEFORE_FREEZE_REGISTER（D6） | 文件可能成为未关联孤儿，但不能有虚假的已冻结控制记录 |
| AFTER_FREEZE_REGISTER（D6） | 原冻结目录可重查，摘要一致，不能生成第二份有效冻结目标 |

D1～D5 各至少 20 次进程终止，之后各至少 10 次实际突然断电。断电应由现场人员按 M71 厂家允许的方法实施。拔掉 USB 但电池仍供电、正常关机、重启、force-stop 都不是突失电。

真正重启后测试授权要求复核；已保存记录不删除，未确认记录不自动换新授权。确认失败提示/处理未确认项后才能更新测试授权并继续。保留发生异常时的原始现场清单、屏幕、DB/WAL/SHM 和审计，不卸载重装“修复”。

### 冻结文件的解释

正文文件各自刷盘，manifest 记录各文件摘要，文件完成后才登记冻结控制。每次导出独立目录；目录里只有 `.tmp` 或没有完整 manifest 的文件属于未完成导出。只有数据库 `local_submission` 所引用且摘要、内容校验均通过的目录才是有效冻结证据，其他目录保留作故障分析。文件目录元数据/外置存储层的突失电耐久仍必须由 D6 真机验证，不能以普通文件写入测试替代。

## 8. 业务和恢复边界

单独验证：仅剩一个计划名额、两个已确认候选竞争；重复条码；错产品；48 小时到期；时间回拨；当前包周期变化；恢复代次变化；按原设备区分同样的序号；撤销后重新扫码。

“模拟后台状态/恢复代次”只设置隔离测试状态，用于观察待上传、待审、模拟确认/恢复冲突的 UI 和保存边界。没有服务器、实际幂等上传、主管审批或生产扣库。受模拟状态影响的订单不重新放行，另建测试单继续下一轮。

## 9. 小屏与手套

在真实 480×800、默认和加大字体下检查：11 位条码完整可见，产品/重量/确认状态无截断，底部三个按钮可触达，键盘不会把候选与操作遮住，3 个以上产品可在汇总页逐项查看。滑动查看更多历史和菜单，不能把被滚动隐藏的错误当成处理完。

戴手套依次做：扫描→自动保存、损坏条码手输→F1→Enter/大按钮、F2 异常备注/失败处理、多产品来回交错、双击/长按、退出与恢复。实际操作者能正确判断“识别、待确认、已保存、失败”，才算交互通过。

### 2026-09-16：B 模式数据库事务优化（0.1.7）

0.1.6 的自动路径有接收、预校验、意图、最终保存四次耐久提交；首轮总时延超标，证据保留。0.1.7 对 AUTO 的预校验与自动意图使用一个 Room 外层事务，包含原状态变更及确认审计，整体成功返回后才记 CONFIRM_DURABLE。原始接收仍先独立落盘；最终 scan/guard/数量/重量/审计/终态仍同一事务提交。原来自动路径的 WAITING_CONFIRM 中间态不单独对外宣称耐久。MANUAL 与旧候选仍保持四段和人工确认。

全链路计时从完整接收开始，不删除任何阶段。VALIDATED 的 dbServiceNs 包含自动确认同一事务，CONFIRM_DURABLE 标记 serviceIncludedIn=VALIDATED、耗时为 0，避免重复累加；实际总时延不依赖这些分段指标。D1 原接收后故障、D2 组合事务后故障、D3 最终保存中故障均保留验证。WAL/FULL、失败处理、原序号和幂等语义不变。性能门槛未改，须新 APK 真机复测。

### 2026-09-16：全部按键向导（0.1.8）

使用 [按键向导](KEY_VALIDATION_GUIDE.md) 顺序完成正面扫描、左扫描、右扫描、Enter、K1、K2、返回，各两次完整按下/松开。最终确认前保留旧映射；无倒计时，可续测。按键位置需要操作者核对；注入事件和截图不能标为真实按键通过。向导内扫描只写诊断，不计包。完成后再回业务页核验 B 模式真实扫描与手输链路。
